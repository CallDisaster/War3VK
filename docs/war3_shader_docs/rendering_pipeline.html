最近修复 (2024-12-30)

1. Ring Buffer 竞争崩溃修复

问题：在渲染世界对象（CUnit）时，war3_shader_api.cpp 中的 std::vector::push_back 触发 Access Violation (0xC0000005)。

根本原因：

  • std::vector 的 push_back 可能触发内存重分配
  • 重分配过程中，如果另一个线程通过 GetDrawCalls 读取同一个 buffer，会访问已释放的内存
  • 原子索引只保护了"选哪个 buffer"，没有保护 buffer 内部的堆操作

解决方案：将 std::vector 替换为固定大小的 std::array

// 修改前
std::vector<DrawCall> g_drawCallBuffers[kRingBufferSize];

// 修改后
struct DrawCallBuffer {
    std::array<DrawCall, kMaxDrawCallCount> items;
    uint32_t count = 0;
};
DrawCallBuffer g_drawCallBuffers[kRingBufferSize];

当前限制

限制项 当前值 说明
最大 DrawCall 数量 kMaxDrawCallCount = 8192 每帧最多捕获 8192 个 shadowCaster，超出部分将被截断
Ring Buffer 大小 kRingBufferSize = 3 三缓冲，隔离读写线程
内存占用 约 sizeof(DrawCall) * 8192 * 3 固定静态分配，不使用堆内存
为什么选择固定数组？ 固定大小数组完全避免了堆分配和扩容操作，从根本上消除了多线程竞争的风险。 对于 War3 这种场景复杂度有限的游戏，8192 条 DrawCall 上限已经足够。

未来改进：三缓冲 + Fence 同步

如果未来需要突破 8192 上限，可以恢复 std::vector 并实现完整的 CPU Fence 同步：

sequenceDiagram participant Writer as CS Thread (写) participant Buffer as DrawCallBuffer participant Reader as GetDrawCalls (读) Writer->>Buffer: ready.store(false) Writer->>Buffer: items.clear() Writer->>Buffer: push_back(...) Writer->>Buffer: ready.store(true, release) Writer->>Buffer: g_readIndex.store(writeIdx) Reader->>Buffer: g_readIndex.load(acquire) Reader->>Buffer: while (!ready.load()) yield Reader->>Buffer: return items.data()

实现要点

struct DrawCallBuffer {
    std::vector<DrawCall> items;
    std::atomic<bool> ready{ false };  // CPU Fence 标记
};

// 写入侧
buf.ready.store(false);  // 开始写，标记未就绪
buf.items.clear();
// ... 填充数据 ...
buf.ready.store(true, std::memory_order_release);  // 写完了

// 读取侧
while (!buf.ready.load(std::memory_order_acquire)) {
    std::this_thread::yield();  // 等待写完
}
return buf.items.data();
注意：此方案要求所有读者遵守"不跨帧持有指针"的契约。 如果外部模块将 GetDrawCalls 返回的指针缓存到下一帧使用，仍然会导致崩溃。

概述：两条线程的故事

War3MapReforge 的渲染架构基于 DXVK 的双线程模型：

App Thread (应用线程)
运行游戏主逻辑、处理 D3D9 API 调用、捕获渲染状态和 DrawCall 数据。
CS Thread (Command Stream 线程)
异步执行实际的 Vulkan 渲染命令、重放被捕获的 DrawCall、执行阴影/描边/后处理。
关键概念：App Thread 负责"记录"，CS Thread 负责"执行"。两者通过 EmitCs() 传递 Lambda 闭包进行通信。这种设计让游戏主线程不会被 GPU 阻塞。

渲染阶段识别

系统通过 TLS 标记和 Stage 编号识别当前渲染的内容类型：

Terrain (地形)
Stage 9-10, 包含地面、水面、阴影贴花
WorldObject (世界对象)
Stage 11-13, 单位、建筑、可破坏物
UI (界面)
Layer == UI, 所有 2D 界面元素
Skybox (天空盒)
特殊标记, 不参与阴影捕获
// War3TryCaptureShadowCaster 中的识别逻辑
const auto layer = War3RenderState::CurrentLayer();
if (layer == War3RenderLayer::UI) return;  // 跳过 UI

const bool terrainCaster = (stage == 9 || stage == 10);
const bool objectCaster  = (cat == WorldObject) && (stage == 11 || 12 || 13);

if (!terrainCaster && !objectCaster) return;  // 只捕获有效 caster
