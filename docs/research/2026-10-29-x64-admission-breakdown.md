# x64 准入段拆解：EndScene 返回前的时间花在哪里

2026-10-29，Claude 在[流式命令列表](2026-10-29-x64-stream-constant-ring.md)之后实施。只加默认关闭的
计时与开发门读方；不改协议、不接游戏、不部署玩家 DLL、不提交/推送/发布。Game.dll guard 保持。

## 为什么测这一段

流模式安静轮 1,025 draw 完成中位 2.76–2.90 ms，其中只有约 0.16 ms 在 EndScene 返回之后，
其余全在 x86 生产者 → 4 槽队列 → 工作线程写命名管道 → 宿主逐条读、解码、预检、录制、回复
这条准入路径上。在动手改传输或录制之前，先把这段的组成量出来，避免凭猜测优化。

## 计时方式

新增默认关闭的 `WARVK_D3D9_ADMISSION_PROFILE=1`（宿主与代理都读取）。关闭时不读时钟。
三方各自累计，在每次被接受的 EVENT Issue 之后切一个样本，最多 128 个，超出计为 dropped：

- **生产者**（x86 调用线程）：发布次数、队列满时等待的次数和时长（backpressure）、
  同步调用等待（callWait）。
- **工作线程**：空闲、写管道、等回复；DrawBatch 单独累计写与等回复。
- **宿主**：空闲、读、回复；DrawBatch 的读、解码、apply、回复；apply 内再分
  prepare（逐索引预检）、record（录制）；record 内分常量填充、状态绑定（其中 8 个纹理槽的
  采样器/图像视图循环单列）、DXVK draw 调用本身（提交脏描述符/管线/动态状态）。
  FlushDraws、WaitEvent 与其他 op 的 apply 分开记。

读方 `AutoTest/analyze_d3d9_admission.py` 严格检查：三方样本数一致、序号连续不重排、
计数单调、无 dropped、字段集合精确；每个区间必须恰好是一帧工作量（批次数 = ⌈draw/32⌉、
draw 数相等）；嵌套阶段不得超过其外层（例如 常量+绑定+draw ≤ 录制、采样器 ≤ 绑定、
解码+预检+录制 ≤ apply）。去掉前 4 帧预热，取 40 帧。

派生量：
- `hostBatchDispatch` = apply − 解码 − 预检 − 录制（op 分发等杂项）。
- `hostRecordOther` = 录制 − 常量 − 绑定 − draw（环切片、阶段准备、循环开销）。
- `batchOutsideHostWork` = 工作线程批次往返 − 宿主 apply − 宿主回复，
  即管道拷贝、宿主读、两次线程唤醒。这是同一机器上两个时钟的差，**是估计值，不是测得的传输时间**。

全部是 CPU 墙钟时间，不是 GPU 执行时间。

### 结论

1. **整条链是串行的。** 工作线程每写一条就等宿主回复，管道传输和宿主处理从不重叠；
   生产者 4 槽队列很快填满，准入时间的 75%（1.90 / 2.52 ms）是 x86 调用线程在等空位。
   每批往返 69 µs 中，宿主 apply 占 65%，管道拷贝+宿主读+唤醒约占 29%，回复约 6%。
2. **宿主 apply 的大头是 DXVK 自身。** 状态绑定 + draw 调用约 1.0 ms/帧，
   即每 draw 约 1.0 µs（绑定 431 ns、draw 540 ns），占宿主 apply 约 70%。
   解码、预检、常量填充、分发合计约 0.33 ms，不是主要矛盾。
3. **8 槽采样器循环不是瓶颈。** 每 draw 只有约 54 ns（录制的约 4%），
   采样器对象已复用、绑定只是比较。之前"逐 draw 重绑 8 个纹理槽很贵"的猜测不成立。
4. **group 比 stream 多出的宿主时间都在"录制其他"**（0.65 对 0.11 ms），即 flight 槽/批次 UBO
   处理；流模式已消除这部分。绑定和 draw 在两种模式下相同。
5. 对照原生 DXVK D3D9（推断，未测）：原生应用线程只把命令写进 CS chunk，`DxvkContext` 在独立的
   CS 线程上执行，并且只在 D3D9 状态真正变化时设置对应 DXVK 状态。我们的宿主在 IPC 线程上
   逐 draw 直接调用 `DxvkContext`；本轮未开已有的 `WARVK_D3D9_BATCH_STATE`（仅在同一批内跳过未变的
   7 组管线状态，不含着色器、缓冲、纹理、采样器、规格常量和视口），所以每个 draw 都重设全部状态，
   DXVK 因此每个 draw 都重新做管线状态查找。
   这能解释为什么宿主 1,025 次 draw 的绑定+提交就有约 1 ms，而进程内本地整条路径只要 0.5–0.6 ms。

## 范围与限制

- 合成 fixture，只覆盖 SM3 DrawBatch 路径。这个 fixture 每 draw 之间实际改了多少状态
  未统计；真实游戏的状态变化频率可能更高，脏跟踪的收益在游戏中可能更小。
- 固定功能 `DrawFixed`（游戏主体）不在本 fixture 里；它在代理侧仍是每 draw 一次同步 IPC。
- 每轮安静的端只有一两个；40 帧样本，p99 即接近最大样本，不作尾延迟认证。
- `batchOutsideHostWork` 是两个时钟之差，可能有噪声。

## 建议的下一步（按收益/风险）

1. **固定功能 draw 走异步批次**（原路线 ②，保持第一）。准入数据说明一次往返的传输+唤醒
   约 20 µs，而目前每个 FF draw 都要付一次完整同步往返，不是 32 个 draw 共摊一次。
   War3 主体是固定功能，这仍是游戏规模下最大的一项。复用现有异步批次准入与整批原子预检。
2. **宿主录制按原生方式做脏跟踪**（新增）。把现有仅限批内的 `WARVK_D3D9_BATCH_STATE` 扩展为：
   在打开的流列表内记住上一次已录制的
   着色器、顶点/索引缓冲、输入布局、光栅/混合/深度状态、规格常量、视口和各纹理槽，
   未变化就不调用对应 `DxvkContext` setter；开新命令列表时保守地全部重绑。
   目标是每 draw 约 1.0 µs 的绑定+提交。FF 与 SM3 都走 `recordDraw`，两条路径同时受益。
   用同一 `--admission-profile` 复测；像素/VVL/故障门必须与当前完全相同。
3. **让传输与录制重叠**（原路线 ④ 的前置一步）。宿主在预检通过后立即回复、再录制
   （预检是原子拒绝点，录制期的 DXVK 异常本来就是终止性失败，语义不变），或者宿主单独的
   接收线程。串行每批 69 µs，重叠后上限约为宿主自身工作（约 45–56 µs/批）；
   之后再用共享内存环去掉管道拷贝与唤醒。
4. **暂不处理**：采样器循环、解码、预检、常量填充（每项 ≤ 0.17 ms/帧）。

建议仍按作者未批准的 1.5×/2× 门槛口径记录，本批不改变门槛状态。
