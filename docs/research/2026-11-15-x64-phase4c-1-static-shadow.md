## 1. 结论

- **阴影 pass 本身在 x64 宿主里运行，用的是 x86 设备的同一份源码。** 没有改写成执行器。宿主编译 pass 的九个源文件，
  它引用而宿主编不进来的符号（诊断与游戏状态）由一个服务文件提供；输入由三种记录重建（光照 492 字节、帧事实 56 字节、投射体 136 字节）。
- **两种模式像素逐字节相同。** 对照门 15 帧在进程内与四个代理变体（直连、流、流 + 命令环、流无校验层）下全部 0 像素差异。
  没有用到容差：x86 与 x64 各自算的级联矩阵没有产生任何可见差别。
- **两种模式里 pass 的账目相同。** 运行 25 次、渲染阴影图 20 次、画接收 24 次、用了 69 个投射体、拒绝 1 个（动态缓冲）、
  往级联里画了 236 次、拒绝不完整集合的回放 3 次，五组逐项相等。
- **校验层第一次覆盖阴影 pass，报了四类违规，已修，修后 3 个带校验层的宿主会话 0 错误 0 警告。**
  其中三类是 pass 原本就有的（进程内的命令流从来没有校验层），一类只在宿主的目标布局下出现。修正前后进程内的 14 帧哈希逐个相同（§4）。
- **x86 内存**：代理模式开阴影 x86 增量 0 字节（私有 2.4 MiB 不变）。进程内开阴影私有内存多 2.9 MiB（另两次开发运行是 6.3 和 30.3 MiB，
  与 4a/4b 见到的波动是同一现象）。
- **原有路径没有变。** 特效门的 154 个哈希字段（7 组 × 11 帧）、GPU 参照门的 48 个像素哈希都与阶段 3 逐个相同，
  两道门共 41 个带校验层的宿主会话 0 错误 0 警告。正向切口仍是 19 个符号、24 条边。
- **只做了静态投射体。** 动态缓冲、蒙皮、alpha 测试、点光、时间滤波归 4c-2；生命周期的对照测试归 4c-3；
  x86 游戏内发记录归阶段 5.1。GPU 蒙皮与原生灯光分离不迁移（发布版里是关的）。**没有在游戏里跑**（§7）。

## 3. 对照的帧

夹具画一块地面和三个箱子（固定管线变换，物体空间顶点，投射体的几何就是 draw 自己的缓冲），太阳手工给定
（不随时间运动、不做时间调色、光照时钟固定），级联 1024 纹素，目标 64×64。15 帧，按顺序：

| 帧 | 发了什么 | 期望（两模式都满足） |
|---|---|---|
| `world` | 无记录、无标记 | 基准 |
| `shadow`、`shadow-again` | 三个箱子 | 有阴影；两帧相同 |
| `sun-moved` | 太阳换方向 | 与 `shadow` 不同 |
| `sun-back` | 太阳回到原方向 | 以后同样的帧都等于它；与 `shadow` 差 11 个像素（见下） |
| `terrain` | 三个箱子加地面（地形类投射体） | 等于 `sun-back`：平地被画进级联，但不投出阴影 |
| `one-caster` | 一个箱子 | 与 `sun-back` 不同 |
| `no-casters` | 空集合，已封口 | 等于 `one-caster` |
| `unsealed` | 三个箱子，没有 `ShadowFrame` | 等于 `one-caster` |
| `short-count` | 两个箱子，`ShadowFrame` 说有三个 | 等于 `one-caster` |
| `dynamic` | 三个箱子，其中一个在动态缓冲里 | 等于 `one-caster`；账目记 1 个动态缓冲拒绝 |
| `strength-zero` | 阴影强度 0 | 等于 `world` |
| `shadow-ssao-smaa` | 三个箱子加 SSAO 与 SMAA 记录 | 与 `sun-back` 不同：特效处理的是带阴影的世界 |
| `off` | 有标记、无阴影记录 | 等于 `world` |
| `shadow-return` | 三个箱子 | 等于 `sun-back` |

另有 12 帧无阴影、12 帧有阴影的计时帧，以及 12 条畸形记录的拒绝（光照 4 条、帧事实 3 条、投射体 5 条），两模式都在生成处拒绝。

三条是这次跑出来才知道的 pass 行为，已钉进门禁，两模式一致：

- **空集合与不完整集合都不发布新阴影图，画面停在上一张。** 不完整集合（未封口、数量对不上、有被拒绝的投射体）是设计预期；
  空集合也这样是 pass 现有的行为（它不为零个投射体渲染阴影图，接收照常用上一张）。游戏里不会出现“一帧没有任何投射体”，
  但阶段 5.1 的生产端如果某一帧一条投射体都发不出来，玩家看到的是上一帧的阴影而不是没有阴影。
- **太阳动过之后，同一个太阳方向的画面与最初不同**（11 个像素，最大通道差 35）。原因在 `d3d9_war3_csm.cpp`：
  级联的光空间基底沿用上一帧的 right 向量（为了跨帧连续），所以基底的滚转取决于太阳走过的路径。是确定的：三次独立运行与五组门禁哈希全部相同。
- **平地作为地形投射体不投出可见阴影**，但确实被画进了四个级联（账目里多 4 次）。

## 4. 校验层第一次覆盖阴影 pass

进程内的命令流没有校验层覆盖（4a 起就写明的缺口）。pass 进宿主后第一次在校验层下运行，开发版宿主的一次会话报了：

| 次数 | 规则 | 原因 | 进程内录的是同样的命令吗 | 修法 |
|---|---|---|---|---|
| 224 | `VUID-vkCmdDrawIndexed-None-08608` | 画投射体时绑定顶点缓冲又传了一遍步长，而内建管线的步长是静态的 | 是，每个投射体每个级联一次 | 步长传 `nullptr`。管线键的步长本来就取自这次 draw，值不变 |
| 3 | `VUID-VkGraphicsPipelineCreateInfo-Input-07904` | 投射体顶点着色器声明了四个输入，没有混合数据和 UV 的投射体只提供位置，另外三个没有来源 | 是，所有静态投射体的管线 | 没有来源的输入别名到位置属性（永远在缓冲内；这些输入在该模式下不被读取） |
| 23 | `SYNC-HAZARD-READ-AFTER-WRITE` | 颜色拷贝后恢复目标布局的屏障只开了写访问，接下来的接收以 LOAD 开始渲染，要读 | 是，每次接收一次 | 屏障的目标访问加上附件读 |
| 23 | `VUID-vkCmdBeginRendering-pRenderingInfo-09592` | 接收写死颜色附件布局；宿主的目标保持在 `GENERAL` | 命令相同，但进程内的目标本来就在附件布局，不违规 | 用 `queryLayout` 读：是 `GENERAL` 就用 `GENERAL`，否则同原来 |

“进程内录的是同样的命令”是从代码得出的：这几处在两端共用的源文件里，没有按模式分支；进程内没有校验层，所以没有它自己的报错记录。

改动共五处，在 `d3d9_war3_shadow.cpp`（四处）和 `d3d9_war3_shadow_resources.cpp`（一处）。验证：

- 修后带校验层的宿主会话 0 错误 0 警告（开发运行 1 次，正式门 3 个会话）。
- 修前与修后，进程内 14 帧的哈希逐个相同（修前的运行里还没有 `sun-back` 帧）；两模式仍然逐字节相同。

前三类按上面的推断是玩家现在跑的 pass 里一直有的规范违规，没被发现是因为进程内没有校验层。
它们在玩家的驱动上有没有可见后果，这次没有验证；夹具上修前修后画面相同。
**同样的写法在这次没跑到的路径上还留着**（点光阴影、投射体遮罩、描边），位置列在设计文档 §7，等那些路径进了对照门再改。

## 6. 分账

阴影对照门的数字（64×64 目标、1024 纹素级联、三个箱子；机器上有别的任务，时间只在同一轮内比较）：

| 组 | x86 私有内存：世界 | 开阴影后增量 | 帧时间：世界 → 阴影（微秒，中位数） |
|---|---|---|---|
| 进程内 | 287.1 MiB | +2.9 MiB | 359 → 480 |
| 代理，直连（校验层） | 2.4 MiB | 0 | 3587 → 6350 |
| 代理，流（校验层） | 2.4 MiB | 0 | 1711 → 2221 |
| 代理，流 + 命令环（校验层） | 2.4 MiB | 0 | 1240 → 2072 |
| 代理，流（无校验层） | 2.4 MiB | 0 | 1743 → 1906 |

- 宿主里一次 BeforeUi（阴影加当帧的特效）平均 391 微秒（无校验层那组，含第一次运行时建管线和阴影图）。
- 代理模式的帧时间里大头是每帧一次回读的同步往返，不是阴影：无校验层那组开阴影只多 163 微秒。这些是数字，不是门槛。
- **宿主一侧阴影占多少内存没有计数。** 4a/4b 的 `resourceBytes` 只统计特效执行器；阴影图（四个 1024² 的 D32 级联）、颜色与深度拷贝在 pass 自己手里。
  要对“x86 省下的内存去了哪、宿主涨了多少”给出完整的账，需要给 pass 加一个资源字节数的出口，归 4c-3。

## 7. 没覆盖的与要知道的

- **没有在游戏里跑。** §4 的五处改动在玩家正在用的阴影 pass 里。依据是：进程内 14 帧修前修后逐字节相同，且每处改动按构造不改变录下的命令。
  出 1.22.x 补丁前与 4a、4b、阶段 3 的改动一起做实机回归。
- **生产端是夹具。** 记录的值由夹具手写。游戏里 9.7k 行的投射体采集还没有改成发记录（阶段 5.1），
  所以“游戏里的投射体经记录重建后与原来一致”这件事还没有任何证据。
- **进程内臂不读 `ShadowFrame` 里的四个数据层事实。** 游戏时刻、墓碑序号、策略版本、关闭的模块，进程内的 pass 读的是 x86 自己的全局量；
  夹具里这四个值是常量（光照时钟固定，所以时刻也不起作用），两模式一致不能说明它们被正确传递。归 4c-3。
- **生命周期只有机制，没有测试。** 宿主每次运行前按纪元调 `InvalidateMapEpoch`，`SessionReset` 与 `Reset` 会推进纪元；
  但对照门里没有一帧跨过地图切换或设备重置。归 4c-3。
- **只覆盖了太阳级联和接收。** 点光阴影、alpha 测试、蒙皮、时间滤波、体积光用的太阳阴影图、描边的代码都编进了宿主，但没有一帧跑到它们，
  也就没有被校验层检查过（§4 末）。
- **夹具的投射体只有一种形状**：16 位索引、步长 16 字节、位置在偏移 0、静态缓冲。宿主的开发档位本来也只有 16 位索引和流 0。
- **宿主里的诊断是空的。** 性能区间、帧证据、诊断中心在宿主里全部空操作；游戏内的阴影诊断面板在代理模式下看不到宿主里的 pass。阶段 5 接线时决定怎么带回。
- **帧时间在共享机器上不稳**，只能同一轮内比较。
