## 1. 结论

- **四种“生命周期结束”在两种模式下结果相同**：投射体被永久移除（墓碑序号）、阶段策略改变（策略版本）、
  地图切换（`SessionReset`，连续四次，其中一次是游戏退出）、设备重置（`Reset`）。每一种之后，旧阴影图都不再被画出来，
  下一个完整的投射体集合画出的阴影与事件之前相同。对照门 32 帧在进程内与四个代理变体下 0 像素差异。
- **四个帧事实在进程内臂也经记录走了，并且各有一帧证明它起作用**：墓碑序号、策略版本、游戏时刻、关闭的模块。
  两种模式下 pass 每一次运行读到的事实逐项相同（42 次运行 × 17 个字段，五组相等；模块关闭的一对是 43 次）。
- **修了 4c-1 宿主的一个错**：没有 `ShadowFrame` 记录的帧，宿主把四个事实退回默认值。4c-1 的夹具里事实恰好等于默认值，
  所以没露出来。用 4c-1 的宿主跑新夹具，在没有 `ShadowFrame` 的帧上丢了阴影图，夹具失败（§4）。
- **宿主一侧有了内存账，并且不随地图和设备增长。** pass 自己拥有的图和缓冲是 21,009,664 字节（20.0 MiB），
  两种模式相同，从第一次运行到最后一次不变。宿主设备分配器的已用字节在四次地图切换、一次设备重置和其后的 12 帧里
  一个字节都没有变（流模式 35,032,320，直连 30,846,464）。
- **x86 内存**：代理模式下 x86 私有内存在世界、阴影、生命周期、计时四个采样点都是 2.4 MiB，增量 0。
- **原有路径没有变。** 特效门 77 帧的 231 个帧字段、GPU 参照门的 48 个像素哈希都与 4c-1 逐个相同；
  三道门共 45 个带校验层的宿主会话 0 错误 0 警告。正向切口仍是 19 个符号、24 条边。
- **线上格式没有变。** 三种记录的布局、编号、大小都与 4c-1 相同。
- **没有在游戏里跑**；生产端仍是夹具；“模块打开且请求时间滤波”那一帧归 4c-2（§7）。

## 3. 对照的帧

4c-1 的 15 帧不变，后面接生命周期段。记录里的事实：墓碑序号从 `tombstone-held` 起是 1，策略版本从 `policy-held` 起是 2，
时刻除两个时刻帧外都是 12。“空”指已封口的空集合，“全”指三个箱子。

| 帧 | 发了什么 | 结果（两模式相同） |
|---|---|---|
| `tombstone-held` | 墓碑序号 0 → 1，空 | 等于 `world`：pass 渲染了一张空阴影图，旧图没有再出现 |
| `tombstone-fresh` | 全 | 等于 `shadow-return`（事件之前的阴影） |
| `facts-kept` | 全，**没有 `ShadowFrame`** | 等于 `tombstone-fresh`；集合不封口，不发布新图；pass 读到的序号仍是 1 |
| `policy-held` | 策略版本 1 → 2，空 | 等于 `world` |
| `policy-fresh` | 全 | 等于 `shadow-return` |
| `time-9` | 光照时钟跟随游戏时间，时刻 9 | 与另外两个时刻的画面都不同 |
| `clock-held` | 固定时钟 | 隔开两个时刻帧（见下） |
| `time-15` | 跟随游戏时间，时刻 15 | 与 `time-9`、`time-return` 都不同 |
| `time-return` | 固定时钟，全 | 生命周期后半段的基准画面 |
| `session-pending` | 已请求地图切换，还没 `Present`；空 | 等于 `time-return`：会话还没结束，旧图照用 |
| `session-held` | `Present` 之后，空 | 等于 `world` |
| `session-fresh` | 全 | 等于 `time-return` |
| `map-2`、`map-3`、`map-4` | 每帧之前一次地图切换加 `Present`（第四次的原因是游戏退出），全 | 都等于 `time-return` |
| `reset-held` | 设备 `Reset` 加 `Present` 之后，空 | 等于 `world` |
| `reset-fresh` | 全 | 等于 `time-return` |
| `taa-requested`（只在模块关闭的一对里） | 设置里请求阴影时间滤波，全 | 等于 `reset-fresh`；pass 报告 `taaModule` 0、`taaMode` 0 |

之后仍是 12 帧无阴影、12 帧有阴影的计时帧。拒绝的请求从 12 条变成 16 条：多出的四条是畸形的会话重置
（原因 0、原因 3、代数 0、重复的代数），两种模式都拒绝。

这次跑出来才确定的 pass 行为，已钉进门禁：

- **生命周期结束后的空集合渲染一张空图。** 4c-1 记下的“空集合不发布新图、画面停在上一张”只在同一段生命周期内成立。
  墓碑、策略、地图、设备任何一个变了之后，pass 手里没有可留的图，空集合也会渲染（账目里 `mapExecuted` 1、投射体 0），
  画面是没有阴影的世界。所以旧地图的阴影不会因为新地图第一帧没有投射体而留在屏幕上。
- **序号和版本只比较“变没变”。** x86 上两者只增不减，地图切换也不归零；宿主照此不在 `SessionReset` 时清它们。
- **地图切换在 `Present` 处生效，不在请求处。** 两种模式一致（`session-pending`）。
- **光空间基底的连续性不随地图或设备清掉。** 新地图第一帧的画面等于同一个太阳下旧地图最后的画面（`time-return`），
  不等于进程第一帧（`shadow`）。4c-1 记过“太阳动过之后同方向的画面与最初差 11 个像素”，这个差别跨地图保持。
- **跟随游戏时间的时钟只有第一帧是确定的。** pass 从第二个连续的“跟随游戏时间”帧起按墙上时钟平滑时刻，
  所以两个时刻帧之间隔了一帧固定时钟。时刻本身确实到了 pass：账目里三帧读到的是 9.0、12.0、15.0。
- **模块开关不请求就不起作用。** 模块打开与关闭的两个进程内参照，32 个共同的帧逐字节相同。

### 两种模式都要 `Present`

进程内的地图切换和设备重置都是在 `Present` 里应用的。实测：不 `Present`，地图切换请求永远不生效；
设备 `Reset` 之后不 `Present`，之后每一次运行都因设备纪元过期被拒绝。所以夹具现在真的调 `Present`
（进程内成功；代理的离屏档位返回 `E_NOTIMPL`，但 `SessionReset` 是在 `Present` 之前送出的，照样到达）。

这带出一个与阴影无关的现象：进程内渲染器第一次 `Present` 时在窗口上建 Vulkan 交换链，系统的 `opengl32.dll`
随后把窗口过程换成它自己的，叠在渲染器的钩子上面。渲染器销毁设备时只在“当前窗口过程是我的钩子”时才摘钩，
于是摘不掉，链条里留着指向渲染器的地址；之后卸载渲染器 DLL，窗口再收到消息就执行到已卸载的代码
（0xC0000005，落点是 `dxvk::D3D9WindowProc`）。游戏从不卸载渲染器，不受影响；夹具会卸载，所以在卸载前把窗口过程
恢复成窗口类自己的。门禁要求这个恢复只发生在进程内臂（代理不动窗口）。这是上游 DXVK 的通用行为，这次没有改渲染器。

## 4. 宿主的一个错

4c-1 的宿主在每次运行前这样取事实：有 `ShadowFrame` 就用记录的，没有就用默认值。x86 上这四个量是进程里的全局变量，
一帧没有人写它们，它们就保持原值。差别在没有 `ShadowFrame` 的帧上显出来：前一帧的记录说策略版本是 1，
这一帧 4c-1 的宿主把它退回默认的 0。pass 只看“变没变”，于是认为策略变了，丢掉阴影图；这一帧的集合又没封口，不渲染新图。
结果是画面变成没有阴影的世界，而约定是“停在上一张图”。

验证：新夹具配 4c-1 的宿主（`build64_render_host_phase4c_20261115_a`，开发运行，不是门禁回执）。
新夹具的记录带的是 x86 的初值（策略版本 1）。运行在 4c-1 就有的 `unsealed` 帧上失败：这一帧以及其后的 `short-count`、`dynamic`
都等于 `world`，夹具的断言报“新阴影图来自空的或不完整的集合”。修后三帧都等于 `one-caster`，通过。
4c-1 没有发现它，是因为当时夹具的记录里四个事实恰好等于宿主的默认值；这正是 4c-1 回执 §7 写的“被正确传递目前没有证据”。

改法两处：事实只在有记录时改写；默认值改成 x86 数据层的初值（原来策略版本的默认是 0，x86 是 1）。

## 6. 分账

阴影对照门的数字（64×64 目标、1024 纹素级联、三个箱子；机器上有别的任务，时间只在同一轮内比较）。

**宿主一侧**（代理模式；进程内臂的 pass 存储相同，设备内存不采）：

| 项 | 字节 | 说明 |
|---|---|---|
| pass 拥有的图和缓冲 | 21,009,664（20.0 MiB） | 每次运行后相同，7 组相同。约为四层 1024² 的 D32 级联 16.0 MiB、四层 1024² 的投射体遮罩 4.0 MiB，其余是 64×64 的颜色与深度拷贝和几个小缓冲 |

| 设备分配器已用，流模式 | 35,032,320（33.4 MiB） | 第一次阴影运行后 34,752,768；跑 SSAO 与 SMAA 的那一帧到 35,212,544；之后 30 次运行（31 次，模块关闭那组）全是 35,032,320 |
| 设备分配器已用，直连 | 30,846,464（29.4 MiB） | 同上，30 次运行不变 |

## 7. 没覆盖的与要知道的

- **没有在游戏里跑。** 这一段没有改 pass 的逻辑，但 4c-1 留下的五处改动仍然没有实机回归；出 1.22.x 补丁前与 4a、4b、阶段 3 的改动一起做。
- **生产端是夹具。** 游戏里谁在哪一帧调 `WarVKD3D9RequestSessionReset`、谁填 `ShadowFrame` 的四个事实，是阶段 5 的接线。
  进程内地图卸载同时还清对象注册表和蒙皮缓存，这些在宿主里有没有对应物届时要核对。
- **“模块打开且请求时间滤波”没有帧。** 那一帧跑的是时间滤波本身，归 4c-2；这次只有“模块关闭时请求不起作用”的一半。
- **模块开关用两个进程对照，不是帧内切换。** x86 的运行时配置在进程启动时读一次。宿主是逐帧读记录的。
- **进程内“事实到不了就拒绝”没有运行时的帧。** 序号或版本比数据层的小、一次要推进 64 步以上、要求的模块开关与进程不同，入口会拒绝；
  只有静态规则钉住它在运行之前判断。如果它错放了一帧，后果会在逐次运行的事实对比里显出来。
- **进程内臂为了推进墓碑序号，真的向数据层发布了一条墓碑**（一个合成的句柄）。夹具进程里没有别的消费者。
- **世界场景中间请求地图切换，两边处理不同**：进程内入口拒绝，代理接受并留到下一次 `Present`。夹具只在帧之间请求，没有对照这种情况。
- **代理一侧的 `Present` 是离屏档位的**（返回 `E_NOTIMPL`）。带真实呈现的宿主会话里跨地图、跨设备重置的阴影没有对照；GPU 参照门有呈现的帧，但不带阴影。
- **宿主进程自己的内存（CPU 一侧的私有字节）没有按地图采样。** 采的是显存一侧：pass 的存储和设备分配器。
- **存储只在 1024 纹素级联、64×64 目标下量过。** 玩家的级联分辨率和窗口大小不同，字节数随之变；出口本身与分辨率无关。
- **只覆盖了太阳级联和接收**，与 4c-1 相同。点光阴影、时间滤波的历史、体积光用的阴影图这些跨帧状态在生命周期帧上有没有清干净，
  要等它们进了对照门才知道；设计 §7 写了 4c-2 怎么挂上来。
- **`opengl32.dll` 叠窗口过程的现象**（§3）没有改渲染器，只在夹具里绕开。游戏不卸载渲染器，所以不是玩家问题；
  以后如果有“运行中卸载并重新加载渲染器”的需求，这里会崩。
- **帧时间在共享机器上不稳**，只能同一轮内比较。
