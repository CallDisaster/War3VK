# x64 代理线 P4：固定管线绘制记录的线格式（决定）

日期：2026-11-18。对应 `docs/plan/2026-11-17-x64-proxy-performance-plan.md` 第 10 节第 4 项。
选项与数据见 `2026-11-17-x64-state-delta.md` 第 5 节；本文只写决定和理由，供实现的人照做。

## 1. 决定

**做“消息内、按字位图的差量”，不做跨消息的持久基线。** 一步到位，不再单独做“只去掉恒零块”的中间格式：第一条记录对全零基线做差，恒零的 1,024 B 常量和空灯位自然就不发了。

具体格式（新 op `DrawFixedDeltaBatch`，追加在 `Op` 枚举末尾）：

- 一条消息里有 `count` 条记录，`count` 仍在 `args[0]`，上限仍是 20。
- 每条记录描述一份完整的 3,180 B 固定管线绘制记录（795 个 32 位字），写法是“相对基线哪些字变了”：
  1. 一个 32 位**块掩码**：795 个字按 32 个一块分成 25 块，第 i 位为 1 表示第 i 块里有字变了。高 7 位必须为 0。
  2. 对每个置位的块，按块号从小到大：一个 32 位**字掩码**（必须非零；最后一块只有 27 个字，高 5 位必须为 0），后面紧跟这一块里变了的字，按位号从小到大。
- 基线：消息里第一条记录的基线是 795 个零；之后每条的基线是同一条消息里前一条**还原出的完整记录**。
- 消息结束时字节数必须正好用完。

宿主的处理：把每条还原成完整的 3,180 B，然后调用**现有的** `DecodeFixedDraw`，之后的校验、资源解析、`prepareDraw`、绘制全部不变。前端的做法对称：先用现有的 `EncodeFixedDraw` 得到完整记录，再和批内上一条逐字比较后写出。

## 2. 为什么这样选

1. **没有跨消息状态。** 每条消息可以单独解码和重放；Reset、换图、宿主拒绝、设备丢失都不需要“两端同时作废基线”的纪律。持久基线一旦错位，会一直错到下次重置，而且错的是画面，不是崩溃，最难查。
2. **字节收益已经够。** 调研的估计是消息内差量能拿到持久方案约九成的字节。按批内平均 3.7–4.8 条算，每条绘制从 3,180 B 降到约 500 B。
3. **等价性最容易证明。** 宿主还原出的记录与 `EncodeFixedDraw` 的输出逐字节相同，后面仍是同一条解码与校验路径。不按语义分组，记录布局以后变了，差量格式不用跟着改。
4. **不把 setter 并进记录（这一版）。** Effects / Sampler / TextureStages 现在各有一个写入口，并进来就有两个。先看这一版之后的批长度，再决定要不要并。

11-18 凌晨的新数据也支持先做字节：四个 P2 开关都开之后，生与死每帧过环 8.6 MB，其中固定管线绘制 4.28 MB、缓冲上传 4.05 MB，4 MiB 的环装不下一帧，x86 每帧有 0.4 ms 在等环腾出空间；而且这张图上 x86 游戏线程已经是瓶颈（每帧自己要 17.5 ms），前端每条绘制少写、少拷贝几百个字是直接收益。P4 对 x86 内存没有影响，这一点不变。

## 3. 细则

- **协商**：`Initialize` 的 `args[6]` 加一位 `InitializeFixedDelta=4`。宿主不认识这一位就拒绝初始化，和现有两位的规则一样。前端开关 `WARVK_D3D9_FIXED_DELTA=1`（默认关，验证后进 `product` profile）；没开时仍发原来的 `DrawFixedBatch`。两个 op 宿主都要一直支持。
- **拒绝**：差量解不出来（未知掩码位、字掩码为零、字节数不对、还原后 `DecodeFixedDraw` 失败）时，整条消息不执行。同步模式下返回 `D3DERR_INVALIDCALL`，异步模式下按现有规则终止会话。和今天一条畸形的 `DrawFixedBatch` 的后果相同。
- **校验模式**：`WARVK_D3D9_FIXED_DELTA_VERIFY=1` 时，前端在每条记录后附完整记录的 64 位哈希，宿主还原后比对，不一致即终止（细节写 `delta-mismatch`）。门禁至少跑一轮这个模式。
- **批上限**：保持 20 条。先不放宽；实现时顺手统计每批条数的直方图，上限确实卡住了再改。
- **注解**：按批内绘制序号绑定的规则不变；新 op 与 `AnnotateDraws` 的先后关系和 `DrawFixedBatch` 相同。
- **计数**：前端从第一天起就记“完整字节”和“实际发出的字节”，写进现有的 `fixed-batch-proxy` 旁边的新一行。不再单独做调研里说的 P4a 测量模式。

## 4. 验收

沿用 `2026-11-17-x64-state-delta.md` 5d 节的不变量和测试，重点三条：

1. 每条绘制，宿主还原的记录与 `EncodeFixedDraw` 的输出逐字节相同（线格式测试用随机状态序列逐条比）。
2. 阴影门、特效门、GPU 参照门在开和关差量时帧哈希完全相同。
3. 畸形差量都被拒绝，且不影响之后的合法消息（因为没有持久基线，这一条天然成立，但要有测试）。

收益看字节和每条绘制的微秒，不看 fps。

## 5. 分工

格式到此为止已定。实现（前端编码、宿主还原、协商位、测试，约 2–3 天）可以由 Opus 做。宿主侧的复用（按块跳过解码与校验、键缓存）是另一批，做之前先由 Fable 审失效点清单。

## 6. 实现与验证（11-18 后半夜）

实现由 Codex（Astra 6.2，xhigh）按本文完成，Fable 读过差异、自己构建并跑了下面的测试。没有偏离格式；有一处容量上的处理要说明。

**实现**

- 新文件 `tools/render_host/d3d9_ff_delta_wire.h`（编码、宿主侧整批还原与校验）；`d3d9_wire.h`（操作 44、协商位、共用的 64 位 FNV-1a）；`d3d9_connection.h`（开关、协商、暂存与冲刷、账目）；`dxvk_core/d3d9_host_main.cpp`（协商检查、整批验证后才执行、账目）。
- **容量**：协议的 `MaxPayload` 是 65,408 B；20 条记录全字变化时差量需要 65,680 B（带哈希 65,840 B），比完整记录还大。做法是保留 20 条上限，前端在放入每条记录之前先确认还装得下一条最坏情况的记录，装不下就先发出已有的批、从零基线另起一批（最坏情况拆成 19 + 1）。
- x86 常驻：每个 `Connection` 多 5,952 B（661,056 → 667,008；暂存区扩到 `MaxPayload`、批内基线 3,180 B、计数）。没有按绘制的堆分配，没有跨消息的历史。
- 两个账目行：前端 `D3D9 fixed-delta-proxy`（消息数、记录数、`fullBytes`、`sentBytes`、按批长的直方图），宿主 `D3D9 fixed-delta-host`（消息数、记录数、`restoredBytes`、`rejected`、`verified`）。

**测试**

- 线格式测试（i686 与 x86_64）：各 1,458,854 项，0 失败（固定种子序列、批长 1–20、全同、全异、末块、灯增减、畸形尾记录、拒绝后恢复、注解绑定）。
- `Connection` 的 CPU 夹具 `test_d3d9_connection_fixed_delta_cpu.cpp`：6 个组合（开关 × 同步/异步；2 条可编程 → 23 条固定 → 1 条可编程，中途 Reset，注解序号），两种位宽都过。
- 冻结轮 f6 的差量组（P2 四个开关 + 固定批 + 差量 + 逐条校验）：阴影门（370 条记录）、特效门（295 条）、GPU 参照门（7 个固定批用例，1,578 条）全部通过，`verified` = 记录数，`rejected` = 0；帧哈希与 5.2 冻结轮逐项相同（352 / 77 / 52 项）。GPU 参照门钉死了哪些臂开固定批，所以给它加了 `--fixed-env`：只对本来就开固定批的臂加差量开关。
- 游戏实跑（同一会话，`product-async` 对 `product-async` + 差量，f4 x86）：

| | Lost Temple | 生与死 |
|---|---|---|
| 每帧环流量 | 1,435 KB → 624 KB（−56%） | 8,680 KB → 4,911 KB（−43%） |
| 其中固定批 | 887 KB → 76 KB | 4,275 KB → 505 KB |
| `sentBytes / fullBytes` | 7.6% | 8.7% |
| 世界帧率 | 198.5 → 210.4 | 55.8、54.8 → 54.9、54.0（持平） |
| 环满等待 | 0 → 0 | 每帧 4.5 μs → 0 |
| 校验模式（另一次运行） | 3,223,674 条全部相符 | 7,563,948 条全部相符 |

- 两端账目相等：前端记录数 = 宿主记录数，`fullBytes` = `restoredBytes`，`rejected` = 0，没有 `delta-mismatch`。
- 校验模式要对每条完整记录求哈希，帧率掉到 179 / 41.9，只用于诊断。

**读法**

- 收益是字节，不是帧率：生与死上传输已经不是瓶颈（前端阻塞占比 0，宿主有约 20% 空闲），所以帧率不动。
- Lost Temple 上 57% 的消息只有一条记录（平均每条消息 3.75 条），批内基线能省的主要是“同一批里相邻两条相同的那部分”；跨消息的持久基线能再省，但那正是本文第 2 节排除掉的做法。
- 每条记录实际发出约 240–280 B（第 2 节估的是约 500 B）。批长直方图里，到 20 条上限的消息在 Lost Temple 上占 9%；上限偶尔卡住，但放宽它要先加大 `MaxPayload`，这一版不动。
- 差量之后剩下的环流量主要是 `UploadBuffer`（生与死每帧 2,345 次、4.06 MB；Lost Temple 404 次、0.44 MB）。要再降，下一个对象是动态顶点缓冲的上传，不是绘制状态。
- 探针档位 `product-async-delta` = `product-async` + `WARVK_D3D9_FIXED_DELTA=1`。

## 7. 编码器在 x86 上的开销（11-18 清晨）

上表里“生与死持平”是各两次运行的结果，差 1.5%。清晨在同一次占锁里交替跑了三对，差量比 `product-async` 慢 5.8%（45.3 / 46.8 / 45.1 对 48.6 / 48.1 / 48.9 fps），而且慢在 x86 游戏线程自己：每帧 21.9 ms 对 20.6 ms，前端没有阻塞。生与死每帧 1,325 条固定管线绘制，折合每条 0.96 μs。

单独的基准（`AutoTest/bench_render_host_fixed_delta.cpp`，i686，前端的编译选项，记录内容是合成的，疏密按游戏里每条约 270 B 配）：

| 每条记录在“生成记录”之外多花的时间 | 较疏 | 较密 |
|---|---|---|
| 整条记录的路径（拷进批，再拷进环） | 0.10 μs | 0.09 μs |
| 第 6 节的编码器 | 0.98 μs | 1.11 μs |
| 现在的编码器 | 0.26 μs | 0.31 μs |

第 6 节的编码器对每个字做一次比较和一次依赖数据的分支；一条记录里脏字和干净字交错，分支预测不中。现在的写法先求出一个块（32 个字）的脏字位图，有 SSE2 时一次比 4 个字，尾部按字比，没有依赖数据的分支；再只访问置位的字。格式和输出字节都没有变，宿主一行没改。

- 等价性：与第 6 节的编码器逐字节比对 506,672 条记录（四种疏密，校验开和关），全部相同。线格式测试加了一段与朴素写法的逐字节比对（每个字位置单独置位和清零、随机的疏密变化、四种输出对齐），共 1,464,444 项，两种位宽 0 失败。把编码器故意改坏两种方式（每组第一个字永远不算脏；尾部少比一个字），这段检查分别报 9,015 项和 4,544 项失败。
- 修后同样的交替探针（冻结 f7 宿主）：`product-async` 49.3 / 49.3 / 48.4 fps，差量 46.9 / 48.8 / 48.8；x86 每帧 20.4 ms 对 20.5 ms（46.9 那次是负载）。
- 冻结轮 f7（这个头文件是宿主构建的输入）：三个门 × 四组十二次全过，差量组仍然逐条校验；帧哈希与 5.2 冻结轮逐项相同。
- 静态测试没有新增失败（读到相关文件的 8 个模块、103 条，失败的是已知五个里的两个；294 个静态脚本只有已知的一个失败）。
- 比整条记录的路径还多的那部分（每条约 0.16 μs，生与死每帧约 0.2 ms）没有再拆开量。两处可能的来源：每条记录都要把 795 个字扫一遍；每条消息的首条记录对全零基线，要把所有非零字写出来，而 58% 的消息只有一条记录。收益已经在游戏测量的噪声以内，这一版不做。
