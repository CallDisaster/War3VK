# x64 迁移阶段 5.1-a 回执：真实游戏第一次跑在 x64 宿主上

2026-11-16，Claude（Fable 5.2）。对应[整体路线](../plan/2026-11-13-x64-migration-roadmap.md)阶段 5 第 1 项的第一段。
后面四段（5.1-b 到 5.1-e）的形状与验收条件在[5.1 设计](../plan/2026-11-16-x64-phase5-1-first-wiring.md)里。
全部改动未提交；没有碰玩家目录（`E:/Work/Warcraft III/d3d9.dll` 仍不存在，每一轮探针都核对它“不存在且保持不存在”）。
这一段**没有改玩家在用的代码**：`src/d3d9` 一个文件都没动，改的都在 `tools/render_host`（开发代理与宿主）和 `AutoTest`。

## 1. 结论

- **沙盒里的真实游戏已经完全由 x64 宿主渲染。** War3 1.27 把开发代理当作 `d3d9.dll` 加载，x86 进程里没有
  `vulkan-1.dll`，也没有任何显卡驱动模块；画面由宿主画到游戏自己的窗口。Lost Temple、stormtide、(2)EchoIsles、
  “生与死”四张图都进了图。
- **游戏没有用到代理没实现的东西。** 193 个未实现的 D3D9 入口都加了首次调用跟踪，所有轮次里一次都没有响；
  没有一次 `Present` 失败（宿主崩溃实验除外）。
- **会话干净。** 每一轮发布的消息全部被宿主应用（单轮最多 312 万条），退出时资源计数归零、宿主正常返回、游戏进程返回 0。
- **x86 内存（无数据层，产品内存配置）**：Lost Temple 100 MiB 专用字节，stormtide 75，EchoIsles 88，生与死 527；
  低 2 GiB 可用地址空间分别是 1633、1663、1648、1102 MiB。这是下限，不是产品数字（§6）。
- **生命周期在传输层是通的**：两次窗口缩放、最小化与恢复、激活切换、暂停键之后会话仍然干净；
  宿主被终止时代理立即察觉，游戏不崩不挂，仍能正常退出。
- **这还是“原版画面”。** 没有数据层，所以没有阴影、天气、后处理、控制面；缩放后画面布局不对（数据层的活）；
  换图没有跑。这些是 5.1-b 到 5.1-e。
- **原有路径没有变**：见 §5。

## 2. 做了什么

| 部件 | 文件 | 说明 |
|---|---|---|
| 资源表 | `tools/render_host/d3d9_resource_registry.h` | 上限 64 → 16384；`reserve()` 从最低空闲提示开始找，仍返回最低空闲 id |
| 宿主槽位 | `dxvk_core/d3d9_backend.h`、`d3d9_host_main.cpp` | 纹理槽随资源表放大；槽位查找一遍完成（原来是平方） |
| 游戏配置 | `d3d9_window_identity.h`、`d3d9_connection.h`、`d3d9_proxy.cpp` | `WARVK_D3D9_GAME=sandbox-isolated-v1` 加非输入桌面才允许进有 Game.dll 的进程；不设时拒绝照旧。游戏配置下允许在窗口线程上建设备、接受 `LOCKABLE_BACKBUFFER` 标志 |
| 父进程身份 | `win32_transport.{h,cpp}`、`owned_child.{h,cpp}`、`d3d9_connection.h`、`d3d9_host_main.cpp` | 父进程把只带两项权限的自身句柄交给宿主继承，宿主核对 PID 与创建时间后收下；旧的按 PID 打开保留给直接起宿主的夹具 |
| 宿主日志 | `d3d9_connection.h`、`d3d9_host_main.cpp` | 游戏进程里每条连接取下一个不存在的 `<log>.<n>`；传输失败打印故障、阶段、Win32 错误码 |
| 首次接线跟踪 | `d3d9_unsupported.h`、`d3d9_proxy.cpp` | 游戏配置下：`Direct3DCreate9` 与 `CreateDevice` 的参数、每个未实现入口的首次调用、第一次失败的 `Present`、按帧数转储后备缓冲（Target 回读） |
| 探针 | `AutoTest/run_x64_game_proxy_probe.py` | 新建沙盒实例、隔离桌面、受限令牌；内存与地址空间采样；对游戏自己窗口的定时动作（缩放、最小化、激活、按键、点击、终止自己的宿主）；回执 |
| 测试 | `AutoTest/test_render_host_d3d9_resource_registry.cpp`、`test_render_host_d3d9_wire.cpp` | 写死的 64 / 65 换成 `MaxResources`；大表放堆上 |

## 6. 内存

探针每 2 秒采一次游戏进程的专用字节与工作集，关闭前采一次低 2 GiB 地址空间。

| 图 | 传输配置 | x86 专用字节（稳态 / 峰值） | 可用地址空间 | 最大空洞 |
|---|---|---|---|---|
| Lost Temple | 流式 + 命令环（x86 留完整副本） | 149 / 153 MiB | 1568 MiB | 1007 MiB |
| Lost Temple | 产品内存配置 | 100 / 100 MiB | 1633 MiB | 1007 MiB |
| stormtide | 产品内存配置 | 75 / 75 MiB | 1663 MiB | 1007 MiB |
| (2)EchoIsles | 产品内存配置 | 88 / 93 MiB | 1648 MiB | 1007 MiB |
| 生与死 | 产品内存配置 | 527 / 532 MiB | 1102 MiB | 659 MiB |

- “产品内存配置”是阶段 1 定下的 32 MiB 回读预算加 1 MiB 上传窗口。Lost Temple 上它比留完整副本少 49 MiB。
- 生与死的 527 MiB 是游戏自己为这张图分配的。同一时刻宿主留着 350 MiB 的纹理与缓冲内容（峰值 367,140,616 字节）；
  在“x86 留完整副本”的配置下，这些内容是留在 x86 里的。
- 没有量的：宿主进程自己的内存；进程内模式在同一张图、同一时刻的数字（同图 A/B 是 5.2 的门）。
  所以这里不给“省了多少”的数字。

## 7. 没覆盖的与要知道的

- **帧率没有结论。** 帧转储间隔算出来的帧率在 15–60 之间跳。本机同时有别的重负载；原版游戏在窗口不活动时自己降速
  （隔离桌面上窗口永远不活动），进程内模式是数据层的钩子把它关掉的。命令环统计里每帧约 90 条同步记录，
  是 5.2 帧时间门要先看的地方。
- **真实的 Alt+Tab 没有跑。** 隔离桌面上没有前台切换；跑的是对窗口发 `WM_ACTIVATEAPP`。
- **换图没有跑。** 裸代理没有控制面；退出时全部资源的释放是跑了的（计数归零）。归 5.1-c。
- **生与死的世界画面没有看到。** 开局是黑色迷雾；要等 5.1-b 有控制面后开全图再看。
- **声音设备。** 隔离桌面的受限令牌下游戏报“不能初始化声音设备”，与代理无关；现有实机门也是这个环境。
- **三个 Direct3D9 对象各起一个宿主**，启动因此多约 1.5 秒。产品 DLL 常驻后可以合成一个（设计 §4）。
- **只接受窗口化。** 探针一律带 `-window`；全屏请求现在会被代理拒绝（设计 §7）。
- **锁后备缓冲没有实现**（游戏的截图键）；标志已接受，这几轮里游戏没有去锁。
- **探针不是门。** 它不比较画面，`ok` 只表示设备建成、有非空画面、会话干净、进程自己退出、被保护的文件没有变。
  画面正确是看帧转储得出的。
