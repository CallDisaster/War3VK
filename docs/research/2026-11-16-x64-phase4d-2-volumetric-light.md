## 1. 结论

- **体积光的 froxel 与光线步进两条路径在两种模式下结果相同。** 对照门 45 帧（模块关闭的一对 46 帧）在进程内与四个代理变体下
  0 像素差异，阴影 pass 与体积光 pass 每一次运行的自述逐项相同（§5）。
- **体积光 pass 原样进宿主。** 量过链接面（对 4d-1 的 x86 构建）：它直接引用 5 个目标文件里的 16 个符号，来自 `d3d9_device.cpp` 的是 0 个。
  其中 4 个宿主已经有了（阴影 pass 自己的 `_resources`、混合光追判定、雾体积，以及由服务文件提供的性能监视器），
  只新编一个闭包为零的辅助文件（着色器工作量准入）；宿主服务文件只补了性能监视器的两个空操作。不改写。
- **校验层报了 1 条规则 4 次**（每个体积光帧一次）：合成时把帧的颜色目标写死成附件布局，宿主的目标是 `GENERAL`。
  照 4c-1 改成按 `queryLayout` 选，带校验层的宿主会话 0 错误；改前改后四个臂的帧哈希逐个相同（§4）。
- **新的跨帧状态过了生命周期帧。** 第一个体积光帧阴影 pass 建体积光专用的太阳阴影图（512² × 2 层，2 MiB），
  体积光 pass 建它自己的图和缓冲（froxel 292,864 字节，光线步进 290,816）；之后经墓碑、策略、四次地图切换和一次设备重置
  不再变，宿主设备分配器的已用字节从 `shadow-return` 起 30 次运行同一个值（§6）。
- **原有路径没有变。** 与 4d-1 共有的 41/42 帧在 7 组里哈希逐个相同；特效门 77 帧、GPU 参照门 48 个哈希与 4d-1 逐个相同；
  正向切口不增（§5）。
- **线上格式只加不改**：新记录 15（`VolumetricLight`，164 字节）；已有记录的布局、编号、大小不变。
- **x86 内存**：代理模式下 x86 私有内存在各采样点都是 2.4 MiB，增量 0；体积光的图、缓冲与管线都在宿主里（§6）。

## 3. 对照的帧

4d-1 的 41 帧不变，在 `outline-geometry` 之后插入 4 帧。“全”指三个箱子，记录都只开 `enabled` 并把 `volumeSunResolution` 设为 512，其余默认。

| 帧 | 发了什么 | 结果（两模式相同） |
|---|---|---|
| `volumetric` | 全，外加一条 `VolumetricLight` 记录，`quality` 2（froxel 高） | 与 `sun-back` 不同。体积光 pass 报告后端 2、已合成；阴影 pass 建体积光的太阳阴影图，体积光 pass 建 froxel 资源（§6） |
| `volumetric-again` | 同一帧再来一次 | 与 `volumetric` 相同；后端 2、已合成 |
| `volumetric-march` | 同上，`quality` 0（光线步进） | 与 `volumetric` 不同；后端 0、已合成 |
| `volumetric-lamp` | 同 `volumetric`，外加 `point-light` 帧的那盏点光（同一条 `PointLights` 记录与同一份 `Lighting`，点光不投影） | 与 `volumetric`、`point-light` 都不同：点光照亮了空气。阴影 pass 的账目与 `point-light` 帧相同（`pointShadow` 1：设置里点光阴影开着） |

四帧之后的帧没有 `VolumetricLight` 记录，体积光关闭、阴影 pass 不再渲染它的太阳阴影图，所以与 4d-1 的画面相同。

这次跑出来才确定、已钉进门禁的行为：

- **`volumetric-again` 与 `volumetric` 画面相同。** froxel 的历史混合在两帧之间确实发生了（帧序号连续，两端都是
  “已执行的 BeforeUi 次数 + 1”），但同一个场之间混合不改变结果。所以这一帧证明的是“重复稳定”，不是“用了历史”；
  门里的事实叫 `volumetricRepeats`。历史在两端是否走同一条曲线，要等一组“场在变”的连续帧才能看出来，本段没有。
- **体积光 pass 的存储随路径变。** 四次运行依次是 292,864、292,864、290,816、292,864 字节：froxel 帧一个值，光线步进帧少 2,048 字节，
  回到 froxel 又是原值。这个夹具的目标只有 64×64，所以 froxel 的图本身很小；差的是哪几样没有逐项拆。
  对照门只要求“只在跑过的运行里非 0、两模式相同”，不钉每帧的值。

## 7. 没覆盖的与要知道的

- **没有在游戏里跑。** §4 改的是玩家在用的体积光合成与构造；与 4a、4b、4c、4d-1、阶段 3 的改动一起，出补丁前统一做实机回归。
- **生产端是夹具。** 游戏里谁发 `VolumetricLight`（数据层的体积光设置，每帧一条）是阶段 5.1 的事。记录的含义是“这一帧跑体积光”：
  游戏里体积光还受“后处理”模块开关（`War3RuntimeModule::PostFx`，进程内注册 pass 时读）与 `postFx.enabled` 管，这两者不在记录里，
  生产端在它们关掉时不发记录。进程内模块关闭时阴影 pass 仍可能渲染体积光的太阳阴影图（它只看设置），x64 不会；画面不受影响。
- **天气介质与雾体积没有进来。** 体积光 pass 还有两种介质：天气的雾与低空雪（读 `input.weather`，进程内来自天气运行时的快照）、
  地图放的雾体积（读数据层的雾体积管理器）。两种模式下它们都不活动；记录与帧归 4d-3。
- **点光接触阴影已经在宿主里但没有对照帧。** 它是阴影 pass 的一部分（`Lighting` 里的 `pointRayShadow*`，默认关闭，
  打开时走混合光追的 HiZ 计算 pass），记录早已带着这些字段；4d-3 给它加一帧。
- **只覆盖了默认设置附近。** 高度雾、自适应采样数关闭、体积光的太阳阴影图回退到级联阴影、双级联关闭、中低两档 froxel 质量，
  都只有布局测试，没有对照帧。
- **froxel 历史没有“场在变”的连续帧**（§3）：只证明了重复稳定。
- **帧时间在共享机器上不稳**，只能同一轮内比较。
