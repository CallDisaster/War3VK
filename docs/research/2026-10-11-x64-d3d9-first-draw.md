# x86 D3D9 → x64 现有 DXVK：第一条真实绘制链

日期：2026-10-11。开发 checkpoint，**不是游戏可用 DLL、正式发布或内存收益证明**。
执行依据：[已批准的 D3D9 迁移边界](../plan/2026-10-11-x64-d3d9-migration-boundary.md)。
工作树为 `codex/v1.22-main-tree-20260920`，HEAD `a2054a9776e40edc3f01f6f390c06037965b8ef2`
加原有 dirty 与本批改动；不能用 HEAD 或整树 diff 代替本批源码身份。

## 这次确实搬了什么

独立 32 位程序加载真正导出 `Direct3DCreate9` 的开发 COM DLL，调用资源创建、Lock/Unlock、
shader/声明/常量/状态、`DrawIndexedPrimitive`、EVENT query 和读回；按值命令经过有界队列及
专属 I/O owner，到 64 位进程使用**本项目原 DXSO、DXVK allocator/Context/submission/retirement**执行。
32 位测试进程没有加载 Vulkan。它已经不是“两个独立 demo 各画各的”，也没有借用 RH2 的小型 Vulkan renderer。

32 位仍保留符合公开 API 地址寿命的 buffer/texture backing、原 shader token 与 COM 状态。
CPU ACK、实际 GPU timeline 完成、DXVK resource-use 退休分别统计；未把上传 ACK 当作释放许可。
当前每次 RPC 同步，是**受外部 watchdog 保护的实验基线**，不是产品异步服务或热路径性能方案。

## 本批相关代码边界

- `src/dxso/dxso_options.*` 不再依赖整个 x86 `D3D9DeviceEx`，改为显式接收 device、options 与实际 VS 常量布局大小。
  原 shipping caller 同步调整；默认 options 的字段显式初始化。
- `d3d9_fixed_function.cpp` 中十个公共 SPIR-V helper 的连续函数体移到 `d3d9_shader_helpers.cpp`，
  编入唯一 `dxso_lib`，shipping 与宿主共用，不复制一份实现。抽取正文按统一换行 SHA-256 为
  `DF4B9CF37DC651206066B48376F155E21B0E58C22D1153E219BB30584AFF95B9`，与抽取前正文相同。
- `tools/render_host/d3d9_proxy.*` 是明确受限的开发代理。公开 COM 引用保活 device，device 内部绑定使用
  private reference；资源 ID 在连接内不复用，不传进程地址、C++ lambda 或 ABI 结构体。
- `d3d9_wire.h`/`d3d9_draw_wire.h` 明确定义小端字段与 1,140 B draw-state 载荷；原始 SM3 token
  经两端有界 scanner 检查，再交给实际 DXSO。
- `dxvk_core/d3d9_backend.*` 接受这一小份能力集合；它没有移植完整 D3D9 兼容层。后续扩大支持时应继续
  收敛共享语义，而不是把实验翻译层长期发展成与 shipping 并行的第二套规则。

## 实际发现并修正的问题

### 1. 命令完成了，几何却没有画出来

初次真实测试 r2 中，3 个 draw/query/readback 均返回，但 960 个不透明点和 196 个混合点全部只得到清屏色：
`pixelFailures=1156`。该失败保留在 `AutoTest/artifacts/x64-d3d9-20261011-r2`，没有删掉或追认。

原因：宿主使用公开的 `endRecording → submitCommandList`，而 descriptor-buffer 的未满批次发布和 CPU
同步点只在 `flushCommandList` 路径设置。`getSyncHandle()` 实际还会发布未满的 descriptor-copy block；
小场景不足以自动填满，GPU 因而可能读到尚未写入的描述符。clear 不依赖这些描述符，所以清屏成功不能反证。

现在把这项工作放在 `endRecording` 的收尾之后、`finalize` 之前，删除原 flush 入口的重复设置。
这是统一“返回的 command list 可提交”合同，不是关闭 descriptor buffer、改 shader 或跳过 draw。
同一原始 fixture 在 r3 的正常与错误恢复场景均为 2,548 点零错误，全图 FNV 与参考 DLL 相同。
生产普通 flush 的 GPU 同步仍保留；latency 通知相对 descriptor dispatch 的细微顺序变化不称为零成本证明。

### 2. 错误输入与设备故障分开

Draw 的无副作用 CPU 预检使用专用 `ProfileRejected`，宿主只把这类失败翻译为 `INVALIDCALL`。
GPU/提交/资源退休/内部所有者失败继续终态隔离，不把任意异常吞成可恢复错误。
新增用例故意使用编译合法但要求 `TEXCOORD1` 的 VS，与固定声明不匹配；拒绝后换回合法 VS，
必须继续完成原场景。此项最终实测结果见下方回执，不能仅凭源码判通过。

### 3. 健康闲置不等于半包超时

旧实验接线在等待下一次 API 前就启动 5 秒读包期限，会把合法闲置误判成断线。
新增显式选择的首字节 idle 入口：等待数据或精确 peer 退出；收到首字节后，剩余 header/body
仍共用原 5 秒期限。旧 RH0/RH1 调用不改语义，取消仍须等待真实 I/O 完成后才能释放缓冲。
6500 ms API 间隔、半包超时及 peer 退出取消分别验证，健康闲置不能靠心跳掩盖。

## 对照过程中暴露的既有生命周期问题

保留的单进程天气 DLL 正确画出了参考图，**但最终 device Release 返回 15，而非 0**。
原始失败为 `x64-d3d9-20261011-reference-r1` 与 r3 的 reference-normal，不是新代理的资源循环。

源码持有关系与实测计数吻合：PostFX 初始化持有 14 个 public COM 资源反向保活 device，
ImGui DX9 初始化另持有 1 个 device 引用；device 拥有这些内部消费者，其析构又被这些引用阻止。
保留一个 fixture texture 时返回 16，释放该 texture 后剩 15。这里是源审与引用计数一致解释，
未做逐地址对象 census，不扩写为游戏的所有泄漏根因。

没有通过反复 Release、修改原 DLL 或放宽测试让参考门变绿。验收分列：
`remoteGatePassed`、`referenceImageMatched`、`referenceLifecyclePassed`，总 `ok` 仍要求三者都成立。
参考图像通过不代表其退出通过。后续需为 PostFX/ImGui 定义 device-owned 内部所有权，包含初始化失败、
Reset、后续 UI buffer/texture 及 GPU 退休；不能只删除第三方 backend 的一条 AddRef。
参考失败时 `factoryFinalRefs=UINT32_MAX` 是未执行哨兵，factory 释放、DLL 卸载和窗口正常收尾均未到达。
这些进程最终由失败路径退出，不能算正常 GPU/窗口析构验收。

## 能力范围及下一步

当前固定为 64×64 BGRA8 离屏、D32F depth（无 stencil）、单 stream/texture、固定顶点声明、
INDEX16 triangle list、point/clamp sampler、受限 SM3 与常量。`Present` 明确返回 `E_NOTIMPL`；
Reset/Ex、固定功能、stateblock、UP、完整 mip/texture/Lock 兼容、多线程入口均未完成。
无游戏 Hook、WarVK pass 搬迁、玩家画面/性能验收或实际游戏减量。

下一顺序：先收紧已发现的内部 COM 生命周期；将这个真实 D3D9 链接到原 DXVK Presenter/WSI；
完善产品异步 owner、背压和故障退出；再扩固定功能/纹理/状态/Reset 与全画面覆盖，最后测游戏 x86 VA/commit
及帧时间。不会以关闭 caster、扩大预算或同时保留两套大缓存冒充迁移收益。
