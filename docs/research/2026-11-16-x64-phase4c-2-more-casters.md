## 1. 结论

- **四类投射体与特性在两种模式下结果相同**：动态缓冲里的投射体、alpha 测试的投射体、点光（照亮与投影）、阴影时间滤波。
  对照门 39 帧（模块关闭的一对 40 帧）在进程内与四个代理变体下 0 像素差异，pass 每一次运行的自述逐项相同（§6）。
- **蒙皮投射体延后，交给阶段 5.1 定路线**。读采集代码后发现，进程内阴影里的蒙皮投射体不是游戏的 draw：游戏（1.27a）在 CPU 上蒙皮，
  把姿态后的顶点写进动态缓冲画出来，`D3DRS_VERTEXBLEND` 恒为关；进程内阴影用的是数据层从模型 geoset 读出的绑定姿态几何
  加每帧的骨骼调色板（`PaletteSkinnedFF`）。到 x64 有两条路：在游戏的蒙皮 draw 上发记录（执行端本段已经具备，它就是一个
  动态缓冲里的 FixedWorld 投射体），或者走内容载荷（geoset 几何按内容键、骨骼走 `BonesRef`）。选哪条是生产端的决定，
  后一条还要动 pass 封口里的三个 `dynamicPose*` 字段，按规则归 Fable（§5）。
- **修了 pass 里一个玩家也会碰到的越界读**：时间滤波的运动矢量与可见性两个辅助 pass 只给 17 个绑定的布局写了 14 个描述符，
  DXVK 更新描述符时按布局读满 17 个，多读的 3 个是栈上的垃圾。夹具里一开时间滤波，**进程内的 x86 渲染器和宿主都崩**（0xC0000005）。
  这个布局从 v1.22.00 起就是 17 个绑定，**v1.22.00–v1.22.03 的玩家在面板里把“阴影时域模式”选成 Temporal 就会走到这里**；
  游戏里没有验证（§4.1）。
- **点光阴影路径上校验层报的 `08608` 已修**（设计 §7 表里的那两处），改后带校验层的宿主会话 0 错误。
  投射体遮罩路径的两处没有改：那条路径只有研究开关能打开，对照门跑不到（§4.2）。
- **新的跨帧状态都过了生命周期帧**：动态缓冲的拷贝一帧一还；时间滤波的历史在新会话里没有了（`taa-session` 等于 `taa-first`）；
  点光的立方阴影图在第一个投影的点光出现时建一次，之后经四次地图切换和一次设备重置不再变。
  宿主设备分配器的已用字节从 `shadow-return` 帧起到会话结束不变（§7）。
- **原有路径没有变。** 特效门 77 帧、GPU 参照门 48 个哈希与 4c-3 逐个相同；正向切口不增（§6）。
- **线上格式只加不改**：新记录 12（`ShadowCasterAlpha`，12 字节）与 13（`PointLights`，最多 580 字节）；已有记录的布局、编号、大小不变。
- **x86 内存**：代理模式下 x86 私有内存在各采样点都是 2.4 MiB，增量 0（§7）。

## 3. 对照的帧

4c-3 的 32 帧不变，插入 7 帧。“全”指三个箱子。

| 帧 | 发了什么 | 结果（两模式相同） |
|---|---|---|
| `taa-first` | 设置里请求阴影时间滤波，全 | 与 `shadow` 不同（时间滤波本身）。pass 报告 Temporal 模式、写了历史、没读历史 |
| `taa-history` | 同上，紧接着 | 与 `taa-first` 不同：读了上一帧的历史并混进来 |
| `taa-session` | 地图切换加 `Present` 之后，同上 | 等于 `taa-first`：新会话没有历史可读 |
| `dynamic` | 箱子 0 在动态缓冲里，draw 之后、BeforeUi 之前被调用方改写 | 等于 `sun-back`：回放的是 draw 读到的内容。账目：拷贝 1 个投射体、456 字节（24 个 16 字节顶点、36 个 16 位索引） |
| `alpha-off` | 箱子 0 贴条纹纹理、开 alpha 测试，不发 alpha 记录 | 与 `sun-back` 不同（箱子本身画成条纹）；它的影子仍是整块 |
| `alpha` | 同上，发 alpha 记录 | 与 `alpha-off` 不同：影子也有条纹的缺口。账目：一个投射体按 alpha 测试准备 |
| `point-light` | 一盏暖色点光在箱子上方，开点光与点光阴影，点光不投影 | 与 `sun-back` 不同（被点光照亮） |
| `point-shadow` | 同上，点光投影 | 与 `point-light` 不同：箱子的点光阴影。pass 建它的点光立方阴影图（§6） |

模块关闭的一对里，三个时间滤波帧都等于 `shadow`，`taa-requested` 仍等于 `reset-fresh`；其余 36 帧与模块打开的一对逐字节相同。

这次跑出来才确定、已钉进门禁的行为：

- **pass 报告的 `taaMode` 是实际生效的模式**（Temporal = 2），“读了历史”另有一位。所以门里用历史位而不是模式值判断有没有读历史。
- **时间滤波历史作废的原因**逐帧固定：模块打开时第一次运行是“阴影图资源新建”加“时间滤波资源新建”，第一个不请求的帧是“模式切换”，
  墓碑与策略两帧是“生命周期”；模块关闭时没有“时间滤波资源”一位，而 `taa-requested` 和其后第一帧各是一次“模式切换”。
- **接收的“有点光阴影”只看设置与有没有点光**，不看点光是否投影：`point-light` 帧也是 1。投影与否由画面和立方阴影图的出现区分。
- **没有 `PointLights` 记录的帧没有点光**：执行端把光源管理器清空，所以点光帧之后的帧与之前的画面相同。

## 4. pass 原有的两个错

### 4.1 时间滤波辅助 pass 的描述符数

阴影接收的管线布局有 17 个绑定（14–16 是 v1.22 加的原生光照基线）。接收自己写 17 个描述符；时间滤波的运动矢量 pass 和
可见性 pass 用同一个布局，却只声明了 14 个元素的数组。DXVK 的 `setLayout->update` 按布局逐个读描述符指针，读到数组外面的
3 个栈槽。夹具第一次开时间滤波，两种模式都崩在描述符拷贝：进程内臂崩在 x86 渲染器 `renderer.dll`（就是玩家 DLL 的构建）
偏移 0xA864A3，读一个野指针，用 `llvm-nm` 对映像定位到 `DxvkDescriptorUpdateList::copyAligned<4>`；宿主一侧设备丢失。

改法：绑定数命名一次（`kReceiverLayoutBindingCount = 17`），三个 pass 的数组都按它声明；两个辅助 pass 不用 14–16，
照接收在没有基线时的做法填上深度拷贝视图。改后两模式 0 像素差异，带校验层 0 错误；静态测试钉住三处都用这个常量、不再有 14 个元素的数组。

**对玩家的影响**：git 记录里 17 个绑定的布局随 `17ecf66` 进来，v1.22.00 到 v1.22.03 四个标签都包含它，而那时两个辅助 pass
仍是 14。玩家面板的“阴影时域模式”选 Temporal（默认不是），默认的运行档位又不关 `shadow.taa` 模块，就会走到这里。
夹具里同一份 x86 渲染器在这一步崩了；多读的 3 个指针是什么取决于栈，游戏里可能崩、也可能绑上垃圾描述符，**没有在游戏里验证**。
修复只在工作区里。

### 4.2 点光阴影路径的 `08608`

设计 §7 表里预告的那一类：绑顶点缓冲时又传一遍步长，而管线的步长是静态的。`point-shadow` 帧第一次让校验层看到这条路径，
报了 `VUID-vkCmdDrawIndexed-None-08608`。改法照 4c-1：步长传空（点光管线的键本来就取这次 draw 的位置、混合、纹理坐标三个步长），
两处都改。改后带校验层会话 0 错误，画面哈希不变。

投射体遮罩路径的同类两处没有改。那条路径由 `kShadowS1TerrainCasterMaskEnabled`（发布版 `false`）或环境变量
`DXVK_WAR3_S1_TERRAIN_CASTER_MASK` 打开，玩家路径上没有，对照门也跑不到；照设计“不要提前盲改”的规则留着，设计 §7 表已更新。

## 5. 蒙皮投射体为什么延后

设计里的设想是“骨骼矩阵走 `BonesRef`，再加一条混合权重/索引的布局记录”。照 §7 第一步读采集代码，结论是这一项
在 4c-2 里做不完，要先由生产端定路线：

- **游戏自己不做顶点混合。** 项目早先的实测（`docs/research/war3_render_issues/28_gpu_skinning_takeover_feasibility`、
  `AGENTS_HISTORY` 里的 draw 时姿态普查）：1.27a 的 `D3DRS_VERTEXBLEND` 在 draw 时恒为关，骨骼变换全在 CPU 上做，
  送进 D3D9 的流 0 已经是姿态后的顶点，写在动态缓冲里。
- **进程内阴影的蒙皮投射体来自数据层，不来自 draw。** 采集代码（`d3d9_device.cpp` 里构建持久几何的两处）用模型 geoset 的
  绑定姿态位置、混合权重与索引建几何（键里带 `authoritativeSkinned`），回放模式是 `PaletteSkinnedFF`，调色板是数据层每帧算的姿态；
  这一帧有多少姿态、蒙皮输出多少、姿态签名，就是 `ShadowFrame` 的三个 `dynamicPose*` 字段，pass 把它们混进回放封口
  （`replaySeal.mixU64`），点光阴影的持久准备也拿它们核对。
- **所以 x64 有两条路，选哪条是阶段 5.1 的事：**
  1. **在游戏的蒙皮 draw 上发 `ShadowCaster`。** 执行端本段已经具备：这就是动态缓冲里的 FixedWorld 投射体（`dynamic` 帧），
     几何在 draw 时拷进宿主的池。x86 不多读、不多存任何东西。代价是只有画出来的单位才投影，视野外单位落进视野的影子会缺，
     这正是进程内改走数据层几何的原因之一（进程内“draw 时姿态”的接入在代码里还是 TODO）。
  2. **走内容载荷。** geoset 几何按内容键上传一次（阶段 1 的内容协议，宿主有按键的仓库），骨骼调色板走 `BonesRef`，
     `ShadowCaster.mode` 加一个新值和一条混合布局记录。这条路要定 `dynamicPose*` 在宿主里怎么算、怎么进封口，
     碰的是封口语义，按路线图的规则归 Fable。

本段没有为第 2 条路先写执行端：它的记录形状取决于生产端怎么交出 geoset 与姿态，先写等于替 5.1 做了决定。

最初我把延后的原因写成“宿主固定管线画不了顶点混合的 draw”（宿主的固定管线状态对 `D3DRS_VERTEXBLEND` 确实只收 0，
也没有 `WORLDMATRIX(n)`）。这条对游戏不成立，因为游戏从不打开顶点混合；已改正，记在这里以免别人重复这个判断。

## 7. 分账

阴影对照门的数字（64×64 目标、1024 纹素级联、三个箱子、一盏 256 纹素的点光；机器上有别的任务，时间只在同一轮内比较）。

**宿主一侧**（代理模式；进程内臂的 pass 存储相同）：

| 项 | 字节 | 说明 |

## 8. 没覆盖的与要知道的

- **没有在游戏里跑。** §4 的两处改的是玩家在用的 pass；与 4a、4b、4c-1、阶段 3 的改动一起，出补丁前统一做实机回归。
  §4.1 的越界读在已发布的 v1.22.00–v1.22.03 里，是否要单独出补丁由作者决定。
- **生产端是夹具。** 游戏里谁发 `ShadowCasterAlpha`（采集时读 draw 的 alpha 测试状态和纹理级）、谁发 `PointLights`
  （数据层光源管理器每帧的活动点光）是阶段 5.1 的事。
- **点光只有一盏、一种分辨率（256）。** 多盏点光的排序、预算拒绝、立方阴影图按面更新（pass 有“面预算”，未更新的面沿用上一帧）
  都没有对照帧。点光阴影在进程内是在帧内异步准备、帧内汇合的，发布版不开持久准备；宿主同样。
- **原生灯光（游戏自己的 D3D 灯）没有记录**，宿主里 `nativeLightCount` 恒为 0。原生灯光分离是 4c-1 划掉的研究开关，不影响玩家路径。
- **时间滤波只覆盖了 Temporal 模式与“新会话没有历史”。** 相机移动下的运动矢量、历史拒绝的阈值没有对照帧；夹具的相机不动。
- **动态缓冲只覆盖了“draw 之后被改写”这一种。** 池满（一帧 16 MiB）时按遗漏计、不崩，只有静态规则钉住，没有运行时的帧。
  流模式下拷贝读的是宿主那份缓冲里 draw 已经上传的内容，命令环模式与此相同（都在门里）。
- **alpha 记录只覆盖了第 0 级纹理、第 0 组纹理坐标。** 其它级和组只有布局测试和静态规则。
- **帧时间在共享机器上不稳**，只能同一轮内比较。
