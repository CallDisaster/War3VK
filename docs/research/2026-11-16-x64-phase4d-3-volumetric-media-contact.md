## 1. 结论

- **地图的雾体积、天气的雾与低空雪、点光接触阴影在两种模式下结果相同。** 对照门 50 帧（模块关闭的一对 51 帧）在进程内与
  四个代理变体下 0 像素差异，阴影 pass 与体积光 pass 每一次运行的自述逐项相同，带校验层的宿主会话 0 错误（§5）。
- **雾体积走一条新记录，带作者写下的值**（`FogVolumes`，编号 16，4 + 52n 字节，最多 8 个）。执行端用数据层雾体积管理器
  自己的接口把它们建进本进程的管理器，pass 读到的矩阵在两端由同一段代码算出（§2；为什么不送帧快照见 §4）。
- **天气介质不加记录。** 它来自 4a 的 `Snow` 记录（雪的执行器本来就读它）：执行端取 pass 读的那部分，帧序号与纪元用自己的，
  天气运行时的两个修订号不上线（天气实例的时间滤波是关的，不留历史）。有天气介质的帧即使没有 `VolumetricLight` 记录，
  体积光 pass 也跑（§2）。
- **点光接触阴影两条路径都进了对照帧。** 屏幕空间步进（A0）在接收着色器里画出 302 个像素的接触阴影；
  HiZ 路径（A1，混合光追的计算 pass，设置里的默认）跑了、结果被接收着色器采用，但它的解算在这个夹具里**不产生遮挡**，
  画面等于没有接触阴影。两种模式相同。为什么不产生遮挡没有查（§3）。
- **补了 4c-3 起漏数的一笔存储。** 阴影 pass 的存储出口没有数混合光追拥有的图和缓冲（它只数了 pass 每次运行清掉的两个视图），
  `point-contact-hiz` 帧第一次让它们出现。现在经混合光追的三个只读访问器数到，静态规则要求它的每个图和缓冲成员都被数到（§4）。
- **原有路径没有变。** 与 4d-2 共有的 45/46 帧在 7 组里哈希逐个相同；特效门 77 帧、GPU 参照门 48 个哈希与 4d-2 逐个相同；
  正向切口不增（§5）。GPU 参照门前两轮因 GPU 被别的任务占满、宿主建设备超时失败，回执留着，第三轮通过（§5）。
- **线上格式只加不改**：新记录 16；已有记录的布局、编号、大小不变。
- **x86 内存**：代理模式下 x86 私有内存在各采样点都是 2.4 MiB，增量 0。宿主设备分配器的已用字节比 4d-2 多 208,384，
  正好是天气实例的 froxel 资源（191,488）加混合光追的资源（16,896），跨生命周期不增（§6）。

## 3. 对照的帧

4d-2 的 45 帧不变，在 `volumetric-lamp` 之后插入 5 帧。“全”指三个箱子。

| 帧 | 发了什么 | 结果（两模式相同） |
|---|---|---|
| `fog-volume` | 全，`VolumetricLight`（froxel 高）加一条 `FogVolumes`：一个盒（中心 (0, 0, 160)，半尺寸 (520, 520, 170)，绕 z 转 30°，密度 0.8，羽化 0.2），外加一个关闭的球 | 与 `volumetric` 不同（3,235 个像素）。体积光报告散射了 1 个雾体积（关闭的球不进快照） |
| `weather-medium` | 全，一条 `Snow`：降雪 0，雾 0.6，低空雪 0.5，区域 ±900、高 0–420；没有 `VolumetricLight` | 与 `weather-clear` 不同（3,952 个像素）。体积光 pass 跑了、它自己的介质关着（后端 −1、未合成），天气实例合成了 |
| `weather-clear` | 同上，雾与低空雪都是 0 | 与 `sun-back` 相同：没有天气介质，体积光 pass 不跑；降雪为 0，雪的执行器也什么都不画 |
| `point-contact` | 全，`point-light` 帧的那盏点光，`Lighting` 关掉点光立方阴影、打开接触阴影并关掉 HiZ（A0） | 与 `point-light` 不同（302 个像素，最大通道差 79） |
| `point-contact-hiz` | 同上，HiZ 打开（A1，设置的默认） | 与 `point-light` 相同。阴影 pass 建了混合光追的资源（存储增长，§5） |

两处取舍：

- **接触阴影的帧关掉了点光立方阴影。** 接触阴影只往立方阴影没遮住的地方加遮挡（取两者的小值），而这个夹具里射线找到的地方
  立方阴影已经全遮住了；两者都开时画面等于 `point-light`。
- **A1 不产生遮挡，钉的是“两模式相同”，不是“画出了东西”。** 能确定的是 A1 跑了、结果被采用：A1 失败时接收着色器退回 A0，
  画面会等于 `point-contact`，实际等于 `point-light`。A1 的解算是保守的（接收着色器从 4 个半分辨率纹素重建，深度差超过
  接收深度 0.2% 的纹素不算、锚点纹素不可信时整体不遮挡，缺证据只会往“全亮”走）。是哪一条把这个 64×64 夹具里的遮挡清零的，
  没有查；它与迁移无关（两种模式同一份代码、同一个结果），是 A1 本身的事。

这次跑出来才确定、已钉进门禁的行为：

- **天气实例第一次出现时建一次资源，雾体积不建。** 体积光 pass 的存储逐次是：`volumetric`、`volumetric-again` 292,864，
  `volumetric-march` 290,816，`volumetric-lamp` 292,864（这四个与 4d-2 相同），`fog-volume` 292,864（与 `volumetric` 相同），
  `weather-medium` 484,352——多出的 191,488 是天气实例的 froxel 资源，记在同一个账里。之后的帧不跑体积光 pass，不记。
- **混合光追的资源在 `point-contact-hiz` 建一次**：阴影 pass 的存储从 24,741,120 增到 24,758,016（+16,896），之后不变。
  修存储出口之前，开发中的探索运行里这个数在这一帧增长、下一帧又落回去（pass 每次运行清掉它的两个视图，出口原来只数了视图，
  而混合光追自己留着图和缓冲），于是补了出口（§4）。

## 4. 对玩家代码的改动

这一段没有改 pass 的渲染逻辑。玩家在用的代码改了四处：

| 改动 | 文件 | 对玩家的影响 |
|---|---|---|
| 混合光追加三个只读访问器 | `war3_hybrid_ray_tracing.h` | 无：只返回成员的引用 |
| 体积光 pass 加 `WeatherLastRun()` | `d3d9_war3_volumetric_light.h` | 无：只返回天气实例已有见证的指针，没有天气实例时为空 |
| 阴影 pass 的 `ResourceBytes()` 数混合光追的图和缓冲 | `d3d9_war3_shadow_resources.cpp` | 只是诊断数字：进程内打开接触阴影的 HiZ 路径后，这个数多出混合光追的那几块（原来漏数）。不分配、不录命令 |
| 体积光 pass 的 `ResourceBytes()` 加上天气实例的 | `d3d9_war3_volumetric_light.h` | 同上，只是诊断数字 |

`d3d9_device.cpp` 的改动都在夹具入口里（`War3RunSceneEffectsForFixture`），游戏不走它。`ApplyFogVolumes` 只在夹具入口与宿主里调用：
游戏里的雾体积仍由 JASS 写进数据层的管理器。

**为什么送作者写下的值而不是帧快照。** 数据层头文件（`war3/state/war3_fog_volume.h`）在阶段 3 写的是“代理模式下把快照送给宿主”。
4d-3 改成送原值：快照是派生出的世界→局部矩阵与包围球（每个体积 21 个字），原值是 13 个字；送原值时两端用管理器同一段代码
派生，记录的校验也照管理器自己的范围，宿主拿到的东西不会是管理器构造不出来的。代价是生产端要一个新的只读接口（§7）。

## 7. 没覆盖的与要知道的

- **没有在游戏里跑。** 与 4a、4b、4c、4d-1、4d-2、阶段 3 的改动一起，出补丁前统一做实机回归。
- **生产端是夹具。** 游戏里谁发 `FogVolumes` 是阶段 5.1 的事：管理器现在只对外给派生后的帧快照，没有按原值列出体积的接口，
  生产端要加一个只读的；没有记录等于没有雾体积，所以每帧都要发（执行端只在记录变了时重建）。天气介质的生产端就是 4a 的 `Snow` 记录，
  已经有了，但它在游戏里由谁、在哪一帧发也归 5.1。
- **A1 接触阴影在夹具里不产生遮挡**（§3）。没有查原因；要查的话从混合光追计算 pass 写的可见性与置信度开始。
  接触阴影默认关闭，玩家路径上默认不走它。
- **天气实例不留历史。** 修订号留 0（§2）；以后若打开天气实例的时间滤波，修订号要上线，碰跨帧状态的语义，归 Fable。
- **只覆盖了一种组合。** 圆柱没有任何测试；球只以关闭的形态出现（布局测试与夹具）；多于一个活动的雾体积、
  天气与 `VolumetricLight` 同时存在、天气区域部分在视野外，都没有对照帧。
- **帧时间在共享机器上不稳**，只能同一轮内比较。
