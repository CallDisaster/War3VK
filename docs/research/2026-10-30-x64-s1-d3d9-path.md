## 1. 调用方普查（`warvk-d3d9-caller-census/v1`）

冻结的 v2 迁移普查把 WarVK 自己的内部调用（特效、阴影、后处理）和 Game.dll 的调用混在一起，
据此估计 S1 范围会偏大。新普查与 v2 并列（v2 行和 `test_d3d9_migration_census_integration.py` 不变）：

- 每个公开设备方法入口取 `__builtin_return_address(0)`，按 PE 映像范围分为 `game`（Game.dll）、
  `self`（本 DLL）、`other`。范围在设备构造时由 `GetModuleHandleW(L"Game.dll")` 和本模块的 SizeOfImage 求得；
  Game.dll 未加载时 `gameModuleKnown=false`，全部记为 other。
- 每个调用方：48 个 API 尝试计数、5 种 draw、7 种图元类型（含非法）、超过旧代理上限 4096 图元的 draw 数、
  最大图元/顶点数、出现过的渲染状态/纹理阶段状态/采样器状态集合、最多 32 个 FVF；
  纹理类按 (调用方, 种类, 格式, usage, pool) 聚合（最多 32 类）。
- 与 v2 相同的 try-cell 并发记录（`atomic_flag`，忙则计入 `recordBusy`，不阻塞）；快照 3,696 B，随 v2 里程碑一起输出。
- 局限：若公开方法被内联进本 DLL 的另一帧，会记成该帧的调用方。内部 SetFVF→SetVertexDeclaration 正确地记为 self，
  说明主要路径没有被内联。
- 读取器 `AutoTest/analyze_d3d9_caller_census.py` 严格解析（字段精确、重复键/NaN 拒绝、draw 计数平衡、
  集合有序无重、同设备序号不回退、坏行不跳过）；`test_d3d9_caller_census.cpp` 42 项（x86/x64）、
  `test_d3d9_caller_census_reader.py` 8 项通过，原 58 项普查测试仍通过。

构建 `x86-caller-census-build-20261030-r1`（`build32_device_owner_caller_census_20261030`），
DLL `DC055084…44E0`（24,469,504 B）。实测 `s1-caller-census-20261030-r1`：
`LOCAL_GAME_START_CAPTURE_EXIT_PASSED`（沙盒实例、隔离桌面、模块校验、截图、正常退出 0、受保护文件不变），

## 3. 第一组实现（G1 + G2）

- **`tools/render_host/d3d9_topology.h`（新）**：代理与宿主共用。`MaxDrawPrimitives=65535`；
  `DrawElementCount`：LINELIST 2n、LINESTRIP n+1、TRIANGLELIST 3n、TRIANGLESTRIP/FAN n+2，其他为 0（拒绝）；
  点仍然拒绝（本协议不携带点大小/点精灵状态）。
- **代理**：DrawPrimitive/DrawIndexedPrimitive 用 `ValidDrawTopology` 和 `DrawElementCount` 做范围与索引校验；
  非索引 draw 的 `numVertices` 等于元素数。SetRenderState 接受上表值域，DITHERENABLE（≤1）只保存在代理并可读回、
  进状态块（像素类，与原版 `d3d9_stateblock` 一致）。Caps：`MaxPrimitiveCount=65535`，ZCmpCaps 全部比较，
  Src/DestBlendCaps ZERO..SRCALPHASAT，PrimitiveMiscCaps 加 CULLNONE/CW/CCW 和 BLENDOP；协商时与物理 caps 求交。
- **宿主 `dxvk_core/d3d9_backend.cpp`**：profile 检查改用 `ValidDrawTopology`，索引数用 `DrawElementCount`，
  输入装配按图元类型映射到 `VK_PRIMITIVE_TOPOLOGY_*`（批内状态复用已按图元类型比较）。
  剔除映射与 DXVK 一致：CW→`VK_CULL_MODE_FRONT_BIT`、CCW→`BACK`，正面为 CLOCKWISE。

## 6. 第二组：G3 真实分辨率后台缓冲与呈现

### 设计

- **wire（`d3d9_wire.h`）**：Initialize 的 args[0..1] 是协商出的目标尺寸，每轴 1..4096（`MaxTargetDimension`，
  `ValidTargetExtent`）；`Width/Height=64` 只留作 wire 默认值和 64×64 测试。ClearRegions 按会话尺寸校验。
- **分带回读**：Readback 的 args[0] 是起始行，[1] 是行数，[2] 是源（Target=0、Presented=1），[3..4] 是帧号。
  (0,0) 表示整图，只在整图放得进一次回复（≤ 65,440 B）时有效；否则按整行分带，每带不超过一次回复
  （`ReadbackBandRows`：宽 1902 每带 8 行，963 行共 121 带；宽 257 每带 63 行；宽 4096 每带 3 行）。
- **Present 回复**：整图放得进一次回复时（`PresentedInline`，64×64 照旧），回复里同时带帧号和整图；
  否则只回 8 B 帧号，代理按这个帧号分带取宿主冻结的快照，所有带到齐后才发布帧号。
  宿主只接受等于当前 `presentedFrame` 的帧号。非诊断的 IsolatedPresenter 档位 Present 不带回复载荷。
- **代理**：CreateDevice 按 D3D9 窗口模式语义：后台缓冲某轴为 0 时取客户区尺寸，成功后写回
  `BackBufferWidth/Height`；呈现档位要求客户区等于后台缓冲。默认视口和默认剪裁矩形都覆盖整个后台缓冲，
  与 DXVK 在 Reset/SetRenderTarget 时的行为一致。SetViewport、CreateOffscreenPlainSurface、GetRenderTargetData
  和 Clear 快路径都按设备尺寸处理。
- **宿主**：Peer 表面模式下，离屏目标和交换链都用协商尺寸。host-top-level/host-child 仍是冻结的 64×64 合同，
  非 64×64 直接拒绝。宿主回读缓冲从 256 KiB 降到一带（65,440 B）。
- **x86 内存**：Offscreen 与 IsolatedPresenter 档位下，x86 侧不持有任何整图。只有诊断档位
  `presenter-readback-isolated-v1` 保存一份 8 + w×h×4 的呈现副本（1902×963 时为 7,326,512 B）。
  GetRenderTargetData 的系统内存面按 D3D9 语义是 w×h×4，只在调用方创建它时存在。
- 尺寸变化（Resize/Reset）仍是永久的尺寸故障，留给 G4。

### 设计

- **游戏的交换链**：窗口模式、X8R8G8B8 后台缓冲、D16 自动深度、`INTERVAL_IMMEDIATE`，behaviorFlags 66
  （`HARDWARE_VERTEXPROCESSING|FPU_PRESERVE`，原先就接受）。
- **代理 `ResolveSwapChain`**：CreateDevice 和 Reset 共用同一套参数检查。
  - 只接受窗口模式；后台缓冲 A8R8G8B8 或 X8R8G8B8，BackBufferCount ≤ 1，不做多重采样，DISCARD。
  - 自动深度 D32F_LOCKABLE 或 D16；Flags 0，不设刷新率，hDeviceWindow 必须一致。
  - 间隔只接受 DEFAULT、ONE 和 IMMEDIATE（窗口模式 D3D9 只有这三种）。
  - 某轴为 0 时取客户区尺寸；呈现档位要求客户区等于后台缓冲。
  - Factory 的 CheckDeviceType/CheckDeviceFormat（RT/DS）/CheckDeviceMultiSampleType/CheckDepthStencilMatch
    同样接受 X8R8G8B8 和 D16。
- **wire**：
  - Initialize 的 args[7] 是后台缓冲格式：0 是 A8R8G8B8，22（`OpaqueBackBuffer`，即 X8R8G8B8）是不透明目标。
  - args[5] 是间隔：离屏必须为 0；呈现档位是 `IntervalOne=1` 或 `IntervalImmediate=0x80000000`。
  - 新增 `Op::Reset`（排在最后）：args[0..1] 是尺寸，[5] 是间隔，[7] 是格式，含义与 Initialize 相同；
    不带 id、代数和载荷，档位和窗口沿用会话的。
  - `PresentSkipped=0x8876086A`（D3DERR_NOTAVAILABLE）：窗口尺寸已变、尚未 Reset 时，宿主跳过这次 Present。
- **X8R8G8B8**：存储仍是 BGRA8。混合因子里 DESTALPHA 换成 ONE，INVDESTALPHA 换成 ZERO；
  呈现时采样视图把 alpha 固定为 ONE。**D16** 与 WarVK 原生 fork 一样映射到 D32_SFLOAT，宿主不用改。
- **Reset 按原版 D3D9 的顺序**：
  1. 参数校验失败，或正在录制状态块：返回 INVALIDCALL，状态不动，设备仍正常。
  2. 否则一律先清空状态（ResetState），并释放隐式后台缓冲。
  3. 如果还有可丢失资源：DEFAULT 池 VB/IB、应用持有的后台缓冲引用、状态块。设备进入 NotReset，返回 INVALIDCALL。
     与原版一样，状态块也计数。
  4. NotReset 期间，TestCooperativeLevel 返回 DEVICENOTRESET，Present 返回 DEVICELOST；
     下一次成功的 Reset 恢复设备。MANAGED 纹理跨 Reset 保留。
  5. 成功后：新尺寸写回 `BackBufferWidth/Height`，视口和剪裁矩形覆盖新目标，
     效果、采样器和纹理阶段状态重新发到宿主。
- **清空哪些状态，以参考 DLL 的 `D3D9DeviceEx::ResetState` 为准**（r2 暴露）：
  - 重置：渲染状态、纹理阶段与采样器状态、纹理绑定、VB/IB 绑定。
  - 流缓冲置 null 时，offset 和 stride 保留（DXVK 的 SetStreamSource 传 null 时也不改这两个值）。
  - 保留：着色器、顶点声明（因此 FVF 也保留）、着色器常量、变换、材质和灯光。
  - 视口和剪裁矩形在 Reset 绑定新后台缓冲时覆盖新目标。
  - 代理原先把这些全部清掉，现在按 DXVK 的范围清。
- **默认 CULLMODE**：代理原先沿用宿主 `RenderStates` 的 NONE；D3D9 和 DXVK 的默认值是 CCW。
  创建和 Reset 现在都设为 CCW。现有夹具都在 draw 之前显式设置 CULLMODE，所以原有哈希不受影响。
- **宿主 `reset()`**：
  - 前提：尺寸、间隔合法；host-owned 模式只支持 64×64；没有活的缓冲。
  - 等 GPU 空闲、上一次呈现退役，确认没有已获取的交换链图像。
  - 解绑作者资源，丢掉旧的颜色/深度视图和图像，按新尺寸、格式重建（`createTargets`，与 initialize 共用）。
  - 呈现档位重新校验窗口，`setSurfaceExtent` 让交换链在下一次获取时重建，`setSyncInterval` 设为
    IMMEDIATE→0、其他→1。
  - 诊断档位重建呈现回读缓冲。
  - 新目标清零后才回复 OK；在第一次 Present 之前，Presented 回读一律拒绝。
- **改尺寸后、Reset 之前**：宿主在 acquire 之前检查客户区。只有尺寸变化时跳过这一帧，返回 PresentSkipped，
  代理把它当作 D3D_OK。窗口身份变化仍是永久故障。原版 D3D9 会把这一帧拉伸显示，这里是丢帧。
- **WarVK fork 的 WM_SIZE 处理**（r1 暴露）：fork 的窗口过程 hook（`d3d9_window.cpp`）收到 WM_SIZE 时，
  自己调 `ResetSwapChain` 到新客户区尺寸，改写 War3 内部的分辨率字段，而且不把 WM_SIZE 转给 War3
  （注释写明 War3 自己的窗口模式 WM_SIZE 路径会让进程崩溃）。也就是说，游戏改窗口尺寸时并不调 Reset。
  dev 代理没有这个 hook。

## 8. 第四组：G5 动态 VB/IB 的 Lock 模式

### 普查（`warvk-d3d9-buffer-census/v1`）

- **做法**：沿用调用方普查的模式（§1）。x86 fork 的 `D3D9Buffer::Lock/Unlock` 按返回地址把调用方分成
  game/self/other，按（调用方、种类、长度、usage、pool、格式、FVF）归类，最多 16 类。
  - 每个缓冲一个游标：上次 Lock 的结尾、已写前缀、嵌套深度。
  - 每类计数：Lock/Unlock 次数、字节数、最大 Lock、各 flag 次数、size=0 与整缓冲 Lock、越界、嵌套、
    顺序追加、回绕与回绕时带 DISCARD、跳过未写区域、8 档 Lock 尺寸分布，以及每帧最多 Lock 次数和字节数。
  - 只在 `WARVK_D3D9_MIGRATION_CENSUS_DEV` 构建里编译；有界 try-cell，冷路径只在呈现里程碑和设备正常销毁时输出。
  - 严格读取器 `analyze_d3d9_buffer_census.py`：多余字段、计数不平衡、flag 超过 Lock 数等都拒绝。
- **普查构建** `x86-buffer-census-build-20261030-r1`（`build32_device_owner_buffer_census_20261030`，
  DLL `A778C927…BE16`，24,477,696 B），回执 `C9C9BB40…06A6`。
- **游戏普查** `g5-buffer-census-20261030-r1`（`run_native_d3d9_survey.py --normal-exit-test`），
  `LOCAL_GAME_START_CAPTURE_EXIT_PASSED`，受保护文件不变，回执 `AC13F56B…A016`。
  共 1951 次 Present，最后一份快照来自设备正常销毁：

| 缓冲（全部 DEFAULT 池，usage 0x208 = DYNAMIC\|WRITEONLY） | Lock 次数（每帧平均 / 最多） | 字节（每帧平均 / 最多） | 最大一次 Lock | flag |
|---|---|---|---|---|
| VB 524,288 B，FVF 0x112（XYZ\|NORMAL\|TEX1） | 26,572（13.6 / 160） | 5.4 KB / 523,488 B | 169,120 B | NOOVERWRITE 26,552，DISCARD 20，全部带 NOSYSLOCK |

- 三个都是顺序环形缓冲：Lock 依次追加，放不下时回到 0，每次回绕都带 DISCARD。
- 没有越界、嵌套、跳写和 READONLY Lock。self（WarVK 自己）只有一个 72 B 的 WRITEONLY VB。

**由此发现远端路径接游戏的三个问题**：

1. 代理的 Lock 拒绝 `D3DLOCK_NOSYSLOCK`，游戏两个 VB 的每次 Lock 都会失败。
2. wire 的 `MaxBuffer` 是 256 KiB，小于游戏 512 KiB 和 576 KiB 的 VB，CreateVertexBuffer 就会失败。
3. 宿主的 `uploadBuffer` 每次都先 settle（等 GPU 空闲并退役），再经暂存缓冲复制并 `submit(true)`，
   即每次 Unlock 两次 GPU 排空。游戏每帧大约 52 次 Lock，多的时候 400 次，等于每帧把 GPU 排空上百次。

### 设计

- **wire**：
  - `MaxBuffer` 改为 1 MiB（覆盖游戏最大的 576 KiB VB）。
  - CreateBuffer 的 args[2] 是 `D3DUSAGE_DYNAMIC`（0/1，其他值拒绝）。
  - UploadBuffer 的 args[1] 是这次 Lock 的方式：`UploadMode::Ordered=0`、`NoOverwrite=1`、`Discard=2`。
    `ValidUploadMode`：静态缓冲只接受 Ordered，动态缓冲接受 0..2，其他值拒绝。
- **代理**：
  - CreateVertexBuffer/CreateIndexBuffer 把 DYNAMIC 传给宿主。
  - Lock 接受 NOSYSLOCK（与 DXVK 一样只当调度提示），并记下 Lock 的 flag。
  - Unlock 按 MaxPayload 分块上传；只有第一块带 Discard，其余块写进新存储，标为 NoOverwrite；普通 Lock 是 Ordered。
  - `call` 本来就会先刷出暂存的 draw，所以上传不会越过它之前的 draw。
- **宿主**：
  - 动态缓冲用 host-visible、coherent 的内存（`coherentBuffer`，与 stream 档位的常量环相同）。
  - **NoOverwrite**：直接写映射内存，不等 GPU。应用保证这段范围没有在用。
  - **Discard**：
    - stream 档位：`invalidateBuffer` 给缓冲换一块新存储，已经录制的 draw 继续读旧存储；
      再把旧存储里已初始化的前缀复制过来（初始化前缀模型要求宿主保留这些字节）。不等 GPU。
    - 其他档位：先 settle，再原地写。这些档位每个 draw 都单独提交，settle 之后 GPU 已经读完旧数据。
  - **Ordered**（动态缓冲上的普通 Lock）：settle 后原地写。
  - 静态缓冲照旧：settle、暂存复制、提交。
  - 新增 stderr 行 `D3D9 dynamic-buffer-host:`（`warvk-d3d9-dynamic-buffer-host/v1`）：dynamicBuffers、
    orderedUploads、noOverwriteUploads、discardUploads、discardRenames、discardCarriedBytes、uploadSettles。

### 测试

- **wire CPU 测试**：`MaxBuffer==1048576` 且不小于 589,824；`ValidUploadMode` 的
  (0, 静态/动态) 有效，(1, 2, 静态) 无效，(1, 2, 动态) 有效，(3, UINT32_MAX, 动态) 无效。
- **普查单元测试** `test_d3d9_buffer_census.cpp`：29 项，x86 和 x64 都通过；读取器测试 5 项，含 25 种篡改。
- **extent fixture 的 `--ring` 模式**，照普查结果重放游戏的缓冲用法：
  - 三个缓冲与游戏相同：512 KiB XYZ\|NORMAL\|TEX1 VB、576 KiB XYZ\|NORMAL\|DIFFUSE\|TEX1 VB、96 KiB INDEX16 IB，
    DEFAULT 池、DYNAMIC\|WRITEONLY；VB 的 Lock 带 NOSYSLOCK。

## 9. 第五组：G2b DEPTHBIAS 与按 FVF 缓存声明

### 设计

- **DEPTHBIAS（渲染状态 195）**：游戏设置的渲染状态里只剩它远端不支持。SLOPESCALEDEPTHBIAS（175）游戏不用，不携带。
  - wire：effects 包的第 16 个键（`EffectKeys` 末尾追加），默认 0，要求是有限的 float；包长 76 → 80 B。
    effects 包与 draw 有序，不改 draw 记录布局。
  - 代理：SetRenderState/GetRenderState 存取，状态块按像素状态捕获（与原版 `CapturePixelRenderStates` 一致），
    ResetState 清零。Caps 的 RasterCaps 加 `D3DPRASTERCAPS_DEPTHBIAS`（与物理 caps 求交）。
  - 宿主照原版 `D3D9DeviceEx`：
    - 建设备时按 `VK_EXT_depth_bias_control` 选表示方式：支持 float 表示就用 FLOAT、系数 1；
      否则用 least-representable（或 force-unorm），系数取深度目标的 R 值。
    - 宿主的深度目标总是 D32_SFLOAT（D16 与 fork 一样映射过去），所以 R 值固定按 D32_SFLOAT 算。
    - 每个 draw 设 `depthBiasConstant = DEPTHBIAS × 系数`；DXVK 在偏移非 0 时才启用。
- **按 FVF 缓存声明**（G5 发现：每次切 FVF 宿主都新建一个声明）：
  - 照原版 `m_fvfTable`，代理按 FVF 保留声明，设备在声明就在；SetFVF 命中时直接绑定。
  - 缓存最多 64 项，用私有引用，不会让设备循环引用自己。
  - 开发宿主只有 4 个声明槽位（原版没有这个限制）。创建时宿主返回 OUTOFVIDEOMEMORY，就放掉缓存里
    既没绑定、调用方也没持有的声明，再重试一次。r1 暴露了这个问题，见结果。
  - 新增 stderr 行 `D3D9 fvf-proxy:`（`warvk-d3d9-fvf-proxy/v1`）：cached、evictions。

- **extent fixture `--depth-bias`**（门的 ring 用例一起跑）：64×64、游戏的交换链（X8R8G8B8、D16）。
  - 先写一层 z=0.5 的底色，然后在同一深度画四条竖带，都不写深度：
    1. 偏移 0、LESS：失败，留底色（对照：相等深度过不了 LESS）；
    2. 偏移 −1e-4、LESS：通过；
    3. 偏移 +1e-4、LESS：失败；
    4. 偏移 +1e-4、GREATER：通过（证明正偏移是往远处推，而不只是"非 0"）。

## 10. 第六组：G6 有序状态与缓冲内容不等回复

### 问题

G5 之后远端路径能画游戏的缓冲，但每次 Unlock 的每一块、每次 draw 前的状态同步（effects、采样器、附加纹理阶段）
都是同步 `call`：先刷出暂存的 draw，再等宿主回复。游戏平均每帧约 52 次 Lock，每次至少一次管道往返；
而且 `call` 先刷出暂存 draw，固定功能批在 G5 的 ring 用例里只剩每批 1 个 draw（64 批）。

### 设计

- **只在异步批次档位**（`WARVK_D3D9_ASYNC_BATCH=1`，stream 档位都带它）生效；同步档位保持逐条等回复，作为严格对照。
- **连接 `enqueueOrdered`**：UploadBuffer、SetEffects、SetSamplerState、SetTextureStages 四种 op 像 Clear 和 draw 批一样
  直接进有序队列，不等回复；载荷在返回前已复制进队列。宿主拒绝在这个档位下是终止性的（与异步批次相同）：
  代理已经在本地做过同样的校验，宿主拒绝说明两边不一致。
- **NOOVERWRITE 内容可以越过暂存的 draw**：按 D3D9 的 Lock 约定，NOOVERWRITE 写的范围不会被已发出的 draw 读到，
  所以它先于这些 draw 到达宿主不影响结果；宿主的初始化前缀只会变大，已暂存 draw 的校验不受影响。
  DISCARD、普通 Lock 和三种状态仍然先刷出暂存的 draw（它们会改变暂存 draw 要用的数据或状态）。
- **代理**：Unlock 的每一块、draw 时的 effects/采样器/附加纹理阶段同步都走 `Device::ordered`；
  NOOVERWRITE 块带 passStaged。Reset 后重发状态仍用 `call`，在这个档位下它的失败同样是终止性的。
- 新增 stderr 行 `D3D9 ordered-async:`（`warvk-d3d9-ordered-async/v1`）：enabled、uploadsPublished、statesPublished、
  passedStaged、remoteSucceeded。

### 测试

- **连接 CPU 测试 `asyncOrderedState`**：
  - 非异步档位、未初始化、非有序 op、状态带 passStaged 都返回 INVALIDCALL，序号不动。
  - 暂存 1 个固定 draw 时，NOOVERWRITE 上传先发出，暂存数不变；改写调用方缓冲后，队列里的副本不变。
  - 再暂存 1 个 draw 后，DISCARD 上传先刷出 2 个 draw 的批，再发出自己；没有暂存时 NOOVERWRITE 不计越过。
  - 四条消息在没有任何回复的情况下入队（队列满 4 条），宿主顺序为 上传、批、上传、上传、状态。
  - 宿主拒绝、DEVICELOST、带载荷的成功、S_FALSE 四种回复都终止连接，之后的提交返回 DEVICELOST。
- **门 ring 用例**：
  - 同步档位：ordered-async 行全 0。
  - stream 档位：uploadsPublished 等于宿主的 uploads（每次上传都不等回复），statesPublished > 0，
    remoteSucceeded 等于两者之和；没有固定功能批时 passedStaged 为 0。
  - stream + 固定功能批：门里按 fixture 的执行顺序独立算出批的切分。暂存的 draw 只在 DISCARD 块、EndScene、
    满 20 个，以及 depth-bias 图里 DEPTHBIAS 变化时刷出。预期 20 批、69 个 draw、最大一批 6 个；NOOVERWRITE 块越过暂存 draw 140 次。
- **r2 暴露的约定**：原有的 fixed-rejection-stream 故障用例要求，异步档位下用 `call` 发出的 SetSamplerState 被宿主拒绝后连接仍可恢复。
  第一版按 op 判断回复是否异步，把这种拒绝也变成了终止。现在连接记下正在等回复的那次 `call` 的序号
  （`callSequence`，在发布之前写入），只有其他序号的有序 op 回复才按异步处理。CPU 测试补了这一项。

- 纹理上传（游戏加载时 2104 张托管纹理）仍是同步 `call`。
- 队列仍是 4 条；异步档位下宿主拒绝有序 op 是终止性的（代理已先做同样的校验）。
- 只在隔离桌面用夹具验证，没有接游戏，没有部署。

## 11. 第七组：G7 窗口自己改尺寸（WM_SIZE）

### 问题

§7 的回执发现，游戏改窗口尺寸时不调 Reset。WarVK fork 的窗口过程 hook 截获窗口模式的 WM_SIZE，
自己调 `ResetSwapChain` 到新的客户区尺寸，改写 War3 的分辨率字段，并且不把 WM_SIZE 转给 War3。
dev 代理没有这个 hook，所以远端路径上窗口变了尺寸以后，宿主只会按 §7 丢帧，要等应用自己 Reset，而游戏不会调 Reset。

### fork 的语义（读源码确认）

- `D3D9WindowProc`（`src/d3d9/d3d9_window.cpp`）：窗口模式、未最小化、客户区和后台缓冲尺寸不同时调 `ResetSwapChain`。
  不管尺寸变没变，WM_SIZE 都交给 DefWindowProc，War3 收不到。
- `D3D9DeviceEx::ResetSwapChain` 的行为：
  - 重建隐式交换链的后台缓冲和自动深度，并 `SetDepthStencilSurface`。
  - 非 Ex 设备再 `SetRenderTarget(0, 新后台缓冲)`，所以视口和剪裁矩形覆盖新目标。
  - 其余状态、绑定和 DEFAULT 池资源都保留，也不检查 losable 资源。
  - 应用手里的旧后台缓冲成为孤立表面，保持旧尺寸。
- 之后的 `TryOverrideWindowedClientSize` 和 `TryNotifyWindowedUiSizeChanged` 改写 Game.dll 内存里的分辨率字段。
  没有 Game.dll 时它们什么也不做。这一步属于留在 x86 的数据层，不在本组范围内。

### 设计

- **代理挂窗口过程**：每种 profile 都挂，和原版挂所有窗口模式交换链一致。
  - `DeviceWindowProc` 收到 WM_SIZE 时，只把客户区尺寸写进设备的原子变量，然后交给 DefWindowProc，不转给应用；
    其他消息照常转给原窗口过程。
  - 同一个窗口上，最后创建的设备拥有 hook。
  - 窗口先销毁时，表项在 WM_NCDESTROY 时删除。设备销毁时，如果之后没有别的子类化，就恢复原窗口过程。
- **由 owner 线程接手**：dev 路径的窗口线程和 API 线程是分开的，窗口线程里不能做 IPC。
  - `Device::followWindow` 在下一次与尺寸有关的调用里接手，并且只在场景外接手。
  - 这些调用是：GetBackBuffer/GetRenderTarget、Set/GetViewport、Set/GetScissorRect、BeginScene、Clear、
    状态块的 Create/Capture/Apply，以及 Present 之后。
  - 放在 Present 之后，是因为游戏的消息泵在两帧之间运行；在此之前画好的那一帧由呈现宿主按 §7 丢弃。
  - 应用自己的 Reset 成功后，丢弃还没接手的尺寸。
- **wire**：Reset op 的 `args[6]` 新增 `ResetKeepResources`。
  - 宿主只跳过"DEFAULT 池缓冲必须已释放"这一项检查，仍要求没有建了一半的资源、没有进行中的纹理上传；后端同样只跳过这一项。
  - 其余与 G4 的 Reset 相同：等 GPU 和帧退役，再重建颜色/深度目标和交换链尺寸。
  - 宿主的 draw 状态复用只在同一批之内，所以 reset 后的第一条 draw 一定重新绑定目标。
- **代理侧**：
  - 成功后换上新的后台缓冲 Surface，应用手里的旧对象保持旧尺寸；重新分配呈现回读缓冲。
  - 视口和剪裁矩形设为整个新目标（下一次 draw 会同步 effects），其余状态不动。
  - 宿主拒绝时（例如客户区又变了）保持旧尺寸，和原版 ResetSwapChain 失败时只记日志一样；下一个 WM_SIZE 会再试。
- **新计数**：
  - stderr 新行 `D3D9 window-proxy:`（`warvk-d3d9-window-proxy/v1`）：hooked、sizeMessages、resizes、refused。
  - 宿主的 `reset-host` 行新增 `windowResets`。

### 测试

- **wire**：`args[6]=1` 解出 keepResources；2、3、0x80000000 被拒绝。原来"args[6]=1 应被拒绝"的用例改成了上面的有效用例。
- **夹具 `--resize WxH`**：
  - 窗口过程放行 WM_WINDOWPOSCHANGED，于是会产生 WM_SIZE。
  - 第一阶段同 Reset 用例：8 张尺寸图、托管纹理、目标 alpha，`--present` 时再加 3 帧。
  - 改尺寸前的准备：设一组应保留的状态（ZFUNC、纹理、clip 四边形的流和 FVF），再设一组应被替换的视口和剪裁矩形；
    保留旧后台缓冲的引用。然后改窗口尺寸，并与窗口线程往返一次。
  - 13 项检查：
    - 应用没收到 WM_SIZE，设备正常；
    - 新后台缓冲的尺寸和格式正确，而且是新对象，旧对象保持旧尺寸；
    - 视口和剪裁矩形覆盖新目标；
    - ZFUNC、流、FVF、纹理绑定、采样器状态、阶段状态都保留。
  - 之后出两张图：清屏一张；用改尺寸前建的 clip 四边形画满新视口一张。然后在新尺寸上跑第二阶段。
- **门 `--resize`**：
  - game 组：1280×720 → 1902×963（窗口变大，游戏交换链），用例为 reference、remote、remote-stream（stream + 固定功能批）、present。
  - a8 组：257×129 → 64×64（缩小到 inline 尺寸），用例为 reference、remote、present。
  - 远端用例检查：
    - 宿主 resets = windowResets = 1，presentsSkipped 为 0，尺寸和格式正确，没有拒绝；
    - 代理 resizes 为 1，refused 为 0；
    - 回读分带数和呈现帧数精确。
  - 同组的离屏用例像素哈希一致。
  - Reset 用例补查两项：windowResets 为 0，代理没收到 WM_SIZE。

### 未覆盖

- 只验证了隔离桌面上的 WS_POPUP 窗口；没有接游戏 HWND，没有部署。
- **War3 分辨率字段的改写没有搬**（`TryOverrideWindowedClientSize`、`TryNotifyWindowedUiSizeChanged`）。
  它们改的是 Game.dll 内存，属于 S2 中留在 x86 的部分。接游戏时，要在代理接手 WM_SIZE 之后调用它们。
- fork 窗口过程的其他行为也没有搬：SC_MAXIMIZE/SC_RESTORE 交给 DefWindowProc（War3 自己的分支会退出进程）、
  ImGui 输入、帧历史快捷键、IME、WM_ACTIVATEAPP。
- **接手时机不同**：游戏里窗口线程就是渲染线程，fork 在消息分发的当下就重置；dev 路径要等下一次与尺寸有关的调用，
  场景中到达的 WM_SIZE 推迟到场景外。
- 状态块在改尺寸前录下的视口，缩小后可能超出目标；远端 profile 会拒绝（原版保存）。没有对照。
- 改尺寸之后应用再调 Reset 的组合没有对照（fork 的 ResetSwapChain 不维护 losable 计数）。
  应用拿旧后台缓冲做 GetRenderTargetData 时，fork 读孤立表面，代理会拒绝；这一点也没有对照。
- **呈现宿主偶发退出慢**：第二次出现，两次都在呈现用例上。宿主对象全部销毁、`wmain` 返回之后，进程退出超过 5 秒。
  两次都是同一构建重跑后通过。怀疑是共享 GPU 负载下驱动拆除变慢，原因没有查明。
