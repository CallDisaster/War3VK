# 可编排暴风雪 v1：2026-10-10 晨间交付

这轮已经做出能在真实魔兽中运行的第一版：地图作者可以用一组API，让小雪随时间发展成
大雪、暴雪，并控制风向、风速、阵风、雪雾和近地吹雪。不再只是渲染方案或接口空壳。

这是**开发预览候选，不是已发布稳定版**。已经通过下述限定功能与长循环门；仍需要作者
前台试听、画面与性能验收。没有自动覆盖玩家DLL，没有提交、推送、公开发布，
没有推进64位渲染进程，也没有扩Arena或阴影快照预算。

## 1. 玩家与地图作者能得到什么

- 可以同一个触发器启动原版音乐与风雪时间线，用关键帧编排“小雪→大雪→暴雪”。
- 六项独立控制：雪片强度、风向、风速、阵风、雪雾、近地吹雪。
- 室外世界区域可指定XY矩形、上下高度和边缘渐隐。
- 支持渐变、暂停/恢复、关闭/重新开启、跳到某个时间、销毁/重新创建。
- 时间线自动插值风向的最短方向；普通换风不会重算全部历史位移而突然搬走雪片。
- 未创建或未启用天气时，不运行天气渲染，不新建天气GPU资源；不另加天气启用环境变量。
- UI/YDWE action、call、define、常量、JASS包装与作者说明均已接上，不是仅DLL有命令。

首版一个天气实例、最多64个关键帧。天气是渲染效果，不改变移动、攻击、路径或伤害。
音乐继续用原版API播放；作者依据**实际选用的录音**手动标记转折点，并非自动识别高潮，
也不是音频设备采样时钟级同步。

### 新API：共12个

| 类别 | API | 作用 |
|---|---|---|
| 生命周期 | `WarVKCreateSnowWeather` | 按seed创建关闭的实例，返回整数句柄 |
| 生命周期 | `WarVKDestroyWeather` | 销毁实例 |
| 生命周期 | `WarVKIsWeatherAlive` | 查询句柄是否有效 |

| 参数/渐变 | `WarVKSetSnowWeatherTarget` | 六项参数渐变到目标，切手动模式 |
| 时间线编辑 | `WarVKClearWeatherKeyframes` | 按当前编辑条件清空关键帧 |
| 时间线编辑 | `WarVKAddSnowWeatherKeyframe` | 添加严格递增时间的关键帧 |

## 2. 代码实现和原项目的关系

数据只有一条责任链：JASS请求→严格生产解析→有界作者状态→每帧按值冻结→雪片/雪雾消费。
实时控制状态与渲染真正采用的输入分列，不能把一次成功setter当成GPU已经使用。

雪片采用固定16,384个GPU程序化实例，不逐片在CPU更新、不保存整张大地图粒子快照，
也不加入shadowCasters、Stage11或Arena。颜色与深度布局按既有DXVK机制恢复，
在途资源依旧由DXVK资源追踪保活，不用“等两帧应该就安全”代替GPU寿命。

雪雾/低空吹雪复用体积渲染算法，但单独持有Medium网格与历史，不覆盖作者普通雾配置。
天气临时分配失败局部拒绝并重试，避免因此永久关掉普通雾；已锁存device-lost不会被吞掉。
同资源键失败后等120个业务帧再试，换资源键可另试，不逐帧重复昂贵失败分配。

## 3. 这一夜真正找出的问题

**微小时间查询会被读成几秒。** 旧DLL可能返回 `9.73e-05`，魔兽1.27a的S2R不识别
科学计数法，会读成9.73。共享实数文本返回已改为最短普通十进制。
同脚本真实A/B中，旧候选3项失败，新候选35项/0失败；旧失败没有被追认。
这也修正了共同formatter的同类读方兼容问题，但不声称全部极端float在JASS中逐bit精确。

**体积网格与读取它的射线不是同一个坐标域。** 注入/历史是世界视口局部网格，
积分却曾用整张画面的UV读网格。最终候选把读取坐标改为已经用于深度重建的同一局部UV，
没有加浓度、改网格或扩预算。实际功能测试消费域为2560×1440深度图，
世界视口 `(0,47,2560,1081)`，证实这是当前场景确实存在的非全幅视口。
修正同时适用共享Froxel积分；不是声称它单独解释了全部近地吹雪观感。

**长循环测试错误地期待旧PostFX总开关已实现。** `stress-a` 有1083检查但70错误，
每阶段一次 `UnsupportedFeature=18`。没有临时打开能力mask或删除调用：新测试保留真实
调用，明确检查它被拒绝并清除错误。旧运行仍是失败；新的stress-b才是通过。

**测试也会误通过。** 红队实际构造“前三好帧遮住第四坏帧”“unknown资源回落成0”
“错误冻结参数被筛掉”三个反例，已补判据与回归。这是测试修正，不等同于实机发现了
上述三种生产故障。新证据按新契约单独重新采集。

近处雪片世界尺寸从2–6改为1–3，减少软大圆抢占主体；粒子数、alpha、浓度、预算不变。
限定静帧审查认为单位、血条和界面仍可读。近地吹雪单独开启仍比较轻，属于待美术调校，
没有用“命令已提交”代替最终视觉结论。

## 5. 内存和成本：哪些数字可以相信

2560×1440长循环中，同地图/设备/尺寸的当前账户：雪片所需深度副本15MiB、
天气体积图像/缓冲约36.46MiB，合计约51.46MiB；反复启停没有观察到同键当前账持续增长。
这些是当前天气自有账户，不含全部driver内部、pipeline/sampler与在途退役资源，
**不是整个游戏显存峰值，也不是显存只有这52MiB**。普通雾旧所有者的字节账为unknown，
没有用0代替；名义128MiB准入也不是整个天气GPU物理峰值承诺。

进程private中段/末开启/销毁尾段中位约1237.41/1254.97/1239.02MiB；尾段首末约
1254.98→1226.15MiB，有回落，但不能只凭6分多钟和这几个数认证无泄漏。

生产CPU微基准5场景各100万次：默认关闭probe批平均中位1.7ns、普通风推进189.2ns、
满64关键帧996.5ns；窗口内默认new/new[]为0。不是GPU成本、前台FPS、单调用p99、
aligned malloc或所有分配器的全局零分配证明。

## 6. 仍缺什么，下一步怎么做

1. 作者在前台结合实际音乐检查三段演出、可读性和强度；尤其调校低空吹雪。
2. 补移动/缩放相机的连续性、远距覆盖、透明物/战争迷雾/子scissor场景。
3. 同视角天气关闭/开启的前台帧耗时与GPU时间、p95/p99；当前隔离测试不冒充FPS基线。
4. 天气开启时真实换图、D3D9 Reset、连续改分辨率与GPU故障后的安全恢复/驻留峰值。
   原项目已有生命周期基础与本轮CPU清理，但这几项没有拿新天气候选实机认证。
5. 建筑积雪、屋檐挡雪、精确坡地贴合、地图大范围持久积雪延期；首版bottomZ是水平高度，
   不是自动跟随每处地面。屏幕深度遮挡不等于屋顶天气碰撞系统。

本轮判定：**可交付测试的功能候选已完成；产品发布验收未完成。**
完整项目长期重构、全场景收集和64位宿主不因本项完成而自动变成100%。
