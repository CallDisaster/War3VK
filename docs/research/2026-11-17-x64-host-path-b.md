# R3：x64 宿主走哪条路——继续用自己的 D3D9 后端（A），还是换成 DXVK 自己的 64 位 D3D9（B）

2026-11-17，Claude（Opus 5.5），只读调研。对应[帧时间计划](../plan/2026-11-17-x64-proxy-performance-plan.md) §6 的 R3 与 §4 的 D1。
没有构建、没有跑游戏/宿主/探针/门禁；只读了源码、文档，查了 GitHub 与微软文档。行号对应本次读到的工作区（有别人未提交的改动）。
每条结论标 **已核对**（读到代码或文档原文）或 **推断**（由已核对的事实推出，没有实测）。路径相对仓库根目录。

## 1. 结论

1. **现有后端缺的不是覆盖面，是执行方式。** 后端是一个有意收窄的 profile（§2.3），但 5.1-a 在四张图上没有碰到任何未实现入口。
   慢的原因在宿主每次上传、清除、建纹理、Present 都等 GPU 空，以及前端每帧一百多次同步往返。（已核对，见 §2、§6）
2. **本仓库的 `src/d3d9` 不能“去掉 War3 部分”构建成 64 位。** 没有可用的接缝：`d3d9_device.cpp` 51,064 行（上游 9,344 行），
   141 个 include 里 92 个是 War3/钩子；除开发诊断宏外没有条件编译；建设备时直接装 Game.dll 钩子；有按 x86 布局写死的 `static_assert`；
   根 `meson.build` 明确禁止宿主与 `enable_d3d9` 同时开。（已核对，§3）
   **所以现实的 B 是“在宿主里放一份与本仓库 `src/dxvk` 版本匹配的上游原版 `src/d3d9`”**，不是复用产品 DLL 的 D3D9。（推断）
3. **B 不能省掉 P2。** 同步点在前端和我们自己的记录协议上（记录、阶段标记、纹理分块、建资源、Present 都是 `call()`）。
   B 白送的是 P1（宿主不等 GPU）、P4 的大部分（D3D9 本身就是增量 setter）和宿主每 draw 的 CPU 开销。（已核对 + 推断，§5）
4. **B 的代价约是 A 的两倍，风险更大**：新线上格式、前端约一半重写、宿主分发重写、特效执行器改挂 CS 线程、5.1-e 生命周期重做、
   一批开发测试重写、像素门是否还能逐字节相同未知；还要长期维护第二份 D3D9。（推断，§5.3、§6）
5. **新发现：宿主的 Present 是整帧串行的，并且用 `Sleep(1)` 轮询，宿主从不提高计时器精度。**
   Present 前后各等一次 GPU 空，中间两处 `Sleep(1)` 轮询；Windows 10 2004 之后，没调用 `timeBeginPeriod` 的进程 `Sleep(1)` 不保证短于默认的 15.6 ms。
   代理模式 29–30 fps（约 34 ms）与“每帧两次 15.6 ms”或“144 Hz 垂直同步下每 5 个刷新出一帧（28.8 fps）”都对得上。
   这是 A 上最便宜的一刀，应先于 D1 量清楚。（代码已核对；对帧时间的影响是推断）
6. **建议：现在不换。** 先做 E0（Present 路径）+ P0 测量，同时让 Opus 做两个便宜的 B 探针（S1 编译、S2 像素对照），
   在 P2 动工之前按 §7 的标准定 D1。

### 2.2 线上操作（已核对）

### 2.3 “193 个未实现入口”是什么（已核对）

`tools/render_host/d3d9_unsupported.h` 给 11 个 COM 接口各写了一个“全部方法失败并记首次调用”的基类，带跟踪的方法正好 193 个（`:23-24` 的宏，`:26-257`）。
5.1-a 说的“193 个未实现入口”就是这组基类方法；前端子类覆盖了其中一部分。用一个临时脚本（不在仓库里）按类比对 `d3d9_proxy.cpp`、`d3d9_proxy_stateblock.h` 的覆盖：

| 接口 / 前端类 | 基类方法 | 前端实现 | 没实现的 |
|---|---|---|---|
| `IDirect3D9` / `Factory` | 14 | 13 | `RegisterSoftwareDevice` |
| `IDirect3DDevice9` / `Device` | 116 | 67 | 49 个，见下 |
| VB、IB | 各 10 | 各 4 | 私有数据、优先级、`PreLoad` |
| `IDirect3DTexture9` | 17 | 8 | 同上，加 `SetAutoGenFilterType`、`GenerateMipSubLevels`、`AddDirtyRect` |
| `IDirect3DSurface9`（独立 / 纹理层） | 13 | 4 / 5 | 同上，加 `GetDC`、`ReleaseDC`（独立表面还缺 `GetContainer`） |
| 着色器、声明、状态块、查询 | 2/2/3/4 | 全部 | — |

设备上没实现的 49 个：`EvictManagedResources`、`GetDisplayMode`、光标三件、附加交换链三件、`GetRasterStatus`、`SetDialogBoxMode`、Gamma 两件、
`CreateVolumeTexture`、`CreateCubeTexture`、`CreateRenderTarget`、`CreateDepthStencilSurface`、`UpdateSurface`、`UpdateTexture`、`GetFrontBufferData`、
`StretchRect`、`ColorFill`、`Set/GetDepthStencilSurface`、裁剪面四件、`ValidateDevice`、调色板四件、软件顶点处理两件、N-Patch 两件、
`DrawIndexedPrimitiveUP`、`ProcessVertices`、VS/PS 的 I/B 常量八件、`DrawRectPatch`、`DrawTriPatch`、`DeletePatch`。
（5.1-d 的 d1 轮就是被 `GetDepthStencilSurface` 未实现挡住的，后来改成读渲染状态判定。）

### 2.4 “实现了”的也是收窄的 profile（已核对）

- 资源表：缓冲 8 个、着色器各 4 个、声明 4 个、浮点常量 32 个（`dxvk_core/d3d9_backend.h:44-53`）；单个缓冲 ≤ 1 MiB（`d3d9_wire.h:17`）。
- 纹理：只有 2D、边长 ≤ 1024、11 级以内，格式只认 32/16/8 位常见色格式与 DXT1–5（`d3d9_texture_wire.h:10-20`），不做格式转换（`d3d9_backend.cpp:1386-1388`）。
- 着色器：只收 SM 3.0（`d3d9_backend.cpp:1482-1483`），不收 I/B 常量、VS 采样器，PS 只到采样器 0–7、只写一个颜色输出（`:1489-1495`）。
- 顶点输入：只有流 0（`d3d9_declaration_wire.h:16`）、16 位索引（`d3d9_backend.cpp:1612,1847`），没有实例化。
- 渲染状态：模板、sRGB 写只接受 FALSE（`d3d9_proxy.cpp:1784`）；不在表里的渲染状态返回 `E_NOTIMPL`（`:1787`）；渲染目标只能是后备缓冲（`:1559`）。
- 固定管线：顶点混合、裁剪面必须为 0（`d3d9_ff_state.h:53-54`），不收 BUMPENVMAP（`:62-63`），投影纹理坐标的除法未做（`:70`），最多 8 盏灯（`:92`）。
- 索引两端各校验一遍：x86 前端读回 IB 内容逐个索引核对（`d3d9_proxy.cpp:1900-1905`），宿主再逐个核对一遍（`d3d9_backend.cpp:1667-1675`）。

War3 本身用到的面很窄（两个 VB、一个 IB、没有着色器，见 `d3d9_backend.h:46-48` 的注释），所以这些限制在四张图上都没响。
没有量过的是：自定义地图的大贴图（> 1024）、第三方插件直接调 D3D9 的情况（推断：A 下每遇到一种都要补后端）。

### 2.5 固定管线模拟：与 DXVK 用的是同一个生成器（已核对）

- 宿主编译的就是 `src/d3d9/d3d9_fixed_function.cpp`（`dxvk_core/meson.build:103`），着色器键来自两边共用的模板
  `src/d3d9/d3d9_fixed_function_keys.h:124,219`（产品设备在 `d3d9_device.cpp:39601,39746` 用同一份），每阶段一个 `D3D9FFShader`（`d3d9_backend.cpp:1920-1922`）。
- 区别在状态怎么来：前端把固定管线状态整包放进每个 draw（`d3d9_ff_state.h:29-45` 的 `FixedFunctionState`），宿主每个 draw 重建键（`d3d9_backend.cpp:1731-1737`）、
  重填常量（`:1760-1775`），没有脏标记；顶点混合固定为关（`:1735`）。DXVK 的设备按脏标记只在变化时重建（推断，未逐行核对上游）。

## 3. `src/d3d9` 能不能在宿主里构建成原版 64 位

上游 DXVK 每个版本都出 64 位 `d3d9.dll`；挡住我们的是这个分支自己的改动：

| 障碍 | 位置 | 说明 |
|---|---|---|
| 构建策略明文禁止 | `meson.build:8-10`、`tools/render_host/dxvk_core/meson.build:1-12` | 宿主要求 `enable_d3d9=false`，理由写的是“x86 game hooks are not portable”（已核对） |
| 一个 DLL、没有开关 | `src/d3d9/meson.build:40-252`（源码表把 `jass/`、`war3/` 全部列进去）、`:667-678`（唯一的 `shared_library`）、`:583-654`（只有开发诊断选项） | 没有“只编 D3D9”的目标或选项（已核对） |
| 设备本体与 War3 交织 | `src/d3d9/d3d9_device.cpp`：141 个 include 里 92 个是 War3/钩子；“war3/War3”出现 8,188 次；条件编译只有 `WARVK_D3D9_MIGRATION_CENSUS_DEV`（55 处）等开发宏。`d3d9_device.h:15,53-73,107-108` 头文件本身就 include War3 模块 | 约 4.2 万行 War3 逻辑写在设备里（51,064 − 9,344，推断为主要是 War3 代码） |
| 假定在游戏进程里 | `src/d3d9/d3d9_interface.cpp:483-485`（建设备后立即 `War3Hook::InstallHooks`）、`war3/memory/war3_storm_hook.cpp`、`war3_tlsf_pool.cpp` 等 | Game.dll 钩子、Storm 内存、TLSF 池都在同一 DLL 里（已核对文件存在与调用点） |
| 按 x86 布局写死 | `jass/war3_game_struct.h:2759-2766`、`war3/native/war3_native_renderer.h:418-421,1564`（结构体大小断言，含指针成员）、`war3/memory/war3_mdl_trace.cpp:116`（`sizeof(void*)==4`） | 64 位下直接编不过（推断：含指针的结构在 x64 变大） |
| x86 专用代码 | `war3/hooks/war3_jass_native_invoke_x86.cpp:6-46`、`war3/reimpl/war3_render_queue.h:847-849` | 有 `#if` 保护，64 位下编得过但功能变成空（已核对） |

2026-10-11 的边界设计（`docs/plan/2026-10-11-x64-d3d9-migration-boundary.md:214-223`）当时就写了：要先把 Game.dll 读取/钩子与 D3D9/DXVK 语义切开，
不能关断言、不能把游戏指针扩成 64 位、不能散布空桩。后来实际做法是只抽出能共用的几块（FF 生成器与键、DXSO 缓存、options/format/adapter），
其余在宿主里写了一个收窄的后端——这就是现在的 A。（已核对）

**所以 B 的可行形态是“B-原版”**：取与本仓库 `src/dxvk` 对应的上游 `src/d3d9` 原样放进宿主（不进产品 DLL），由宿主的解码线程当它的“应用线程”。要先解决：

1. **版本对齐。** 本仓库没有记录基于哪个上游版本（`git log` 从“重新初始化公开仓库”开始）。`src/dxvk` 带 `dxvk_descriptor_heap`、`dxvk_shader_ir`、`dxbc-spirv`，
   像是 2.7 之后的上游（推断）；`src/dxvk` 里只有两个文件带 War3/WarVK 标记（已核对），`src/dxso` 多了 `dxso_shader_module_cache.*`（已核对）。没标记的改动有多少不知道。
2. **同名符号与 ODR。** 宿主已经编进了本仓库的 `d3d9_fixed_function.cpp`、`d3d9_options.cpp`、`d3d9_adapter.cpp`、`d3d9_format.cpp`、`d3d9_monitor.cpp`、`d3d9_names.cpp`
   （`dxvk_core/meson.build:103-107`），阴影 pass 与体积光 include 了分支的 `d3d9_device.h`（`src/d3d9/d3d9_war3_shadow.cpp:70`、`d3d9_war3_volumetric_light.cpp:2`），
   虽然只在一个构造函数里用到 `D3D9DeviceEx*`（`d3d9_war3_shadow.cpp:2185`）。原版 `D3D9DeviceEx` 进同一个二进制就是两份不同定义：
   要么去掉这两个 include（动玩家在用的源码），要么把原版 D3D9 与执行器一起放进宿主里的一个独立模块（推断）。
3. **分支对 D3D9 基本语义的改动。** 进程内画面来自分支的 D3D9，不是上游；分支在非 War3 文件里改过哪些基础行为（窗口 `WM_SIZE` 钩子、
   `AddDirtyRect` 兼容、DPI 等）需要逐文件对比，现在不知道。

## 4. 特效执行器现在怎么接、换到 `D3D9DeviceEx` 上怎么接

### 4.1 现在（A）（已核对）

- 记录：`FrameScene` 进场景包/阴影包（`dxvk_core/d3d9_host_main.cpp:571-579`）；`StageMarker` 是 BeforeUi 且有活时调 `runBeforeUi`（`:580-611`）；
  `SessionReset` 清场景与内容仓库（`:615-623`）；draw 上的 `ShadowCaster` 记录在 draw 录制后交给 `addShadowCaster`（`:193-220`）。
- `runBeforeUi`（`d3d9_backend.cpp:2072-2120`）：流模式下用当前打开的命令列表，`context->beginExternalRendering()`（`:2090`）拿到列表，
  先跑阴影 pass、再按 SSAO → 雪 → AA → Bloom 跑执行器（`:2093-2099`、`before_ui_effects.h:30-52`），读写后端自己的 `colorView`/`depthView`，设备纪元用 `targetGeneration`。
- 投射体合同（`shadow_before_ui.h:23-42`、`d3d9_backend.cpp:2016-2067`）：draw 的 VB/IB 的 `DxvkBuffer`、声明元素、流偏移与步长、动态缓冲在 draw 时的字节
  （动态 VB 取 `mapPtr`，IB 取后端留的 CPU 副本）、alpha 测试纹理的 view。前提是“draw 之后、下一次上传之前调用”。

### 4.2 换到 `D3D9DeviceEx` 上（B）

- **插入点有现成的公开接口。** 分支的 `D3D9DeviceEx::InjectCs`/`InjectCsChunk` 是公开成员（`src/d3d9/d3d9_device.h:1373-1382`，位于 `:430` 的 `public:` 与 `:1392` 的 `private:` 之间），
  `EmitCs` 是私有的（`:1393`）；上游 master 同样把 `InjectCs`、`AllocCsChunk`、`GetDXVKDevice`、`GetRawState` 设为公开（GitHub 原文）。（已核对）
  BeforeUi 就是在解码线程上 `InjectCs` 一个闭包：闭包在 CS 线程里 `ctx->beginExternalRendering()`，再跑阴影 pass 与执行器——
  分支进程内设备就是这么接的（`d3d9_device.cpp:18445,18768,18998` 在 CS 里调 `beginExternalRendering`）。（已核对接口；做法是推断）
- **颜色/深度 view** 要在解码线程上从当前 RT0、深度表面取 `D3D9CommonTexture` 的 view，按值捕获进闭包（推断）。
- **执行器的 CPU 状态要搬到 CS 线程。** 现在它们属于宿主的单一所有者线程；B 下记录在解码线程到达，要按值拷进闭包，执行器只在 CS 线程上碰（推断）。
- **投射体合同要重做。** 解码线程在转发 draw 之后，用 `GetStreamSource`/`GetIndices`/`GetVertexDeclaration`/`GetTexture` 拿到对象，再转成原版 D3D9 的具体类取 `DxvkBuffer` 与 view
  （要求原版 D3D9 静态编进同一模块）；“draw 时的动态字节”最简单是宿主自己留一份最近一次上传的 CPU 副本（宿主收到了每一次上传的字节），和现在 IB 的做法一样（推断）。
- **纪元**：设备 `Reset`、会话重置由宿主在转发前截住，与现在相同（推断）。
- **呈现**：原版交换链要画到游戏进程的窗口。现在的后端已经跨进程往游戏窗口 Present（5.1-a 已核对），但 DXVK D3D9 交换链会给窗口挂窗口过程
  （`src/d3d9/d3d9_window.cpp:259-272`、`d3d9_swapchain.cpp:245`），对别的进程的窗口 `SetWindowLongPtr` 会失败；失败时的行为、全屏与焦点逻辑要实测（推断）。
  Remix 的服务端也是跨进程画到客户端窗口（其 README 原文），说明路是通的，但它的 DXVK 可能带了补丁（不知道）。
- **工作量**：适配层约 400–800 行新代码，外加 CS 线程上的所有权与生命周期设计（Fable）；体积光、描边跟着阴影 pass 走同一个口子（推断）。

## 5. B 白送什么、要付什么

### 5.1 白送（已核对的是我们后端现在的等待点；DXVK 一侧的机制已核对存在，效果是推断）

| 现在后端的做法 | DXVK D3D9 的做法 |
|---|---|
| 静态缓冲上传：先 `settle()` 等 GPU 空，再单独提交并等完成（`d3d9_backend.cpp:1355-1361`）；无 flag 的动态缓冲上传也先 `settle()`（`:1348-1350`） | 暂存缓冲 `m_stagingBuffer`（`d3d9_device.h:2231`）加 CS 线程有序拷贝，不等 GPU |
| 纹理上传：`settle()` 后单独提交并等完成（`:1417,1426`）；建纹理也等（`:1395-1397`）；改 LOD 等（`:1438`） | 同上；托管纹理在用到时上传 |
| 清除（含整屏 Clear）：`begin()` 里 `settle()`，提交后再等（`:1538,1562`，`clear()` 走同一路 `:1524-1527`） | 记进 CS 流，延迟清除 |
| 每次提交都等提交线程回执（`:704`） | 只入队 |
| Present：前后各 `settle()`，两处 `Sleep(1)` 轮询（`:2256-2257,2309-2323,671-679`） | 异步呈现，帧延迟上限 |
| 销毁资源：`settle()`（`:2355`） | 引用计数加 DXVK 的使用跟踪 |
| 提交策略：每次上传/清除各一次提交，每帧约 75 次 | `ConsiderFlush` 按量与按帧（`d3d9_device.h:1217`） |
| 每 draw 重建 FF 键、重填常量、逐个索引校验 | 脏标记；不逐个校验索引 |
| 只有 DISCARD 在流模式下换存储（`:1341-1347`） | 动态缓冲 `DiscardMapSlice`（`d3d9_common_buffer.h:154`） |
| 收窄 profile（§2.4） | 完整 D3D9：查询、状态块、RT/DS、`StretchRect`、立方体/体纹理、全部格式 |
| 解码、校验、录制、提交都在一个所有者线程 | 解码（应用）线程 + CS 线程 + 提交线程（`d3d9_device.h:2298`） |

### 5.2 不白送：P2

前端的同步点是我们自己的：记录和阶段标记每条都是 `call()`（`tools/render_host/d3d9_connection.h:486-499`），纹理分块每块一次往返（`d3d9_proxy.cpp:923-940`），
`ClearRegions` 走 `call()`（`:1842`），建资源同步，Present 同步（`:420-429`）。只有 draw 批、四种有序状态与上传、整屏 Clear 是异步的（`d3d9_connection.h:435-437,1122-1129`）。
换成哪种宿主都还在。（已核对）B 的新线上格式必须从第一天就按异步设计，P2 的大部分工作会并进 B 的线上格式设计里，而不是另做一遍。（推断）

顺带核对 Remix（`bridge-remix` 的 `bridge.conf`，原文默认值）：`sendCreateFunctionServerResponses=True`（建资源默认同步）、`presentSemaphoreMaxFrames=3`、
`sendReadOnlyCalls=False`（Get 类在客户端答）、`commandBatchingEnabled=False`（注明“尚未实现”）、`clientChannelMemSize=96MB`（映射进 32 位进程）。
**计划 §5.2 写的“参考 Remix 的 `presentSemaphoreMaxFrames=1`”不是 Remix 的默认值，默认是 3。**（已核对）Remix 的桥接开销没有找到公开实测数字。

## 6. A 要多少才能追平

### 6.1 Present 路径（新发现，先做）

`D3D9Backend::present()`（`d3d9_backend.cpp:2221-2349`）每帧：`settle()` 等 GPU 空 → `waitPresentRetired`（`:666-683`，`Sleep(1)` 轮询）→ acquire → blit →
`submit(false)`（等提交线程回执，`:704`）→ `presentImage` → `Sleep(1)` 轮询呈现结果（`:2309-2319`）→ 再 `settle()` → 再 `waitPresentRetired`。前端的 Present 是同步 `call()`，
游戏线程等这一切做完才开始下一帧，CPU 与 GPU 跨帧没有重叠。（已核对）

宿主代码里没有 `timeBeginPeriod`/`NtSetTimerResolution`；DXVK 只在 `dxvk::Sleep::sleep` 第一次被调用时提高精度（`src/util/util_sleep.cpp:23-58,76-77`），宿主平时不走这里（推断）。
微软文档：Windows 10 2004 起 `timeBeginPeriod` 不再全局生效，没调用的进程不保证高于默认精度；Windows 11 对不可见进程也不保证。（已核对）
所以宿主每个 `Sleep(1)` 可能是 15.6 ms。代理模式 Lost Temple 29.1、EchoIsles 30.3 fps，接近“每帧两次 15.6 ms”（32 fps），也接近“144 Hz 垂直同步下 5 个刷新一帧”（28.8 fps；
前端把 `DEFAULT` 间隔折成 `ONE`，`d3d9_wire.h:49-50`；进程内 136/134 fps 像是 144 Hz 封顶）。两种解释都指向这条串行路径，哪种为主要量（推断）。

## 7. 建议与决策标准

**建议：D1 暂定 A，B 留作备选；在 P2 动工之前定死。** 理由：P2 两条路都要做，且同步点在我们自己的协议里；最可疑的瓶颈（§6.1）在 A 上改动小；
B 的工程量约为两倍，并且有两个现在回答不了的大问题（像素是否相同、跨进程窗口）。

| 先做的便宜实验 | 回答什么 | 谁 | 成本 |
|---|---|---|---|
| **E0** Present 路径：宿主提精度、轮询改等事件，同轮 A/B 一张图 | 34 ms 里有多少是 `Sleep(1)`/串行呈现 | Opus | 半天到一天 |
| **P0**（计划已有） | 宿主等 GPU、处理、空等各占多少；前端同步等待按操作分布 | Opus | 计划内 |
| **S1** B 编译探针：确定与 `src/dxvk` 最接近的上游版本（逐文件比对）；在新构建目录里把该版本的上游 `src/d3d9` 编成 x64 静态库，链本仓库的 `src/dxvk`/`dxso`/`util`；只编译不运行，数错误 | B-原版要补多少核心 API 差异 | Opus | 1–2 天 |
| **S2** 像素对照：把现有 D3D9 COM 夹具里不带记录的基础帧编成 x64、进程内直连原版 D3D9（不经 IPC），与 x86 分支进程内的同帧比哈希 | B 下门禁能否逐字节照旧；B 在无 IPC 时的成本下限 | Opus 做，有差异交 Fable 判读 | 1–2 天，要跑 GPU（门禁串行） |
| **S3** 覆盖普查：用现成的普查构建（`warvk_d3d9_migration_census_dev`）跑更多自定义地图 | profile 外的用法（>1024 纹理、RT、`StretchRect` 等）在真实内容里有多常见 | Opus | 每图一轮，游戏串行 |

**换到 B 的条件（满足两条以上再换）：**

1. E0 + P1 原型之后，代理模式仍明显高于进程内 1.5 倍，且 P0 显示剩下的大头在宿主录制/每 draw CPU，而不是前端同步。
2. S3 显示真实地图常用 profile 外的功能，补后端的清单很长。
3. S2 显示原版 D3D9 的基础画面与分支进程内逐字节相同（门禁可以照旧），且 S1 显示核心 API 差异小。
4. 作者接受长期维护第二份 D3D9，并接受产品里两种模式由两份不同的 D3D9 出图。

**留在 A 的条件**：E0/P1 之后帧时间进入 1.5 倍以内或接近，或者 S2 显示像素不同而作者不接受容差门。

## 给计划的结论

1. D1 建议先定 A；B 不在本周动工。B 的两个探针（S1、S2）和 S3 普查 Opus 本周可以做，不需要 Fable。
2. 在 P1 之前加一项 **E0：宿主 Present 路径**（计时器精度、`Sleep(1)` 轮询、Present 前后的 `settle()`）。前两项是调度参数，Opus 可做；
   去掉 `settle()`、加 Present 信用碰生命周期，归 Fable。
3. 计划 §5.2 P2 里“参考 Remix 的 `presentSemaphoreMaxFrames=1`”改成：Remix 默认 3，建资源默认同步（`sendCreateFunctionServerResponses=True`）。
4. P2 与 D1 无关的说法成立；但 B 的线上格式会吞掉 P2 的大部分，所以 **D1 要在 P2 实现开始之前定**，否则 P2 可能做两遍。P1 只在 A 下做。
5. 选 B 时的现实形态是“上游原版 `src/d3d9` 放进宿主”，不是“产品 `src/d3d9` 去掉 War3 部分”；后者没有接缝，要拆 4 万多行。
6. 不论 A、B：x86 侧的逐索引校验（`d3d9_proxy.cpp:1900-1905`）与宿主侧重复（`d3d9_backend.cpp:1667-1675`），至少去掉一端。

## 还不知道的

- 本仓库 `src/dxvk` 基于哪个上游版本、没有标记的改动有多少（S1 回答）。
- 原版 D3D9 与分支进程内 D3D9 在门禁夹具上是否逐字节相同（S2 回答）；分支在非 War3 的 D3D9 文件里改过哪些基础语义。
- 34 ms 的拆分：`Sleep(1)` 粒度、垂直同步、GPU 等待、同步往返各占多少（E0、P0 回答）；测试机显示器刷新率与进程内是否被垂直同步封顶。
- 原版 D3D9 交换链对别的进程的窗口挂窗口过程失败时怎么表现；Remix 的 DXVK 是否为此打过补丁。
- 自定义地图、第三方插件是否用到 profile 外的 D3D9 功能（S3 回答）。
- 数据层的投射体判定是否需要 x86 侧的 IB 内容（决定 B 下能否去掉 x86 的 IB 副本）。
- Remix 桥接的实测开销：没有找到公开数字。
