# WarVK 1.30.00 发布范围与证据

发布日期：2026-11-22。用户授权：“请你着手准备发布到Github作为我们的骄傲版本吧。”（正式版、直接进
main、画面取证默认关闭）；“请你将新版本锁定位v1.30版本，本轮更新的64位迁移实在是太大了直接进行大版本号
的更新。”；首页性能报告：“直接对比开启光影后我们的电脑配置下的性能和原版没开的性能。”；对照的补充：“我建议把原版的
OpenGL去掉帧率限制再进行测试，仅去掉帧率限制。”推送、打标签和公开前另行取得用户的明确同意。

## 范围

收入（玩家包默认生效）：

- **64 位渲染。** x86 `d3d9.dll` 在 `war3.exe` 里运行、旁边有 `WarVK\x64\warvk-d3d9-front.dll` 和
  `warvk-d3d9-host.exe` 时自动启用（`war3_proxy_auto.cpp`），传输配置等于门禁的
  `product-async-delta`；没有 `WarVK\x64`、不是 `war3.exe`、32 位系统或 `WARVK_D3D9_AUTO=0` 时
  不启用；宿主起不来时退回进程内并写 `fallback.txt`。前端是 11-18 冻结的 f8
  （`14E995B6…9AB4`，未剥离），宿主在冻结源码里用 `run_render_host_candidate_build.py` 构建。
- **画面取证默认关闭。** 自动模式写入 `WARVK_D3D9_EVIDENCE=0`（环境里已有的值优先）；宿主的记录器
  此时不建帧环、不做撕裂审计。玩家包里的 `WarVK_EvidenceStart.cmd`（纯 ASCII）设为 1 后启动游戏。
- 阴影按类别设置、贴地部分不投影、预算三项根治（f14/f16）；去掉魔兽烘焙的静态阴影；太阳圆盘与
  一天的光色（j1）；战役过场与进图的白模（j2）；水面 v2–v4（k1–k5，含 Gemini 11-20 的水面 v4、
  迷雾与粒子修复）；地狱火发光；主菜单退出崩溃（模块固定，f9）。
- 版本号 1.30.00：产品、版本资源、JAPI 字符串、打包器、配置审计、测试。

不变：Shader API 1.2.0、JASS wire `warvk:v1`、JASS 命令集合、显卡/驱动下限。作者包除版本号
说明与 `WarVK/README.md` 的“1.30.00 作者须知”外与 1.22.03 相同。

不收入：两个异步资源开关（`WARVK_D3D9_ASYNC_DESTROY`、`WARVK_D3D9_ASYNC_CREATE_TEXTURE`，默认关）、
原版模型自动点光接管、未验收的剔除实验。

## 性能（首页报告的出处）

测试工具 `AutoTest/run_v130_vanilla_compare.py`，运行 `v130-vanilla-compare-20261122-r5`
（2026-11-22 02:22–03:20，24 次运行全部通过）。同一台机器（Ryzen 5 5600X、32 GB、RTX 4060 Ti 16 GB 驱动
621.01、Windows 11 Pro），沙盒实例、隔离桌面、窗口 1902×963；每张图四种方式轮流跑两轮，第二轮倒序。帧率按
内核的 Present 事件（DxgKrnl，事件 184）计，Lost Temple / EchoIsles 取第 50–85 秒，《生与死》取第 135–165 秒；
内存是测量段结束后对游戏进程低 2 GiB 的扫描（VirtualAlloc 还能分出去的空间）。

《生与死》808 / 807 / 481 / 1048。64 位比单进程多 523–567 MiB，比原版 OpenGL 多 226–240 MiB。

**原版的两层帧率限制，以及“去上限”具体改了什么。** 采样原版的主线程（`x86_sampler` 的等待版本）：

1. 75% 的时间停在 `Game.dll` 主循环（调度器在 `0x6F05F7AD` 附近）的 `WaitForSingleObject(句柄, 到期 − GetTickCount())`
   里，超时是 1 ms。`GetTickCount` 按系统时钟 15.625 ms 一跳，所以每秒最多 64 次。只申请 1 ms 计时器
   （`timeBeginPeriod(1)`，并让 Windows 在窗口不可见时也照办）仍是 64.0 帧（`v130-uncapped-check-20261122-r2`…`r7`）。
2. 把 `Game.dll` 导入表里 `GetTickCount` 的指针换成同进程的 `winmm!timeGetTime` 之后是 144.0 帧（`r9`）；此时 57%
   的时间在 NVIDIA OpenGL 驱动的 `DrvPresentBuffers → WaitForVerticalBlankEvent`：游戏从不设置交换间隔，
   OpenGL 默认等垂直同步（内核记录的 `FlipInterval` 仍是 0，等待在驱动里）。
3. 再把 `wglSwapLayerBuffers` 的导入指针换成一个 76 字节的小段代码：第一次呈现时在游戏自己的渲染线程上调用
   `wglSwapIntervalEXT(0)`，之后总是跳回真正的 `wglSwapLayerBuffers`。Lost Temple 610–717 帧（`r11` 与正式运行）。

这三处只在测试实例的游戏进程里做（`run_x64_game_proxy_probe.lift_frame_cap`，动作 `uncap=1`，只允许原版臂），
写入的只有两个导入指针（各自先核对原值）和小段代码所在的一页；不加载任何 DLL，游戏的 `maxfps` 设置
（本机 1000）不动。WarVK 自身默认不等垂直同步，它的 DXVK 也会提高游戏进程的计时精度。

## 未验证与已知边界

- **这个正式构建没有玩家实机验收。** 只在一块 NVIDIA RTX 4060 Ti 上做了隔离自动化测试。
- 真实桌面上的启动、Alt-Tab、拖动改窗口大小、最小化后恢复、运行中改系统缩放、全屏，以及 AMD /
  Intel 显卡、联机，都没有自动化覆盖。隔离桌面上原版的 Direct3D 方式起不来，所以性能对照里的原版是
  OpenGL 方式。
- 64 位方式画面比单进程略亮（f7 起就有，原因未查）；阴影偶发撕裂原因未查；游戏运行中宿主出错时游戏
  退出，不能中途切回单进程；MSAA 请保持关闭。
- 水面风格 0 比 k4 多约 150 µs 的原因未查；傍晚和夜里的 v4 水面、单进程方式下的迷雾没有专项测试。
- 首次进图的阴影着色器冷编译（测试机 3–10 秒）。
- 文件没有数字签名。
