**A/B 两臂比的不是同一件事。** 代理模式的宿主用 FIFO（垂直同步）出帧，进程内是 IMMEDIATE；显示器 59 Hz，代理臂的 29–30 fps 正好是半刷新率
（日志核对过）。原因是进程内 `InitialReset` 调 `War3ForceImmediatePresent`，代理模式的工厂没有。11-17 已在
`src/d3d9/war3/platform/war3_proxy_mode.cpp` 的 `CreateDevice` 补上同一条规则（只在代理模式生效），P0 用新 DLL 重测。
所以下面的“原因”都要在出帧方式一致之后重新称量。

已经确定的（代码或数据核对过）：

1. **同步往返的 82–90% 是纹理区域更新。** 每次 `UnlockRect` 发 Begin、每 64 KiB 一块、Commit，三条都等回答。Present、帧记录、阶段标记合计每帧约 9 次。
2. **主机几乎在每个非绘制操作上把 GPU 等空。** 每次纹理更新最多两次整体排空，并把当前流列表切断；每帧 68 次提交里约 54 次由此而来。
   根源是一块共享的 `owner.staging` 和“每个非绘制操作之后都 settle”的约定（[主机等 GPU](../research/2026-11-17-x64-host-gpu-waits.md)）。
3. **宿主的 Present 全程串行。** 前后都等 GPU 空闲，并用 `Sleep(1)` 轮询两次；宿主没有调高计时器精度。
4. **每次固定管线绘制带 3,180 B 全量状态**，占环流量 49–63%；其中 1,024 B 着色器常量恒为零（War3 不用着色器），未启用灯位约 624 B 也是零。
   宿主每条都重新校验、重算顶点常量、重新查管线（[状态增量](../research/2026-11-17-x64-state-delta.md)）。
5. **DISCARD 时主机拷贝整个旧内容**（每次 333–378 KB；生与死每帧 3.85 MB），D3D9 不需要。
6. **两端的等待与唤醒每帧多花约 1–9 ms**：x86 每次同步只自旋一次（约 40–60 µs），主机每执行完一条记录就叫醒它；宿主以低于正常优先级启动
   （[调度](../research/2026-11-17-x64-scheduling.md)）。CPU 是 5600X，没有大小核，电源节流影响应该不大。
7. **上传窗口和不留副本不是瓶颈。** 窗口从不等待，只分配过 3 块；回主机取旧内容每局约 62 次。
8. **生与死的资源表用到 96%**：活纹理峰值 15,734 / 16,384，不是反复创建（句柄只复用 62 次）。切默认前必须放大。
9. **x86 静态 TLS**：模板 3.22 MiB，代理模式约 145 MiB、进程内约 245 MiB；1.22.x 的 GCC 构建没有这笔开销（[静态 TLS](../research/2026-11-17-x64-static-tls.md)）。
   注意：代理模式线程少（约 45 对 76），5.2 测到的 +566–620 MiB 里约 100 MiB 来自少复制的 TLS 模板，GCC 构建的正式版拿不到这一部分。
   向玩家承诺的收益要按正式版的工具链重新量。
10. **x86 还有可省的大块**（[地址空间余量](../research/2026-11-17-x64-x86-va-headroom.md)）：生与死上 TLSF 扩展池攥着 82.5 MiB 还不回去（两种模式都有）；
    产品 DLL 映像里 56.6 MiB 是静态数组；24 MiB 的渲染队列跟踪表（推断）偏大；探针只扫了低 2 GiB。

**P0 首批数据（带仪表、短窗口，经 [独立复核](../research/2026-11-17-x64-performance-readonly-takeover-review.md) 重算）：**
出帧方式改成 IMMEDIATE 后，Lost Temple 游戏内窗口仍是每帧 47.3 ms（约 21 fps），EchoIsles 43.2 ms。
x86 同步等待墙钟每帧 41.6 / 37.2 ms，其中纹理 Unlock 占 29.6 / 24.9 ms；环满等待为 0。
Lost Temple 每帧 32 次纹理更新，全是 16×16 A8R8G8B8、每张每帧一次，合计约 67 KB，却换来约 97 次同步往返和 64 次宿主提交。
所以垂直同步让旧 A/B 不公平，但解释不了主要差距；第一瓶颈就是“小更新、重同步”。
这些计时是墙钟时间，x86 等待、宿主等待、“GPU”等待互相嵌套，不能相加；名为 GPU 的几项包含资源退休等 CPU 路径。
P0 的生与死一轮停在“按下任意键以继续”，没有进游戏，数据作废重跑；EchoIsles 退出时前端等宿主约 5.05 s 超时，待查。

- 三张图每帧 23–33 次 16×16 整层更新；建这些纹理的是 Game.dll+0xF0408 的通用路径，查不出是哪个功能。
- **约 1.01 s 的周期性卡帧**，正好等于 `RecheckMs=1000`，出现在纹理分块的同步等待上：推断有一处唤醒丢失。这是 p99 的大头，下一步先定位。
- **生与死卡在宿主 CPU 路径**：每帧阴影投射体拷贝 36.5 ms、DISCARD 搬旧内容 30.2 ms（墙钟）。16 MiB 环让环满等待归零，但等待挪到了阶段标记上，帧率只从 6.75 到 8.26。
- 宿主在 `wmain` 返回后还要 3.5–4.6 s 才退出，导致 EchoIsles 和生与死的前端退出超时；原因未知。

还不知道的：唤醒丢在哪一侧；宿主退出慢在哪；投射体拷贝和 DISCARD 是否在读写合并内存；生与死游戏内去掉这两项后还剩什么。

## 2. 目标

- **帧时间**：代理模式中位帧时间不超过进程内的 1.5 倍，p99 不超过 2 倍（“待作者确认”第 1 条，仍未确认）。两臂必须用同一出帧方式。
- **内存**：代理模式的可用地址空间收益不低于 5.2 第一轮（三张图 +566–620 MiB）。新增的 x86 常驻内存逐项记账：
  命令环 ≤ 16 MiB（放在低 2 GiB 时的上限），回存预算 32 MiB，上传窗口 1 MiB，设置面板打开时约 20–28 MiB（关闭即释放）。
- **画面**：阴影门 352 项帧哈希、特效门 77 帧、GPU 参照门全部哈希与 5.2 冻结轮逐个相同；两种模式同机位截图差异不变。

## 3. 原则

1. 先量后改。每个阶段先有能把收益量出来的计数，再动语义。
2. 同一轮内比较。本机有别的会话在跑大型任务，进程内帧率两轮之间能差 38%；A/B 交替跑，只比同一轮，多看计数和字节。
3. 内存优先。提速如果要多占 x86 内存，必须给出数字，并且有开关可以退回。
4. 分工照路线图：碰传输语义、故障语义、跨进程所有权与生命周期的归 Fable；测量、机械改动、门禁、照设计实现归 Opus。
   Opus 写的跨进程改动一律放在默认关闭的开关后面，由 Fable 只读审查后再定默认。
5. 不变的约束全部保留（见 §10）。

### 12.3 计时环境的两个坑（都已写进门禁）

- **输入桌面被拒**：工作站锁屏或安全桌面出现时，探针的桌面安全检查会以 `OpenInputDesktop failed: Win32=5` 拒绝运行，一次持续几秒到几分钟。A/B 门现在在每次运行前等输入桌面连续 10 秒可用，被拒的运行最多重跑 3 次，回执里单列 `desktopRefusals`。检查本身没有放宽。

### 12.5 后半夜：审出的缺陷、P4、第二次冻结

### 12.6 清晨：清理、补跑、差量编码器的开销、第三次冻结（f7）

- **清理**：作者同意后，11-18 新建的 89 个沙盒实例已删除（04:23）。删之前把其中 286 个非硬链接的小文件（7.1 MiB）另存到 `_AutoTestInstanceReceipts`，清单是 `prune-created-2026-11-18.manifest.json`。11-17 的 154 个实例没有动。动手前 E: 已经有 103 GiB 空闲（04:20 前后有人腾过，不是这次清理的结果）。

- **原因有两层**：
  1. 差量编码器在 x86 上太贵。同一次占锁里交替跑只有代理臂的探针（`product-async` 与差量各三次）：48.6 / 48.1 / 48.9 fps 对 45.3 / 46.8 / 45.1（−5.8%）。前端没有阻塞，是 x86 游戏线程自己每帧从 20.6 ms 变成 21.9 ms，折合每条固定管线绘制 0.96 μs。单独给编码器做的基准得到同一个数：整条记录的路径每条 0.10 μs，差量编码器 0.98 μs。代价在“每个字一次比较，加一次依赖数据的分支”。后半夜那一对探针（各两次）只差 1.5%，当时没有看出来。
  2. 生与死上代理臂对整机负载敏感，见本节末项。
- **修法**：`EncodeFixedDeltaRecord` 改成先求出一个块里哪些字变了（有 SSE2 时一次比 4 个字，尾部按字比），再只访问变了的字。线格式和写出的字节都不变。证据：与旧编码器逐字节比对 506,672 条记录（四种疏密、校验开和关）全部相同；线格式测试加了一段“与逐字的朴素写法逐字节相同”的检查（多 5,590 项，共 1,464,444 项，两种位宽 0 失败）；故意把编码器改坏两种方式，这段检查分别报 9,015 项和 4,544 项失败。新编码器在基准里每条 0.26 μs。基准程序留在 `AutoTest/bench_render_host_fixed_delta.cpp`。
- **修后**（冻结 f7 宿主加新前端，同样的交替探针）：`product-async` 49.3 / 49.3 / 48.4 fps，差量 46.9 / 48.8 / 48.8；x86 每帧 20.4 ms 对 20.5 ms。46.9 的那次运行里宿主和 x86 都慢，是负载。环流量不变，因为字节相同。

| 异步销毁 / 建纹理 | Astra 6.2 实现，见 12.9 | |

**回读变慢的原因**：开了 Present 流水之后 Lost Temple 的帧截取有时极慢（121 次回读 1 秒，一次截取超时）。按时间线看是“前几次 0.5 ms / 次，40 秒之后每次 7–9 ms”，采样显示慢的时间全在宿主把回读缓冲拷出来的 `memcpy` 上。回读缓冲和上传缓冲一样申请的是“主机可见 + 一致”，DXVK 在这种要求下允许落到不带缓存的类型上；CPU 读不带缓存的映射本来就慢。改成申请带缓存的类型之后，八次截取全部 0.15–0.24 ms / 次。为什么之前有时快、为什么在流水打开后才显现，没有查清，只确认了修法有效。

**DLL 瘦身**：量过 f4 产品（映像 19.9 MiB）。`.text` 12.2、`.rdata` 3.9、`.eh_frame` 1.8；按名字归类，war3 数据层约 10.5 MiB，DXVK 核心 + d3d9 + dxso + spirv 约 3.2，C++ 运行库约 3.1，imgui 约 0.8。做一个只含代理模式的瘦 DLL 最多省 5–8 MiB；把映像放到 2 GiB 以上不行（它的指针会到游戏代码里）。不建议做。同样的道理，交给游戏的锁定内存（`X86_BACKING_KIB`、上传窗口）必须留在低位；只有环是纯粹自己用的。数据层的 `RenderQueueTracker::m_entries`（6 MiB）也只有自己用，可以照同样的条件放高位，这一轮没做。

**负载敏感的原因**：这台机器是 12 个逻辑处理器。代理模式在生与死上要两条线程同时接近跑满（这一轮之前游戏线程每帧约 23 ms CPU、宿主进程约 17 ms，之后约 20–21 ms 和 14–16 ms），进程内只有一条。别的负载一上来，两条线程里任何一条被挤到同一个物理核的另一个超线程上，帧时间就涨。所以能做的就是把两边每帧的 CPU 降下来，上表各项都是这个方向。稳态下同步往返已经是每帧 0 次（3.2 万次同步调用几乎全在加载期），所以异步销毁 / 建纹理对稳态帧率没有贡献，它减少的是加载和切图时的卡顿。环流量每帧 4.9 MB，其中绝大部分是动态顶点上传；4 MiB 的环没有出现过背压（`ringFullUs` 为 0），容量不动。

测试工具里试过给探针加“正常优先级”启动的选项，受限令牌启动器把创建标志钉死为低优先级（安全断言），启动被拒；没有放宽断言，选项已撤掉。作者自己试用时游戏和宿主都是正常优先级。

### 12.9 异步销毁与异步建纹理（Astra 6.2 实现，Fable 核对）

设计与实现都由 Astra 6.2（极高思考强度）完成，它是 12 个文件的唯一写入者；Fable 核对了它的改动范围（只动了分给它的文件）、重跑了线格式与注册表测试、读了前端的预留事务和宿主的准入代码，GPU 门和游戏实跑由 Fable 做。

- **销毁**（`WARVK_D3D9_ASYNC_DESTROY=1`，默认关）：x86 的最终 `Release` 先冲刷注解和暂存绘制，再把 `Destroy(g)` 发到同一条 FIFO，发布成功才写墓碑、才允许复用这个 id 的下一代。环满时同一条记录、同一个序号重试。宿主执行 Destroy 的逻辑不变（`settle()`、`waitPresentRetired()`、解绑、墓碑）。
- **建纹理**（`WARVK_D3D9_ASYNC_CREATE_TEXTURE=1`，默认关）：x86 与宿主共用一组类型配额（VB+IB 8、纹理 65,472、VS / PS / 声明各 4）。同一设备 nonce 内每种格式第一次创建仍然同步，收到精确成功之后这种格式才走异步；失败过的格式下次还是同步。能在 x86 判定的拒绝（参数、配额、id 用尽）原地返回原来的 HRESULT，不发记录、不耗代际。
- **协商**：`Initialize.args[6]` 加 `0x08`、`0x10` 两位，环版本仍是 2。宿主在进入 `apply` 之前拒绝没有协商过的异步资源记录；协商过的会话仍接受同步版本。
- **与设计的一处取舍**：纹理配额已满而请求的格式还没被证实时，x86 仍走同步，因为宿主先查格式支持再查槽位，本地直接报满会改变第一个 HRESULT。
- **宿主里的故障注入**：只在给了第 6 个命令行参数、没有游戏档位、并且在隔离桌面上时才生效；产品前端不会传这个参数，线上消息也请求不到。
- **证据**：x86 COM 入口的 CPU 夹具 19 个会话全过（消费者不推进 `applied` 时调用已返回；顺序是 注解 → 引用旧资源的绘制批 → `Destroy(g)` → `Create(g+1)` → 新内容上传 → 同步 barrier）；两个开关都关时线上请求和回复 4,760 字节与改前逐字节相同；线格式 1,464,444 项、注册表 661,550 项两种位宽 0 失败；`sizeof(Connection)`、`sizeof(Device)` 不变，开关打开时每个连接多 104 字节。
- **没做的**（设计里的步骤 3）：宿主把“逻辑撤销”和“物理退休”拆开。现在宿主每执行一次 Destroy 仍会把在途的那一帧等完。

### 12.15 11-18 深夜：战役黑屏与界面丢失、低视角阴影消失、静态阴影（f13）

**战役黑屏和界面丢失。** 战役的片头电影由 `Game.dll+0xE3210` 播放：先关闭图形设备（`0xE3160`），放电影（`0xE3240` 调用 `0xE94F0`），再重建窗口和设备（`0xE3050`）。游戏重建后仍沿用动态顶点、索引环形缓冲的写入位置，在新缓冲区里从原来的偏移接着写。D3D9 允许这样做，但冻结的 f8 前端要求加锁起点不超过已写入的连续前缀（`d3d9_proxy.cpp` 的 `offset>initializedPrefix`），于是这些 Lock 全部失败，写入位置也不再前进，依赖这些缓冲的绘制全被前端本地拒绝。沙盒里第二台设备的诊断前端记录到 `vb`、`ib` 的前缀都是 0，`base=13493`、`start=3631` 固定不变，`admittedDraws=0`。

**修法（只改 x86 `d3d9.dll`，前端仍是 f8）。** `war3_proxy_mode.cpp` 替换前端设备虚表的 `CreateVertexBuffer` 和 `CreateIndexBuffer`。一旦有设备结束或发生过 Reset，之后创建的动态缓冲先整块 DISCARD 写零，把前缀补满，再做一次 16 字节的 DISCARD，让后续追加仍走不保留 x86 副本的路径。第一台设备的流程不变。

**低视角阴影消失。** x86 镜像和主机 `ShadowCasterPool` 都限制每帧复制 16 MiB。超出后 x86 不再发送 caster 并声明有遗漏，主机拒绝更新整张阴影图，沿用旧图 8 帧后阴影强度归零。玩家两包证据的 729 个遗漏帧全部符合这条路径。进程内渲染没有这个 16 MiB 门，所以“代理版才出现”可信。上限改为 64 MiB，两端共用 `war3_shadow_scene.h` 的 `CasterCopyFrameBytes`。超限时仍保留整图拒绝，不发布不完整的阴影图。

### 12.16 11-19：阴影预算的三项根治（f14）

由 Astra 6.2 实现，主线程审查、构建和实测。只改代理模式，进程内渲染的门禁逐像素一致。前端仍是 f8。

**1. 真实需求统计和减量复制。** 超限后继续统计真实需求。动态顶点只复制阴影要用的数据（位置 12 字节，带 alpha 测试时加 UV 共 20 字节），按索引实际用到的范围裁剪，同一帧连续重复的切片只复制一次。`(4)生与死`（564 个 caster）每帧复制量 6.44 → 2.59 MiB。

**2. 提前剔除。** 主机在绘制时由实际顶点算世界包围盒，完全在级联外的 caster 不进该级联。caster 管线开了 depth clamp，所以只比较光空间 X、Y，不做 Z 剔除，输出不变。`WARVK_D3D9_SHADOW_EXACT_CULL=0` 可关闭。绘制的 caster 数：`生与死` 2252 → 1899，`LostTemple` 844 → 581。

**3. 超预算按级联隔离。** x86 不再截断，准入由主机决定。被拒的 caster 保留世界包围盒，用来判定每个级联是否完整。完整的级联正常更新，不完整的沿用旧内容最多 8 帧，之后标记不可用，接收端在不可用级联上不投影。任何无法归属的遗漏回退到整图规则。

第一版按 caster 逐个腾挪空间，压力下复制耗时 94–124 ms，已废弃。现行方案不移动已复制的数据：普通帧照旧 next-fit；上一帧需求超限时，按上一帧各层级（caster 最先接触的级联）的需求，给更近的层级预留空间，余量 3.125%，每个 caster 的判定是常数时间。首个超限帧没有历史，先到先得，由 8 帧保持兜底。需求回落后下一帧撤销预留。

**验证（沙盒，`生与死`，同一路线）。** 静态测试 40/40，阴影门禁在剔除开、关两臂都通过，进程内外一致。

|---|---|---|---|
| 默认 64 MiB | 13.09 ms | 0.80 ms | 15/0/0（2720） |
| 强制 2 MiB | 12.21 ms | 0.65 ms | 1/0/14（2884），0/1/14（60） |

### 12.17 11-19：贴地阴影、着色器与预算、按类别的阴影设置（f16）

这一轮有意改变两种模式的画面（偏移和着色器），门禁比较的是代理与进程内一致。类别设置只在非默认值时改变画面，默认路径和以前逐字节相同。前端仍是 f8。

**贴地阴影。** 步兵的脚、低矮围栏等离地很近的多边形不投影，压低视角才出现。原因是接收端的常量偏移按归一化深度给出，远级联的深度范围大，同一个常量折合的世界距离也大；屏幕上的地面主要落在 C2、C3（12.16），比这段距离更贴地的遮挡全被吃掉。压低视角时地面换到近级联，偏移折合的距离变小，所以又出现。改法：接收端偏移改按纹素给出（默认 receiverBias 0.0004、cascadeBiasScale 0、casterBiasClamp 0.001、normalBiasScale 0.0005，按 4096/分辨率缩放），去掉 VS 里的偏移钳制；地形（S1）caster 自身沿光方向推远 `0.0008×(4096/分辨率)`，防止地面自阴影粉刺。1024、2048 分辨率、进程内、`cine5` 设备重建和 `生与死` 低视角都看过画面。

**着色器。** 接收端在混合权重为 0 时不再采样下一级联；核为均匀权重时用 `textureGather` 一次取四个比较结果。新加的 GPU 时间戳（每 6 个查询一组，4 帧后无等待读回）：接收端 `LostTemple` 约 570 → 414–439 µs，`生与死` 约 591 → 481 µs，省 19%–27%。阴影图本身每张约 1.5–1.8 ms。

**预算。** 同一帧内相同的索引数据只复制一次（按内容哈希），每帧省约 456–464 KiB，`生与死` 净复制量 2.58 → 2.46 MiB（−4.6%）。顶点量化在这两张图上从未生效（开关两臂顶点字节相同），改为默认关闭，`WARVK_D3D9_CASTER_QUANTIZE=1` 打开，门禁两臂都跑。教训：索引表最初直接在映射的显存上 `memcmp`，那是写合并内存，CPU 读回极慢，复制耗时 0.18 → 3.7 ms；改为表内自留一份字节副本后 `LostTemple` 复制 0.23 ms、帧时间 3.3 ms（旧版 3.7 ms）。

**按类别的阴影设置。** 类别：单位、建筑、装饰物、可破坏物、其他（地形内部单列，不可关）。`ClassifyCaster(category, stage, kind, unitProven)`：地形类别且非 stage 10 为地形；kind 1 单位、2 建筑、3 可破坏物、4/5 其他；地形或世界对象类别的 stage 10 为装饰物；其余按 unitProven 归单位或其他。每类两个设置：是否投影、最长投影 N（物体高度的倍数，0 不限）。最长投影的做法：k = min(1, N·|Lz|/hypot(Lx,Ly))，把高度方向压到 k 倍后折进 `CasterLightMatrix`（第三列乘 k，平移加 Lz·(1−k)·z0），z0 是物体底部。z0 按物体取：建筑、装饰物、可破坏物取放置原点（模型有埋入地下的地基和树根：主城模型最低点比原点低约 156，树低约 58），单位和其他取最低顶点。设置经 `diag::Block::reservedGame` 传给主机。太阳移动时 k 每帧变，阈值 0.02 以内不算策略变化。

代理模式下绘制本身不带对象身份。三版实现的帧时间（默认 → 改动一个类别）：

| 做法 | `LostTemple` | `生与死` |
|---|---|---|
| 打开进程内对象身份追踪，按条目查登记表 | 3.3 → 21 ms | 17 → 约 205 ms |
| 每帧读游戏的世界对象列表，每次绘制安全读所属对象 4 次 | 3.6 → 14.2 ms | 21.8 → 50 ms |
| 列表跨帧保留，对象进表时读一次（现行） | 2.8 → 3.1 ms | 14.1 → 16.3 ms |

现行做法：渲染组钩子一直记录着 world 指针，`world + (91+组)×4` 是各组列表（组 0..3），列表 +0x0C 数据、+0x14 长度，元素 24 字节，+0x00 是精灵（即绘制的 world object entry），+0x14 是所属对象，与进程内采集器读的是同一份。实测列表只有 117（`LostTemple`）、127（`生与死`）条，读一次约 20 µs。表跨帧保留，每 90 帧、world 变化时、或查不到条目时（最多每 6 帧一次）重读；同一精灵配同一所属对象沿用上次结果，新对象用一次 `ReadProcessMemory` 复制对象头 0x60 字节判断：虚表 RVA 0xA4A704 为 CUnit（+0x5C 建筑标志 0x10000 区分建筑），0xA4FFBC 为 CDestructable，0xA4A2EC 为物品（`生与死` 地上的 `I00B`），句柄取 +0x0C/+0x10。第二版慢的原因：`IsReadableRangeFast` 并没有缓存，每次都是一次 VirtualQuery，32 位进程里约 10 µs。只在有类别被改动时才读列表。分类结果：`LostTemple` 单位、建筑、可破坏物三类关掉后画面都对，未识别 0；`生与死` 关建筑后单位影子保留。

### 12.18 11-19 晚：水面的阴影、水面效果、地狱火发光（i8）

玩家反馈三件事：深水里有大片影子（浅水没问题）；某个光照角度下水下有一段一段的竖纹；地狱火被光照成黄色。用户要求处理水体阴影、把水体现代化（反射和漫反射，可交给 Astra），并调查地狱火过亮。前端仍是 f8。

**游戏怎么画水（沙盒实测）。** 水在世界场景里画，stage −1、类别 Unknown(0)，不是 stage 14。FVF 0x152（XYZ|NORMAL|DIFFUSE|TEX1），16 位索引三角形列表，顶点数是图元数的两倍（每块 64 顶点 32 三角形），动态顶点缓冲（usage 0x208），world 为单位阵，无顶点着色器；深度测试开、深度写关、SRCALPHA/INVSRCALPHA 混合、光照开。只让这些绘制不写颜色时水全部消失，其余不变，确认识别无误。

**影子从哪来。** 阴影接收是 BeforeUi 的全屏一遍，用场景深度重建世界坐标。水不写深度，所以重建出的是水底的地面，地面的阴影透过半透明的水面合成出来：深水里一片树影，太阳斜照时水底起伏的地形投出一段段竖纹。

**改法。**
- x86 把水的绘制作为 ShadowCaster 记录送出（计入 `c.sent`，主机的完整性校验照常）。标记不用新标志位：冻结的 f8 前端用它编译时的头文件校验每条记录，`flags & ~All` 非零就拒收，x86 随即停发所有记录（第一次沙盒跑就是这样：`records=0 refused=1`，整局无阴影）。改用前端不校验的身份字：rawcode `0x7E574154`（"~WAT"，编辑器的 id 不含 `~`）、part 全 1、stage −1、batchTag −1、类别 0，`scene::IsWaterSurfaceRecord`。
- 主机在 `AppendShadowCaster` 里把它分到 `War3FrameScene::waterSurfaces/waterWorlds`，不进投影。
- 阴影 pass 先把水面按相机 viewProj 只写深度重放到一张 D32（binding 17），视口与 DXVK 一致（半像素、Y 翻转、MinZ<0.5 时 +0.001）。接收端找出“水面深度比场景深度近、且不是远平面”的像素，水深 = 水面 z − 地面 z（Z 向上），`keep = 1 − smoothstep(开始, 完全消失, 水深)`。阴影只算一次：水下的取样点随 `1 − keep` 从水底升到水面（水面是平的，那一份不带受光面坡度、额外偏移和墙面滤波），强度从 1 降到 `水面阴影浓度`；浅水就是水底的阴影，深水是水面上一层淡影。（i7 曾在水面再算一次 `computeShadowVisibility`，驱动冷编译接收端从约 8 秒涨到约 31 秒，见下面“门禁”。）阴影预处理模式（`Shadows.TaaMode` 1、2）只在水底取样，那时深水不留淡影。同时写一张 RG16F（binding 18：x 水面受光、y 水深）给水面 pass。DXVK 按视图的 usage 编码描述符，所以这张图建两个视图：仅 STORAGE 的给接收端写，仅 SAMPLED 的给水面 pass 读（Astra 发现）。
- 设置：`War3WaterSettings`（`Water.ShadowFadeStart` 24、`Water.ShadowFadeEnd` 72、`Water.SurfaceShadow` 0.3、`Water.Surface` 1、`Water.Reflection` 0.6、`Water.Specular` 1、`Water.WaveScale` 1、`Water.WaveSpeed` 1、`Water.Clarity` 0.5）；代理模式经诊断块传给主机，块升到第 4 版，末尾追加 9 个字和一个序号字。控制台“水面”在光影参数下面。

**水面 pass（Astra）。** `War3WaterSurfacePass`（`d3d9_war3_water.{h,cpp}`、`war3_water_surface.frag`），主机在阴影 pass 之后、体积光之前运行，只在本帧有水且开着水面效果时创建和录制。一个全屏三角形，只在水面像素着色：四组世界坐标锚定的波纹（波长约 50–174），Schlick 菲涅耳（F0 0.02），屏幕空间反射（最多 12 步加 4 次二分，720 单位，按厚度误差、射线长度、屏幕边缘渐隐到天空色），Blinn–Phong 高光（指数 96，乘水面受光，阴影里没有高光），水体颜色取游戏自己的水色、权重随水深增长（上限 22%）；岸边 1–9 单位内一起淡入。Astra 交接的三项都已处理：太阳关闭时高光颜色为 0、深度量子从接收端传入；无阴影时水面 pass 不跑（仍未做，见下）。

**地狱火。** 沙盒加了只在 `WARVK_D3D9_UNIT_LIGHT_PROBE=1` 下有效的探针，记录世界对象绘制的光照状态。地狱火的发光层：材质漫反射与环境光都是 0、自发光 (0.8, 1, 0)，即游戏只用自发光颜色画它（无光照层）。世界光照把所有材质的环境光强制成白色，于是约 0.56 的灰色环境光（环境光覆盖 0.28 + 光源环境光 0.28）加在青绿色上，饱和成 (1, 1, 0.56) 的淡黄。改法在代理端：前端在发送绘制时才套用世界光照，而观察者回调在那之前，所以 `FrameDraw` 读游戏的材质，漫反射为 0 且自发光非 0 时以 `materialAmbientWhite = 0` 重发世界光照，其余绘制恢复为 1。游戏自己的正午光：漫反射 1.3、环境光 (0.5, 0.5, 0.6)；我们的是 1.0 和 0.28，与这次无关。进程内的同一问题在 `d3d9_device.cpp` 的 `War3EffectiveMaterial`，本轮不动。

**门禁。** i6 的门禁主机构建被边界检查拦下（`d3d9_war3_water.cpp` 不在主机允许的源文件里），加了 `WATER_PASS_SOURCES`；i6 包是在门禁之前打的，作废。i7、i8 两个阴影门禁的远端都在第一帧阴影超时（`D3D9 dev primary failure=timeout stage=header`，`before UI: HRESULT 0x88760868`），lldb 看到主线程在 nvgpucomp64 里编译接收端管线。关掉验证层、改正常优先级都一样。用一个独立的小程序（暂存区 `ccomp`：读生成头文件里的 SPIR-V，按反射出的绑定建布局，驱动缓存指向空目录，计时 `vkCreateGraphicsPipelines`）量冷编译：
- 机器空闲时 i8 接收端 2.5–3.4 秒；另有一个 3D 游戏占约 6 个逻辑核（共 12 个）时 6–16 秒。i4、i5 的接收端在同样负载下 7.6–9.4 秒，和 i8 一样；i7（水面再算一次阴影）约 31 秒。
- 关掉循环展开、spirv-opt `-O` 只省 10–20%：慢在着色器本身大（约 4.5 万字），负载决定能不能在 5 秒内编完。
- NVIDIA 的磁盘缓存按 exe 文件名分（同名换目录命中，同一文件改名不命中）。门禁的远端主机每次都叫 `host.exe`，所以以前的门禁多半是热缓存过的；着色器一变，冷编译超过期限，主机约 6.7 秒被杀，编译从没完成过，缓存永远是冷的，重跑也一样失败。
- 游戏里的沙盒跑（x1–x4）都没有超时；前端的调用预算是 30 秒（`callDeadlineMs`），玩家看到的应是装新版后第一次进图停几秒，README 已写明。以前几版同样如此。后续可以在主机启动时后台预编译接收端，把这几秒藏进菜单和加载画面。

### 12.19 11-20 凌晨：一天的光色（j1）

用户反馈两件事：勾着“真实阴影长度”时清晨傍晚的色调对得上日落，一取消立刻不对；即使勾着，和真实日落也还有差距，希望再风格化一些，曲线和预设都要精调，并且要查论文。前端仍是 f8。

**开关为什么会变色。** `War3SunCycle::Evaluate` 里光的颜色从来不看这个开关，看它的是光照方向的高度角：勾着时用太阳的真实高度（06:40 约 8°），不勾时被夹在 35°–55°。固定管线按这个方向做漫反射，平地得到的直射光是 sin(高度角)，两者差约 4.7 倍。于是同一个 2500 K 的橙色光，勾着时地面主要靠环境光、只带一点橙；不勾时整片被照成又亮又橙。另外阴影浓度在太阳真实高度 6° 以上固定为 0.6075，勾着时清晨大半个画面压在同样浓的长影里，过暗。沙盒在 i8 上复现（`S/sunlook/b2_c.jpg`：06:40、07:30、17:20 各一对）。

**新的模型：这一刻的样子只跟着光自己的高度。** 光的颜色、亮度、给世界着色的方向、阴影的浓度和颜色、环境光的色调，全部由太阳（夜里是月亮）自己的高度决定（自定义路线取路线上的高度，默认路线取 正午高度 × sin(相位)），两种影长模式逐项相同。开关只改阴影投射方向的高度角。
- 着色方向和投影方向分开：着色方向是光的方位加上高度角 `asin(max(0.12, sin(h)^0.42))`，回写到 `settings.sun.direction`（进程内两处、代理 `FeedSunBack` 两处，都写 `lightDirection`）；阴影 pass 自己留着投影方向。指数 0.42 比余弦定律给低太阳更多的地面份额，金色时段才会落在地面上而不只是墙上。
- 阴影拿走直射光、留下环境光，逐通道算：`0.985 × 直射 /（直射 + 2 × 环境光）`，直射 = 光色 × 地面份额，环境光取同一时刻的表值（地面拿到两份环境光：D3DRS_AMBIENT 一份、light 0 的 ambient 一份）。标量浓度按亮度算，正午 0.615（原来固定 0.6075）；三通道与标量的比值作为 `Result.shadowTint`，经接收端 UBO 末尾新增的 `u_shadowTint`（UBO 752→768 字节）送进着色器，合成由 `1 − s + s·vis` 的标量改成逐通道。色调为 (1,1,1) 时与原来逐位相同；关掉天体运动时就是 (1,1,1) 加作者自己的浓度。效果是低太阳的红光几乎全是直射、蓝光几乎全是天空，影子自然偏蓝紫（暖光冷影）；正午影子的乘数约 (0.37, 0.39, 0.43)。
- 环境光 = 作者的昼夜两色按原来的过渡混合 × 色调，色调 = 表值 ÷ 默认两色在同一过渡系数下的混合，所以默认设置下就是表值本身，改过环境光的地图保留自己的比例。锁定太阳时环境光和曝光也用锁定的时间（以前不跟）。

**太阳的颜色从哪来。** 按 Preetham、Shirley、Smits（SIGGRAPH 99）附录 A.1 做了一遍直射阳光的光谱计算（`S/sunlook/physics.py`）：瑞利散射 `exp(−0.008735 λ^−4.08 m)`、气溶胶 `exp(−β λ^−1.3 m)`（β = 0.04608T − 0.04586）、臭氧、水汽，相对大气质量 `1/(cos θ + 0.15(93.885−θ)^−1.253)`，表 2 的太阳光谱，CIE 配色函数用 Wyman 等的解析拟合，转 sRGB。浊度 2 时的相关色温：90° 5603 K、60° 5513 K、30° 5077 K、20° 4689 K、10° 3853 K、7° 3374 K、5° 2979 K、3° 2386 K。对照之下旧代码在白天弧线上 24° 以内都用 2500 K、正午 6500 K、地平线混米色：橙得太久，正午偏冷，地平线发灰。

新表（`kSunMorning`、`kSunEvening`，各 17 个高度）取这条物理曲线再做三处艺术处理：
- 白平衡到“正午是略暖的白”(1.0, 0.975, 0.93)。
- 读表时把高度除以一个系数：早晨 ÷1.30、浊度 2.2，傍晚 ÷1.42、浊度 2.8。金色时段比自然界伸得更高，傍晚比清晨更红（傍晚按上午到下午 10:30–13:30 平滑切换）。
- 颜色有下限 (1.0, 0.46, 0.22)，不让地平线的光变成纯红。
亮度另给：0° 0.12、1.5° 0.42、3° 0.64、6° 0.83、10° 0.93、15° 0.975、25° 以上 1.0。

**月亮、暮色、夜晚。**
- 日月在地平线上交接，光照方向在那一刻翻转 180°。两张表在 0° 用同一个键（太阳的下限色、亮度 0.12），交接时颜色不跳、几乎没有直射光和影子；数值自检量到交接处光 0.120、阴影 0.015。
- 月光（`kMoon`）从这个键升到 (0.60, 0.74, 1.00) × 0.46。色相朝 Jensen 等给出的暗视觉蓝移目标 xy=(0.25, 0.25)（换到显示空间约 (0.63, 0.73, 1.0)）再风格化一点。亮度按夜里环境光的尺度定：两者相加不超过白，夜晚才是蓝的。第一版月光 0.95，地面的光照合计超过 1 被固定管线截断成灰黄，就是 i8“像白天蒙了一层色”的夜晚。
- 环境光（`kAmbient`，按太阳带符号的高度）：夜 (0.150, 0.190, 0.320)；−7° 蓝调时刻 (0.200, 0.208, 0.370)；−3° 紫光 (0.245, 0.235, 0.380)；0° (0.250, 0.228, 0.330)；4°–8° 少蓝的淡紫灰 (0.252, 0.234, 0.280)→(0.258, 0.248, 0.262)，低太阳的暖光因此在地面上显色、影子留冷色；30° 以上是白天偏冷的天空 (0.262, 0.277, 0.315)。夜里的环境光亮度是白天的 67%（原来不低于 85%），夜晚比以前暗。
- 依据：紫光在太阳位于地平线下 3°–4° 时最强、6° 时消失（WMO 国际云图）；暮光先变蓝，来自臭氧 Chappuis 带的吸收，乡村约 −12°、城市约 −6° 最蓝，昼夜照度相差 6–8 个数量级（Spitschan 等 2016）；月光约 0.1 lux、人眼把它看成蓝色（Jensen 等）。

### 12.20 11-20：战役过场的“纯白模”和进图一闪（j2）

玩家反馈：冰封王座暗夜精灵战役第一关，一进去就是一片蓝白、只看得见影子（“纯白模”）；兽族战役“加载的一瞬间”整屏灰白，上面浮着深色的影子形状；进其他图的一瞬间也会闪一下（GIF）。玩家的日志包（11-20 00:48，i8）：代理模式，两段帧取证各 550 帧，x86 与主机日志都没有错误。前端仍是 f8。

**不是雾，也不是白模。** 取证第一段 f250–f400 正是暗夜精灵第一关开场过场的最后一次淡出：镜头离地约 1500–1700，远平面从 10100 变成 5000，整屏是均匀的蓝，影子照常叠在上面。主机的雾参数和进程内 `UpdateFog` 逐项一致，排除雾。沙盒里把昼夜环境光临时改成红色，同一帧淡出变成 (197, 24, 42)：这片颜色就是我们的环境光。

**原因。** 过场的淡入淡出（`CinematicFadeBJ`，`White_mask.tga`，颜色 0,0,0 即淡出到黑）是游戏在世界场景里画的一块贴镜头的四边形：view 为单位阵，FVF 0x152，光照开，`COLORVERTEX` 开，环境光与漫反射的材质来源都是 COLOR1（顶点色），材质 D=A=1、E=0，SRCALPHA/INVSRCALPHA 混合，两个三角形的条带。原生画法下黑色的顶点色就是它的环境光和漫反射，所以它是黑的。
- 进程内（`d3d9_device.cpp`）世界光照也把环境光来源强制成材质、材质环境光为白，但游戏自己设了 `AMBIENTMATERIALSOURCE` 的绘制以游戏的为准（`m_war3AmbientSourceForced = false`），这块四边形保持黑色。
- 冻结的 f8 前端（`WarVKD3D9WorldLighting` 约定）在世界光照生效时给每一次固定管线的世界绘制套上白色材质环境光、替换 light 0，开 `ambientOverride` 时再把 `D3DRS_AMBIENT` 换成我们的环境光。这块黑色四边形于是被照成我们的环境光：白天灰（兽族），夜里蓝（暗夜精灵）。
- 它在世界场景里画，BeforeUi 的阴影合成在世界场景结束之后，所以影子浮在它上面。玩家看到的就是“一片纯色 + 影子”。
- 两条路径的世界场景边界相同（`Hook_WorldRenderScene` → 进程内 `War3SetWorldLightingScope`、代理 `FrameWorldScene`），差别只在环境光来源这一条规则。

### 12.21 水面 v2：在原位换掉游戏的水（设计）

11-19 用户的决定：风格化（让默认 56° 视角下看得见），直接走方案 B（主机拦下游戏自己的水，在那一刻拍下场景，用我们的着色器画水），低端显卡默认关，与 Astra 合作。11-20 用户把方向交给我：Astra 做后端，我做研究、定方向、验收。i8 的教训：日志里“水面 pass 跑了”不等于玩家看得见，每个滑块都要让默认视角的截图变化。

**测量（j2 包 + 主机探针 `WARVK_D3D9_WATER_PROBE=<n>`，只在开发构建里，`S/water/probe_wp1.txt`）。** 水面测试图第 900 个世界场景，255 次绘制：
- 0–171：地形、单位、树、建筑，不透明或 alpha 测试，大多带投影记录。
- 172–188：17 次水，全是 DrawFixed：decl 2、步长 36（XYZ|NORMAL|DIFFUSE|TEX1），一张纹理（游戏按帧换水的动画纹理），深度测试开、写关，SRCALPHA/INVSRCALPHA，光照开，漫反射来源 COLOR1（顶点色：地图的水色和游戏按水深给的 alpha），stage 0 颜色、alpha 都是 MODULATE。每次都带 "~WAT" 投影记录。
- 189–254：66 次相机空间的粒子和加色特效（view 单位阵，SRCALPHA/ONE，雨也在这里）。
- 主机先收到一批绘制的注解（`AnnotateDraws`）再收到这批绘制，所以录制前就能认出水。
结论：在水的那一刻拍下颜色和深度，拍到的是全部不透明的世界（含站在水里的单位），折射和水深是真的；之后的粒子、雨照样画在水上；不需要改前端和 x86 的记录。

**做法。**
1. 主机（`d3d9_host_main.cpp`）在一批绘制里遇到水就把这批拆开：水之前的照常，水用水面执行器画，水之后的照常。注解照常交给阴影 pass（接收端的水深淡影不变）。
2. 每个世界场景第一次画水时：结束当前渲染，把颜色复制到一张快照（单采样、同格式），深度复制一份或以只读布局采样，再接着渲染。之后每次水用我们的管线画同一份几何（同一 VB/IB/声明/图元）。任何一步不行就照游戏原样画并计数，不丢水。
3. 顶点着色器按这次绘制的固定管线状态变换（world、view、projection、纹理坐标），传出世界坐标、顶点色、纹理坐标。投影矩阵在绘制状态里，片元着色器用它把深度换成线性距离，不依赖这一帧的 FrameScene 记录是否已到。太阳是前端套用后的 light 0。
4. 片元着色器，第一版只做三样（之前给用户的优先级）：
   - 水深的颜色：沿视线的水柱厚度和垂直水深，按通道的 Beer–Lambert 吸收（红最快、蓝最慢），深处的颜色从游戏的水色（纹理 × 顶点色）推出来，保留每张地图自己的水色。
   - 岸边白沫：厚度小于约 8–20 单位的一圈，两层随世界坐标流动的噪声，边缘柔和；站在水里的单位、礁石周围也会有。
   - 折射：按水面法线偏移快照的取样位置，偏移量随厚度增加；偏移后取到的像素比水面还近（水面上方的东西）就退回不偏移，防止漏边。
   - 最后 `mix(游戏原样, 我们的, Water.Style)`：Style 为 0 时和游戏原样逐像素相同，用来对照和兜底。
   反射、阳光闪烁、焦散留到第二版。
5. 本帧原位画过水，就不再跑现在的后合成水面 pass；进程内（32 位）路径不变，仍是后合成 pass（`d3d9_device.cpp` 不改）。
6. 设置：新增 `Water.Style`（0–1，默认 1）、`Water.DepthColor`、`Water.Foam`、`Water.Refraction`（0–2，默认 1）、`Water.InPlace`（0 关、1 开、2 自动，默认 2：独立显卡开、集成显卡关）。波纹沿用 `Water.WaveScale`、`Water.WaveSpeed`。诊断块升到第 5 版（x86 编码、主机解码），控制台“水面”一节加滑块，玩家设置解析和静态测试跟上。
7. 新的主机源文件要加进 `run_render_host_core_gate.py` 的允许列表（同 `WATER_PASS_SOURCES`）。

**验收。** 主机门禁构建通过；静态测试覆盖拆批、回退、设置版本；两个阴影门禁照常通过；沙盒默认视角截图：Style 0 与 j2 的水只差动画噪声，Style 1 与 0 在水面区域有明显差别，四个滑块各自改变截图（差值测试）；1080p 下水面执行器的 GPU 时间不超过 0.4 ms；x86 日志无错误、`refused=0`。

### 12.22 水面 v2 第二部分：水面上的光（设计）

用户最早的抱怨是“开不开反射和高光看不出区别，怎么拉参数都一样”。第一部分之后，原位水面开着时 `Water.Reflection`、`Water.Specular` 只作用于已被跳过的后合成 pass，仍是死滑块。这一部分让它们在原位水面里起作用，并加浅水焦散。

**几何事实（决定了风格化的做法）。**
- 默认镜头朝北（屏幕上方 = +Y），俯角约 56°；默认太阳（`war3_sun_cycle.h`）东升、经南、西落。平静水面把视线反射到北方约 56° 仰角，太阳却在南边：**从默认镜头物理上永远看不到太阳的镜面高光**，波纹的法线倾斜（几度到十几度）也补不回来。所以闪光必须风格化。
- 视线与水面法线约 34°，Schlick 菲涅尔 F ≈ 0.02：物理反射几乎为零。反射也要风格化地抬高下限，越往屏幕上方（视线越斜）越亮，这本身就是距离感。
- 默认镜头下屏幕中央约 0.8 像素/世界单位（距离 1650、视场 70°、1080p）：一个 64 单位的焦散格约 50 像素，闪光点至少 2–3 像素才看得见、才过得了中值滤波的差值测试。

**做法（都在原位水面的片元里，Style 0 时仍原样返回）。**
1. 阳光闪烁（`Water.Specular`，0–2，默认 1）：两层。宽的一层是水面的“光带”（Blinn-Phong，指数几十），细的一层是闪点（更高频的法线扰动 + 很高的指数 + smoothstep 阈值，按像素足迹淡出远处防闪烁）。光源用“面向镜头的太阳”：太阳的颜色和高度角，方位转到镜头的前方，这样默认镜头一天里都看得见；亮度随太阳高度（落山渐隐）和光色走，夜里是月光的弱闪。闪光不能被游戏水的 alpha 削弱。
2. 反射（`Water.Reflection`，0–1，默认 0.6）：屏幕空间反射。按带波纹的法线反射视线，用快照深度步进（约 16 步 + 4 次二分，最远约 768 单位），命中就取快照颜色（岸边的树、悬崖、站在水边的单位），没命中、出屏、步数用完就渐变到“天空色”。天空色从这一帧的环境光和太阳光推出来（白天偏蓝、黄昏偏暖、夜里暗），不用贴图。风格化菲涅尔：`F = F0' + (1 - F0') (1 - cosθ)^5`，`F0'` 随滑块抬高（默认值下屏幕中央约 0.1–0.15）。反射色略带地图水色，不把水面洗白。
3. 浅水焦散（新增 `Water.Caustics`，0–2，默认 1）：画在水底（快照深度重建的世界坐标）上，不随水面漂；程序化（两层动画胞元边缘，不加贴图资源），格子约 48–96 单位，随水底的折射略有晃动；在垂直水深约 2–8 单位渐入、48–64 单位渐出；乘太阳高度和光色。加在被吸收之前的水底颜色上，所以深处自然被水色吞掉。
4. 清澈度（`Water.Clarity`）仍只属于后合成 pass；控制台把它挪到“后合成（原位水面关闭时）”小节，反射、闪烁改名为两条路径共用的“水面反射”“阳光闪烁”。
5. 诊断块第 6 版：`waterInPlace` 扩到 8 个字（第 6 个是焦散，后两个保留为 0），第 4、5 版的块照常解码、缺的取默认值。
