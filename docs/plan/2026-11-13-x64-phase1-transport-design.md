# x64 迁移阶段 1：传输层设计

2026-11-13，Claude（Fable 5.2）。[整体路线](2026-11-13-x64-migration-roadmap.md) 阶段 1 的设计说明，供后续照做。
本文定下命令环、同步回复、背压与宿主故障语义，以及内容载荷协议与有界上传窗口（§7，11-15 定稿）；实现各记回执。

路线里三条待作者确认的建议，本设计按建议值取：宿主故障时 x86 侧**安全退出并写报告，不做热回退**。
策略只落在一个挂钩上（§5），改主意不需要动传输。

## 1. 现状与问题

现在每条 D9C2 消息的路径是：调用线程编码进 64 KiB 包 → 复制进 4 槽队列 → 工作线程复制出来 → 写命名管道 →
宿主读管道 → 执行 → 写回复 → 工作线程读回复。工作线程**每写一条就等回复**，传输和宿主执行从不重叠。
[准入拆解](../research/2026-10-29-x64-admission-breakdown.md) 量过：1,025 draw 的帧里，准入时间的 75% 是调用线程在等
队列空位；每批往返 69 µs，其中管道拷贝、宿主读和两次线程唤醒约 20 µs。

要去掉的是三样：逐条回复、逐条唤醒、多次拷贝。不变的是：消息格式（D9C2 头与各 op 负载）、严格的序号顺序、
“异步消息被拒绝即终止”的合同、所有等待有界。

## 2. 形态

```
x86 调用线程 ──写──▶ [生产者区：tail + 字节环]  ──读（只读映射）──▶ 宿主执行线程
x86 调用线程 ◀─读（只读映射）── [消费者区：head/applied/故障/GPU 水位 + 回复槽] ◀─写── 宿主执行线程
x86 看护线程：等宿主进程句柄；管道保持打开，只用于握手
```

- **两个共享内存区，各归一方写。** 生产者区（控制头 + 字节环）x86 读写、宿主只读；消费者区（控制头 + 回复槽）
  宿主读写、x86 只读。游戏进程里的野指针写不到宿主的账本和回复，宿主也改不了 x86 已发布的字节。
  两个区和两个事件都由 x86 按连接 nonce 命名创建（与现有 RH1 槽位相同的 LogonSecurity、拒绝 `ERROR_ALREADY_EXISTS`）。
- **握手仍走管道。** `Initialize` 成功后，下一条消息必须是 `AttachRing`（同步、走管道）：`args[0]` 环容量、
  `args[1]` 回复槽容量、`args[2]` 版本。宿主打开并校验两个区后回 OK，**这条回复之后双方同时切到环**：
  环上第一条记录的序号就是 `AttachRing` 的序号加一。管道此后不再承载命令。
- **不协商就不变。** `WARVK_D3D9_COMMAND_RING=1` 才启用（`WARVK_D3D9_COMMAND_RING_KIB` 可改容量，
  256–65536 且为 2 的幂，默认 4096）。未启用时管道路径逐字节不变。

### 字节环

位置是 64 位的累计字节数（永不回绕），偏移 = 位置 & (容量 − 1)。记录可以跨环尾，分两段拷贝。

```
记录 = 16 字节记录头 + D9C2 消息（128 字节头 + 负载），整体补齐到 16 字节
记录头: u32 bytes（消息字节数，128..65536）
        u32 flags（bit0 = 同步，需要回复；其余必须为 0）
        u32 sequenceLow（消息序号低 32 位）
        u32 check（记录头前 12 字节 + D9C2 头 128 字节的校验）
```

生产者：空间不够时重读一次 `head`；仍不够即 Full（背压，§4）。写完整条记录后才推进 `tail`，所以宿主永远看不到半条记录。

宿主（**每个字段只取一次**）：读 `tail` → 把记录头拷到私有内存并校验 → 把消息拷到私有包 → 校验 check、D9C2 头、
nonce、序号恰好等于期望值且与 `sequenceLow` 一致 → 推进 `head`（此时环空间就还给生产者，不等执行完）→ 执行 →
同步记录写回复槽 → 发布 GPU 水位与 `applied`（最后一条已执行记录的序号）。

校验只覆盖记录头和 D9C2 头，不覆盖负载：负载内容本来就由宿主逐 op 校验（宿主从不信任 x86 字节）；
游戏进程里的野写落在环里的负载上，与早一微秒落在游戏自己的缓冲上没有区别，传输层无法比来源更可靠。
但帧定位一旦错位，后面所有记录都会被误读，所以定位必须能发现。

### 同步回复

同步调用发布记录后阻塞，所以任一时刻最多一条同步记录未回复。宿主把 `D9R2` 回复头和负载写进回复槽，再发布
`applied`；x86 看到 `applied` 等于自己的序号后，先把 96 字节回复头拷到私有内存校验身份（nonce、序号、id、代次、
负载长度），再拷负载。异步记录不写回复槽：按现有合同它们只能是 `D3D_OK`，否则宿主停止消费并发布故障（§5）。

`WaitEvent` 的完成水位改由消费者区的 `gpuCompleted` 提供：记录被执行后水位必须不小于它请求的序号，否则按合同违例终止。

### 唤醒

两个自动复位事件：`work`（宿主等）、`progress`（x86 等）。各有一个“我要睡了”的标志：

- 宿主空了先自旋约几十微秒；仍空则置 `parked`、**再查一次 `tail`**、然后等事件。生产者推进 `tail` 后看到 `parked` 才 `SetEvent`。
- x86 等空间或等回复时同理：置 `waiting`、再查一次、然后等；宿主推进 `head`/`applied` 后看到 `waiting` 才 `SetEvent`。
- 这两对“写标志/读位置”都用顺序一致的原子操作，不会丢唤醒。所有等待另有有限超时做兜底复查，标志被写坏也只是多等一次。

宿主忙的时候生产者一路追加，没有系统调用；这就是批次边界——宿主每次醒来消费到当时的 `tail` 为止。

## 3. 不信任对方的字段

共享内存里的每个值，读的一方都当作输入校验，自己的值只留私有副本、从不回读：

| 读方 | 字段 | 规则 |
|---|---|---|
| 宿主 | `tail` | 不回退；`tail − head ≤ 容量`；非零时至少一条完整记录 |
| 宿主 | 记录头/消息 | §2；任何一项不符 |
| x86 | `head` | 不回退；`≤` 自己的 `tail` |
| x86 | `applied` | 不回退；`≤` 自己已发布的序号 |
| x86 | 回复头 | `DecodeReply` 的身份与长度规则 |
| 双方 | 区头 | magic、版本、nonce、容量，挂接时校验一次，之后只用私有副本 |

任何一条不成立都是终止性故障：宿主发布故障码后自停（退出码 4），x86 fail-closed。没有重试、重同步或跳过。

## 4. 背压与期限

环满时生产者等 `progress`，不丢消息、不扩容。期限：

- **无进展期限 10 s（滚动）**：等待期间 `head` 和 `applied` 都没动才计时；宿主在消费就不算卡死。
  载图时宿主连续执行大量上传属于“有进展”，不会误判。
- **同步调用总期限 30 s**：沿用管道路径的预算（含准入等待）。
- 未执行的工作量上界 = 环容量 + 宿主手里的一条私有记录。默认 4 MiB 约为一帧的量；x86 侧为此付出的地址空间
  是 4 MiB 环 + 64 KiB 回复槽 + 两页控制头。

## 5. 宿主故障语义

x86 侧把第一次终止原因记进一份 `TerminalReport`（先到先得，之后的不覆盖）：

| 类别 | 判定 | 来源 |
|---|---|---|
| HostExited | 宿主进程句柄触发，而此前没有 Finish 或已确认的 DEVICELOST | 看护线程 |
| HostHung | §4 两个期限之一到期，且宿主进程仍在 | 调用线程 |
| HostRejected | 宿主发布故障：异步记录被拒绝（带序号与 HRESULT） | 消费者区 |
| HostDeviceLost | 宿主回复或发布 `D3DERR_DEVICELOST` | 回复/消费者区 |
| RingCorrupt | §3 任一规则不成立（x86 看到的，或宿主发布的故障码） | 双方 |
| LocalContract | 其余本地合同违例（原有 `failClosed()` 调用点） | x86 |

报告字段：类别、宿主退出码、最后发布/已执行的序号、HRESULT、简短说明。之后所有调用返回 `D3DERR_DEVICELOST`
（原有行为）。

**策略挂钩**：`Connection` 在记下报告的那一刻调用一次 `terminalHook(context, report)`（构造时给定，可为空）。
开发代理不装挂钩，析构时把报告打印成 `warvk-d3d9-terminal/v1` 行供门禁读取。产品接入时（阶段 5）在挂钩里做
“写报告文件、提示玩家、请求安全退出”；挂钩在检测到故障的线程上调用，只允许做不阻塞的登记，真正的退出由游戏
主循环在安全点执行。

宿主侧：等待 `work` 时同时等父进程句柄，父进程没了即退出；发现环损坏时先把故障码写进消费者区并唤醒 x86，再自停。
生产者正常关闭（没有 Finish）用生产者区的 `closed` 标志表达，宿主读空后按“流结束”处理，与管道 EOF 相同。
会话在 x86 侧失败时（任何终止原因），看护线程退出前同样置 `closed` 并唤醒宿主：空闲的宿主不必等到父进程退出
才知道流已结束，x86 随后对宿主进程的收尾等待也就不会白等。

## 6. 阶段标记与会话重置（阶段 0 的输入）

- `Stage` 枚举追加 `WorldSceneEnter=5`、`WorldSceneExit=6`。宿主记录器把它们计入现有摘要；BeforeUi 第 10 层与
  帧末兜底在 4a 搬到宿主时只用这两个标记和宿主自己的 draw 计数。
- 宿主用 `SceneTracker`（`d3d9_annotation_wire.h`）保存这份状态：`active`、`completedThisFrame`、
  `drawsAfterScene(draws)`、会话代次。两个场景标记**严格成对**：未进入就退出、已进入再进入都被拒绝
  （`D3DERR_INVALIDCALL`，同步返回给数据层，不改任何状态）。一帧里可以有多对；Present 清 `completedThisFrame`，
  `active` 跨帧保留（与 x86 静态量一致）。
- 新 op `SessionReset`：`args[0]` 原因（1 换图、2 退出对局），`args[1..2]` x86 的换图代次。不带负载、不带资源 id。
  代次必须严格递增，世界场景打开期间拒绝。宿主现在只登记并计入摘要；阴影迁移（4c）时由它驱动宿主侧会话纪元。
- x86 侧分两步：`Connection::requestSessionReset(reason, generation)` **任何线程可调**（换图信号可能来自非渲染线程），
  只记下最新一条请求、不发送；所有者线程在下一条 `Present` 消息之前把它作为一条同步消息发出（`call()` 里保证，
  与进程内“Present 合并应用”同义）。多条请求合并成代次最大的那条。宿主拒绝时只计数、丢弃请求，这一帧照常结束。
  代理导出 `WarVKD3D9RequestSessionReset(device, reason, generationLow, generationHigh)`。
- 两者都要求已协商 Annotations。

## 7. 内容载荷与上传窗口

### 7.1 内容载荷（合同第 4 项，`d3d9_content_wire.h`）

数据层把几何、骨骼矩阵这类大块内容**按自己的身份上传一次**，之后 draw 标注只带身份；字节只在宿主里有一份。

- **协商**：随 Annotations 一起协商，不新增特性位。未协商时三个 op 全部被拒绝。
- **身份**：数据层自己的 64 位内容键（非 0）。资源注册表只有 64 个槽，放不下一张图的模型几何，所以内容不走注册表，
  宿主另有一个按键索引的内容仓库。
- **修订号**：整条连接上严格递增的 64 位数，由 x86 连接层分配并返回给数据层。同一个键再上传就是替换，
  旧修订号从此不再绑定。上传一打开就消耗掉它的修订号，被丢弃的上传也不例外。
- **三个 op**（都不带资源 id）：
  - `ContentUpload`：`args` 为种类、键低/高、修订号低/高、总字节数、偏移；负载是一块（≤ 65,408 B）。
    一个内容的各块必须是**连续的消息**，偏移从 0 起首尾相接，最后一块提交。打开期间收到任何别的消息
    （包括不是下一块的块），那条消息被拒绝，打开的内容被丢弃。
  - `ContentRelease`：键、修订号，必须正好是当前存活的那一份。
  - `ContentRead`：键、修订号、偏移、字节数（≤ 65,408），同步回复带回字节。x86 没有副本，回读只有这一条路。
- **种类（暂定 v1）**：`Geometry=1` 对传输不透明，布局归 4c 的消费者定；`BoneMatrices=2` 必须是整数个有限 float。
  消费者需要别的内容时加种类，不改这两个的含义。
- **上限**：单个内容 4 MiB，16,384 个，合计 256 MiB（宿主内存；x86 只有索引）。
- **引用**：标注 schema `GeometryRef=3`、`BonesRef=4`，记录体 16 字节 `{键, 修订号}`。draw 消息到达时宿主逐条核对
  “存活、修订号相同、种类与 schema 相符”，有一条不成立整条 draw 被拒绝，执行器看不到悬空引用。
- **x86 不留副本，只留索引**：键 → 修订号、字节数、种类。两端跑同一个 `ContentIndex`，x86 在本地拒绝宿主会拒绝的一切，
  所以它放行的内容宿主一定接受。于是异步档位下各块不等回复，宿主的拒绝是协议故障、终止会话；同步档位下同样按故障处理。
- **顺序**：上传和释放是有序屏障，先冲刷已暂存的 draw。“下一条 draw 的记录”已经取走还没提交时，上传和释放被本地拒绝
  （那些记录可能正指着要被替换的内容）。每次上传都会切断批次，所以一帧的骨骼矩阵应在这帧的 draw 之前集中上传。
- **会话重置**：`SessionReset` 成功时宿主清空仓库，x86 清空索引并丢弃还在等 draw 的记录；修订号继续递增。
  内容身份属于一张图，换图后旧身份全部失效。
- **记录器**：提交折入 `(5, 种类, 键, 修订号, 字节数, 全部内容)`，释放折入 `(6, 键, 修订号)`；引用记录和别的 draw 记录一样折入。
  夹具独立折同一序列，摘要相等即顺序、内容、绑定都相同。
- **导出**：`WarVKD3D9UploadContent@28`（返回修订号）、`WarVKD3D9ReleaseContent@20`、`WarVKD3D9ReadContent@32`；
  引用经已有的 `WarVKD3D9AnnotateNextDraw`。
- **冷输出行**：`D3D9 content-proxy:`、`D3D9 content-host:`，只在协商了 Annotations 的会话打印。

### 7.2 有界上传窗口（`d3d9_upload_window.h`）

内容驻留（10-30）把 x86 副本改成按预算淘汰，但每次 `Lock` 仍要先有一份整块副本：被淘汰的缓冲要整块分配，
NOOVERWRITE 追加还要把已初始化前缀整段读回。窗口去掉的是“只写的 Lock”这一类。

- **规则只有一条**：`Lock` 的范围里没有任何应用已经定义的字节，就借一块窗口，`Unlock` 发送后归还，x86 不留副本、不读回。
  - 顶点缓冲带 DISCARD 的 `Lock`（D3D9 规定旧内容未定义）；
  - 顶点缓冲从 `definedEnd` 或之后开始的 `Lock`。`definedEnd` 是创建或上一次 DISCARD 以来写过的末尾：
    游戏的环形缓冲（DISCARD 回到 0，再 NOOVERWRITE 依次追加）每一次都满足，静态缓冲的第一次整块 `Lock` 也满足；
  - 纹理某一级还没初始化时的 `LockRect`（整级清零的窗口，与原先值初始化的副本语义相同，部分写也照旧提交整级）。
- **不走窗口的**：索引缓冲（本地索引校验要读内容，热的索引缓冲本来就驻留）；范围里有已定义字节的 `Lock`
  （部分改写、只读、重锁）。它们走原有驻留路径，预算只为这些真的要读回的内容服务。
- **窗口池**：64 KiB 粒度，取能放下请求的最小空闲块；归还后空闲总量超预算就按最久未用淘汰，
  本身就超过预算的块归还即释放。**上界只管空闲一侧**：借出去的窗口是应用自己持有的指针，数量由应用的并发 `Lock` 决定。
  设计稿原先写的“窗口满即背压”不成立——`Lock` 必须立即返回可写内存，没有可等的东西。
- **清零**：每次借出把请求范围清零。应用没写的字节因此是确定的 0，不会把上一个资源的数据带到下一个里。
- **DISCARD 换存储**：宿主侧已有（stream 档位换存储不等 GPU）。x86 侧现在连整块副本和读回都没有了。
  宿主换存储时仍把已初始化前缀搬到新存储（每次至多一个环，游戏约每 23 帧一次），保持未写字节确定，不改。
- **开关**：`WARVK_D3D9_UPLOAD_WINDOW_KIB=<KiB>`（空闲预算，0..65536），必须同时设置驻留预算，否则拒绝创建设备。
  未设置时行为与之前逐字节相同。

### 7.3 默认 x86 内存档位

`DefaultBackingKiB=32768`、`DefaultUploadWindowKiB=1024`（`d3d9_upload_window.h`，wire 单元测试钉住，门里有对应的臂）。

- 有了窗口，驻留预算不再是“稳态成本”而是**上限**：只有被重锁、部分改写、只读加锁的内容才会在 x86 留副本，
  一次性加载的纹理和每帧重写的动态顶点缓冲都不占它。32 MiB 约是 2 GiB 用户地址空间的 1.6%，
  能放下 20 多张 512×512 满 mip 链纹理的重锁工作集；真正需要更多的图，代价是同步读回而不是出错。
- 1 MiB 空闲窗口正好是游戏最大的一次 `Lock`（512×512 的一级），稳态下所有只写 `Lock` 复用同一块，不再分配。
- 开发代理保持显式开关（未设置 = 旧的完整副本），冻结的门禁臂不变；产品接入（阶段 5）时由设备所有者默认采用这组值。
  游戏里的重锁普查（哪些纹理每帧 `LockRect`）要到接线后才有，届时只需改这两个常量。

## 8. 验收

1. **环单元测试（32/64 位）**：填满、跨尾、精确边界、背压；§3 每条规则各一个反例；双线程随机长度压力并核对内容与顺序；
   回复槽正反例；两种位宽下布局偏移相同。
2. **真实宿主的协议反例**：raw 对端挂接环后发送每一种坏记录，宿主都以对应故障码自停，且不执行其后的记录。
3. **故障注入（真实 Connection）**：杀宿主、卡宿主、宿主发布坏的 `head`/`applied`/回复头；每种都在期限内
   fail-closed，报告类别正确。
4. **GPU 参照门**：环模式下像素哈希与管道模式、与进程内参照逐个相同，VVL 0 错误。
5. **准入测量**：同一轮内环模式对管道模式（1,025 draw 合成帧），只在同一轮内比较。
6. **x86 地址空间**：环模式比管道模式多出的映射只有 §4 列的三项。

## 9. 已知限制

- `Connection` 的序号仍是 32 位：每秒 6 万条消息时约 20 小时用尽并 fail-closed。环本身按 64 位序号设计；
  `Connection` 成为产品所有者时（阶段 5）一并加宽。
- 宿主仍是单线程执行：一条长时间的记录（大型管线编译）期间不消费。期限按 §4 计。
