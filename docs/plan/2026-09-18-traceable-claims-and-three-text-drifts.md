# 让"fail-visible"声明变得**可追溯**；并归纳三处"文字失真"的共同规则 — 2026-09-18

## 1. 本轮改动：把一句隐式断言变成可追溯的

`war3_palette_object_evidence.h:60-61` 原文声称：

```cpp
// 取值 5 是**故意**取的：版本 1/2 读方的阶段表不含它，因而会直接拒绝整份导出，
// 而不是静默忽略（fail-visible）。
```

**这句话曾有一段时间是假的** —— 读方的 `STAGES` 那时是**版本无关**的，v1/v2 遇 stage=5
只被加一个软标记、**并不拒绝**整份导出（独立对抗性审计正是以此判定"③ 保留既有拒绝恢复链"不成立）。

我在 round 218 的 P0 修复中补回了版本门控（`LEGACY_STAGES` + 按版本选表），
**这句话因此重新为真**。

但它是**隐式**的：读者看不出机制在哪、更不知道它曾失真。已补记：

| 补记内容 | 作用 |
| --- | --- |
| 明确指出这句话**曾有一段时间是假的** | 让人知道这类断言会悄悄失真，必须能指向实现 |
| 指名机制：`LEGACY_STAGES`（只含 1..4）+ 按 `version >= PALETTE_OBJECT_FIRST_SIGHT_VERSION` 选表 | 读者可自行核对 |
| 指名失败形态：`lookup()` 的 `require` 抛 `ValueError: unknown palette stage 5` | 可被搜索 |
| 指名锁：`test_first_sight_stage_is_rejected_wholesale_under_legacy_version` | **断言有人看守** |
| 说明该锁的**判别性**：v∈{None,1,2} 断言整份拒绝 + v=3 断言接受 | 钉住"版本门控"而非"一律拒绝" |

## 3. 归纳：本项目已发现三处"文字失真"，共同规则如下

| # | 位置 | 失真内容 | 后果 |
| --- | --- | --- | --- |
| 1 | `analyze_palette_object_evidence.py` 的 `check_header_block`（driven by `test_palette_object_wire_roundtrip.py`） | docstring 称"生产导出必须是版本 2" | v3 出现后失效；G 一跑就失败（round 231-232 查明并修复） |
| 2 | `war3_palette_object_evidence.h:58-62` | 称"版本 1/2 读方会直接拒绝整份导出" | **曾失真**（读方版本无关）；round 218 修复后重新为真；**本轮补上机制与锁** |
| 3 | `war3_palette_object_wire_roundtrip_test.cpp:221` | 称"与生产采集点的真实取值一致" | **仍为假**；掩盖了"生产身份形状零覆盖"（round 235 更正为对照表） |

### 共同规则（建议后续遵守）

```
任何"某处会保证 X"的注释/文档，必须同时给出：
  (a) X 的实现位置（file:line 或符号名）
  (b) X 的失败形态（错误信息/断言名），以便可搜索
  (c) 看守 X 的测试名（若有）
否则该断言无法被复核，且会在实现变更后**静默失真**。
```

### 为什么值得单列

```
代码 bug      -> 会被测试/门禁抓到
假注释        -> 不会被任何东西抓到，且会让后来者以为某件事已被保证/覆盖
```

第 3 处的教训最重：那句假声明**主动掩盖了一个覆盖缺口** —— 读到它的人（包括我自己在多个轮次里）
会以为生产身份形状已被测试覆盖。
