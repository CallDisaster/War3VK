## 1. 结论

- **真实游戏已经在 x64 宿主上跑起来了。** 沙盒里的 War3 1.27 把开发代理当作 `d3d9.dll` 加载，全部 D3D9 调用进宿主，
  画面由宿主画到游戏自己的窗口上。Lost Temple、stormtide、(2)EchoIsles、“生与死”四张图都进了图，画面正确，
  游戏没有碰到任何一个代理未实现的 D3D9 入口，退出时宿主与三条会话全部干净结束。
- **这只是“原版画面”。** 这一段（5.1-a）跑的是裸代理：没有数据层，所以没有阴影、天气、后处理、控制面。
  数据层进代理模式是后面四段（5.1-b 到 5.1-e）的事，本文件给出它们的形状与验收条件。
- **本文件定了三件事**：产品在代理模式下由什么组成（§4）；蒙皮投射体先走“在游戏的 draw 上发记录”（§6.1）；
  宿主崩溃是终止性的，不做热恢复（§6.2）。

## 2. 5.1-a 量到了什么

探针是 `AutoTest/run_x64_game_proxy_probe.py`（开发探针，不是门）。运行条件与现有实机门相同：专用沙盒的新实例、
自有的非输入桌面、受限 Medium 令牌、Job；不动全局输入、注册表、前台窗口与玩家目录。

| 事实 | 数值 |
|---|---|
| 游戏建设备的方式 | `Direct3DCreate9` 三次（前两次只查元数据，各 2 条与 104 条消息），第三次 `CreateDevice`；都在窗口线程上 |
| 交换链参数 | 窗口化，后备缓冲 0×0（取客户区，实测 1520×764），X8R8G8B8，DISCARD，D16 自动深度，`LOCKABLE_BACKBUFFER`，间隔 DEFAULT，行为标志 0x42 |
| 一帧的规模（Lost Temple） | 约 236 次绘制、555 条消息；45 秒 110 万条消息全部应用 |
| 未实现入口 | 0（193 个未实现入口都带首次调用跟踪，一次都没响） |
| x86 专用字节（产品内存配置，无数据层） | Lost Temple 100 MiB，stormtide 75 MiB，EchoIsles 88 MiB，生与死 527 MiB |
| x86 低 2 GiB 可用地址空间 | Lost Temple 1634 MiB，生与死 1102 MiB（最大空洞 659 MiB） |
| x86 进程里的 `vulkan-1.dll` 与显卡驱动模块 | 没有 |
| 窗口缩放、最小化与恢复、`WM_ACTIVATEAPP`、暂停键 | 传输与宿主正常：2 次窗口重置、0 次失败；缩放后的画面布局不对（§6.3） |
| 退出 | 图内 `WM_CLOSE` 得到游戏自己的“确认退出”对话框，确认后进程返回 0，宿主正常返回，资源计数归零 |
| 宿主崩溃（探针终止自己的宿主） | 代理立即得到 `host-exited`，`Present` 返回 `D3DERR_DEVICELOST`；游戏不崩、不挂，之后仍能正常退出，返回 0 |

内存数字是下限：数据层进来后会加上它自己的占用。与进程内模式的同图对比是 5.2 的门。帧率没有结论：
本机同时在跑别的重负载，而且原版游戏在窗口不活动时自己降速（进程内模式由数据层的钩子关掉这一条）。

没有覆盖的：换图（裸代理没有控制面，§5 的 5.1-c 补）、真实的 Alt+Tab（隔离桌面上没有前台切换，只能发
`WM_ACTIVATEAPP`）、“生与死”的世界画面（开局是黑色迷雾，界面正确，世界区域要等控制面开全图后再看）。

## 3. 让真实游戏进来改了什么

实验室代理原先拒绝真实游戏的五个地方，每个都是有意的限制，现在按下面的方式放开：

1. **资源表**（`d3d9_resource_registry.h`）：64 个 id 改为 16384 个，`reserve()` 从“最低空闲提示”开始找，
   仍然返回最低空闲 id；宿主的纹理槽随之放大，槽位查找从平方改为一遍。游戏一张图约 2100 张纹理。
2. **Game.dll 拒绝**：仍是默认行为。只有 `WARVK_D3D9_GAME=sandbox-isolated-v1` 加上非输入桌面才放行
   （`d3d9_window_identity.h` 的 `GameSandboxProfile()`）。玩家环境里这个变量不存在，守卫照旧。
3. **“设备不在窗口线程上建”**：实验室的所有者线程从不泵消息，所以要求窗口在别的线程；游戏在窗口线程上建设备，
   游戏配置下放行。所有者线程的等待不泵消息，实测没有出现宿主的 WSI 等窗口线程的死锁（缩放、最小化都跑了）。
4. **宿主按 PID 打开父进程**：游戏进程的 DACL 拒绝受限令牌的 `OpenProcess`（错误 5）。改为父进程把自己的句柄
   （只有 `SYNCHRONIZE` 与 `QUERY_LIMITED_INFORMATION`）交给宿主继承，宿主核对 PID 与创建时间后收下
   （`ShareSelf` / `AdoptPeer`）。三个参数的旧启动方式保留给直接起宿主的夹具。
5. **交换链的 `LOCKABLE_BACKBUFFER` 标志**：游戏配置下接受；锁后备缓冲仍未实现（游戏的截图路径，§7）。

另外两处是游戏才会碰到的情况：游戏在两个 Direct3D9 对象之间卸载并重新加载 `d3d9.dll`，所以每条连接的宿主日志取
“下一个不存在的 `<log>.<n>`”；宿主的传输失败现在打印故障、阶段与 Win32 错误码。

## 4. 产品在代理模式下由什么组成

同一个 x86 `d3d9.dll`，两种模式（路线图不变）。代理模式下它只跑数据层，不建进程内的 Vulkan 设备。
首次接线时，D3D9 前端用**现在这个代理的二进制**，作为同目录的另一个 DLL 被产品 DLL 加载：这样游戏里跑的前端
就是对照门测过的那一份。两者合成一个二进制是发布前的打包问题，接口不变。

```
Game.dll ──D3D9 调用──▶ 产品 d3d9.dll（代理模式）
                          │  Direct3DCreate9：加载前端，包一层工厂
                          │  工厂.CreateDevice：转给前端，拿到设备后装 Game.dll 钩子、发布设备服务
                          ▼
                        前端 DLL（d3d9_proxy.cpp）──命令环──▶ x64 宿主（DXVK、全部特效）
                          ▲
   数据层（钩子、JASS、注册表、控制面）──记录/标记/会话重置──┘   （前端已有的 WarVKD3D9* 导出）
```

- **数据层 → 前端**：已有导出就够（`SetFrameScene`、`AnnotateNextDraw`、`MarkStage`、`RequestSessionReset`、
  `UploadContent`、`ReadPresentedImage` 等），它们收设备指针，另一个模块可以直接调用。
- **前端 → 数据层**：新增一个观察者（唯一的新导出 `WarVKD3D9SetObserver(device, observer)`），四个回调，
  都在 D3D 线程上：

  | 回调 | 时机 | 数据层用它做什么 |
  |---|---|---|
  | `draw` | 每次绘制发出之前 | BeforeUi 判定、相机采样、投射体记录（对应进程内 `DrawIndexedPrimitive` 里的三处） |
  | `present` | `Present` 发出之前 | 帧记录收尾、BeforeUi 的兜底插入、控制面的截帧与就绪标志 |
  | `resized` | 窗口重置成功之后 | 改写 War3 内部分辨率字段并通知界面（§6.3） |
  | `terminal` | 连接进入终止态 | 宿主崩溃处理（§6.2） |

  实现后是五个回调（`src/d3d9/war3/core/war3_d3d9_observer.h`）：多了一个 `released`（设备销毁前，数据层撤回设备服务）；
  `terminal` 带一个事实结构（`WarVKD3D9TerminalFacts`：终止种类、宿主退出码、已发布与已应用的序号、宿主日志路径）。

  `draw` 回调只带这次绘制的参数；数据层要的状态（变换、FVF、纹理、渲染状态）用设备的 `Get*` 读，
  代理这些读取都从本地缓存回答，不过进程边界。不包 119 个设备方法：合成一个二进制以后，观察者就是一个内部接口，
  而包装层会变成“同一个 DLL 里对自己做 COM 转发”。
- **`IDeviceServices` 的代理实现**（`war3_execution_services.h` 已写明每一项的去向）：世界渲染边界 → 两个阶段标记；
  地图纪元重置 → 会话重置请求；材质着色器 → 设备的 `CreateVertexShader` / `CreatePixelShader`；
  设备状态 → 连接是否健康；GPU 蒙皮桥、验证宿主、实例缓冲 → “不可用”（发布版本来就关着或只供进程内）。
- **模式开关**：5.1 期间只有沙盒开关（§3 第 2 条）。玩家可见的开关、宿主文件放哪、输入桌面上的呈现配置是 5.3 的决定。
- **一个进程一个宿主**：现在三个 Direct3D9 对象各起一个宿主。产品 DLL 常驻，可以让前两个只查元数据的工厂复用
  同一条连接（或缓存第一次的答案）。启动多出的约 1.5 秒归 5.1-b 一并处理。

## 5. 分段

每段的验收都在沙盒里用探针或现有实机门跑；x86 进程里始终不得出现 `vulkan-1.dll`。

**5.1-a 原版画面（完成）。** §2、§3。

**5.1-b 产品 DLL 的代理模式。**
- `Direct3DCreate9` 的模式分支与工厂包装（`d3d9_main.cpp:212`、`d3d9_interface.cpp:485` 的对应物）；
  前端加观察者导出。
- 代理模式的 `IDeviceServices`，在设备建好后发布、销毁前撤回（对应 `d3d9_device.cpp:8984 / 9009`）。
  `Hook_FlushSortedItems` 等还拿具体设备类型的地方改走接口。
- 控制面：`capture_final_frame` 用 Target 回读；`wait_until` 的就绪标志由 `draw` 回调给。
- 验收：产品 DLL 以代理模式进 Lost Temple，Game.dll 钩子装上，控制面能截帧、能 `EndGame`，
  正常退出走现有的 `native_game_exit_acceptance`；画面与 5.1-a 相同（还没有特效）。
- **结果（11-16，完成）**：模式开关是环境变量 `WARVK_D3D9_FRONT=<前端 DLL>`（只在沙盒配置下有效）；入口在
  `war3/platform/war3_proxy_mode.cpp`，设备服务在 `war3_proxy_services.cpp`。与设计不同：三个 Direct3D9 对象仍各起一个宿主
  （合并没有做）；控制面的截帧按设计走后备缓冲的 Target 回读（`GetRenderTargetData`）。

**5.1-c 记录的生产端（不含投射体）。** 4c 设计 §8 的第一条。
- 阶段标记来自 `Hook_WorldRenderScene`；BeforeUi 在世界渲染出口（tier 10）发，`present` 回调兜底。
- `Camera` 来自 `draw` 回调里对 VIEW/PROJECTION 的采样（进程内 `War3RecordWorldCamera` 的判定原样搬）。
- 设置类记录（雪、SSAO、抗锯齿、Bloom 与色调映射）、`Lighting`、`ShadowFrame`、`PointLights`、
  `VolumetricLight`、`Outline`：值都已经在数据层，按 4a / 4c 的记录格式逐帧发。
- `FogVolumes`：给 `War3FogVolumeManager` 加只读的列出接口（按作者原值）；每帧都发（没有记录等于没有雾体积）。
- `SessionReset`：`war3.cpp` 的地图卸载路径调用；同时核对进程内卸载做的其他清理在宿主里有没有对应物。
- 验收：三张图上天气、SSAO、抗锯齿、Bloom、体积光、雾体积、描边可见；**换图**（控制面 `EndGame` 后再载图）
  前后阴影与特效状态正确，宿主显存不随换图增长。
- **结果（11-16，完成，描边除外）**：生产端在 `war3/platform/war3_proxy_frame.cpp`。设计里没有的三件事：
  1. **设置解析搬成两种模式共用的一份。** 管线构造函数里的环境变量覆盖与每帧设置解析原样搬到
     `war3/render/war3_settings_resolver.cpp`，进程内管线与代理模式的生产端都调它。
  2. **日夜太阳解析搬成共用头文件。** 阴影 pass 里的时间平滑与太阳方向、颜色解析原样搬到 `war3/effects/war3_sun_cycle.h`。
  3. **固定管线的世界光照。** 进程内设备在世界场景里改写 0 号灯、材质环境光与 `D3DRS_AMBIENT`，宿主没有对应物。
     现在由前端在组装每个 draw 的固定管线状态时改写（新导出 `WarVKD3D9SetWorldLighting`），值由数据层给。
  换图用新增的测试命令 `game.restart_for_map_test`（调游戏自带的 `RestartGame`）验收：会话重置被宿主接受、0 拒绝、x86 专用字节不涨。
  没有做到的：描边没有在游戏里验证；换到另一张图没有跑（只重开同一张图）；宿主显存没有逐代记录。

**5.1-d 投射体。** §6.1。静态投射体与游戏自己 CPU 蒙皮的单位都在 `draw` 回调里发 `ShadowCaster`
（alpha 测试的发 `ShadowCasterAlpha`）；身份字段换成稳定键（4c 设计 §8）。量一帧几千个投射体时
`AnnotateNextDraw` 的开销。验收：三张图有太阳阴影与点光阴影；与进程内同机位截图对照，列出差异。
- **结果（11-17，完成）**：生产端在 `war3/platform/war3_proxy_casters.cpp`。调研改了这一段的前提：默认配置下进程内只有
  地形、树木与装饰物、桥与坡道三类 draw 走“逐 draw 采集”，单位是在 BeforeUi 时由语义场景按 geoset 与姿态重建的。
  所以“在游戏的 draw 上发记录”对前三类是照搬进程内，对单位是一条新路线（§6.1 的已知缺陷只落在单位上）。
  生产端在发记录前自己拒掉宿主不收的 draw（三角带、位置不在 stream 0 或不是 FLOAT3、固定管线顶点混合、
  alpha 测试投射体的 UV 不在 stream 0 或不是 FLOAT2）。四张图上宿主 0 拒绝。
  顺带补了前端的 `DrawPrimitiveUP`（stormtide 的闪电用它；没有它时这张图的会话以失败结束）。
  点光阴影没有在游戏里单独验证。

**5.1-e 生命周期与故障。**
- 窗口缩放（§6.3）、全屏按无边框窗口处理（§7）、`NotifyWindowActivated` 的对应物、真实暂停下特效的时间行为。
- 宿主崩溃（§6.2）。
- 验收：缩放后界面与世界布局正确；宿主被终止后玩家得到提示、报告写出、进程按设计结束。
- **结果（11-17，完成）**：
  - 缩放：`resized` 回调改写分辨率字段，布局正确。“通知界面重排”在两种模式下都没有命中（找不到窗口的消息目标），
    界面文字是按新尺寸缩放而不是重新生成——与进程内相同，不是代理模式的差异。
  - DPI：进程内模式默认把进程设为系统 DPI 感知（`d3d9.dpiAware`），代理模式原先没有，后备缓冲因此是逻辑像素
    （1520×764 对 1902×963）。现在代理模式在建工厂前做同样的设置，宿主启动时采用游戏进程的 DPI 感知。
  - 全屏：全屏请求的模式等于主显示器当前模式时接受，前端把窗口做成覆盖显示器的无边框置顶窗口；不改显示模式，
    其他模式仍然拒绝。
  - 窗口激活：进程内的 `NotifyWindowActivated` 默认是空操作（`d3d9.deviceLossOnFocusLoss=false`），没有东西要搬。
  - 真实暂停：雪继续下、其余画面冻结，两种模式相同。
  - 宿主崩溃：§6.2 原样实现；没有尝试存档。

5.2 的门（同图地址空间 A/B、帧时间、视觉对照、5 个实机门在代理模式下重跑）在 5.1-e 之后。
**结果（11-17）**：A/B 门是 `AutoTest/run_x64_phase52_ab_gate.py`，数字与没有过的项见回执 §6。

## 6. 三个决定

### 6.1 蒙皮投射体：先走“在游戏的 draw 上发记录”

两条路（4c 设计 §7、§8）：在游戏自己的 CPU 蒙皮绘制上发 `ShadowCaster`；或者数据层的 geoset 走内容载荷、
骨骼走 `BonesRef`。**先走第一条。** 理由：

- 执行端已经具备（4c-2 的动态缓冲投射体），x86 一个字节都不多留，不动传输的封口语义；
- 第二条每帧要送全部单位的骨骼矩阵，并且要回答 `dynamicPose*` 怎么进宿主的封口，是一段独立的传输设计；
- 第一条的已知缺陷是确定的、可量的：游戏不画的单位（视野外）没有影子，影子本该伸进画面的那部分会缺。

5.1-d 在三张图上把这个缺陷量出来（与进程内同机位对照）。只有当它在 5.2 的视觉对照里不可接受时，才做第二条；
到那时第二条是在一个已经跑通的系统上加一种投射体来源，而不是首次接线的前置条件。

**实现后（11-17）**：按第一条做了。5.2 的同机位对照里，画面内的单位、建筑、树都有影子，布局与进程内一致；
视野外单位缺影这一条没有专门造机位去量（对照用的是开局机位，画面边缘没有单位）。是否要做第二条，等作者看过对照图再定。

### 6.2 宿主崩溃：终止性的，告知玩家后结束

实测（§2）：宿主死后游戏进程是健康的，只是画面冻结，`Present` 一直返回设备丢失。

不做热恢复。按 D3D9 的设备丢失协议让游戏 `Reset` 是可以把 DEFAULT 池的 3 个缓冲重建出来的，但两千多张 MANAGED
纹理的内容在产品内存配置下只存在于宿主（x86 只留 32 MiB 的回读预算）；要能恢复就得在 x86 留全部副本，
这正是这次迁移要拿掉的内存。与路线图“待作者确认”第 2 条的建议一致（作者尚未确认）。

5.1-e 的行为：`terminal` 回调里，数据层写报告（终止种类、宿主退出码、已发布与已应用的序号、宿主日志路径），
弹出一条说明，然后结束进程。可以评估的一步：结束前在单人游戏里经数据层已有的 JASS 通道存一次档
（游戏逻辑此时是活的）；做不做看实测是否可靠，不作为 5.1-e 的验收条件。

**实现后（11-17）**：`war3/platform/war3_proxy_host_lost.cpp`。顺序是写报告 → 弹窗 → `TerminateProcess`，退出码
`0xE0574B01`。报告是 `<游戏目录>\WarVK\Log\render-host-lost.txt`（种类、宿主退出码、已发布与已应用的序号、宿主日志路径、
已呈现帧数、后备缓冲尺寸）。弹窗只在玩家看得见的桌面（`Default`）上弹，`DXVK_WAR3_HOST_LOST_DIALOG` 可以强制开或关；
与启动失败的弹窗共用 `war3_player_notice.cpp`。结束前存档没有做。

### 6.3 窗口缩放：前端重置交换链，数据层改写游戏的分辨率字段

前端已经照进程内的窗口钩子做了前一半：窗口的 `WM_SIZE` 不交给游戏，所有者线程在下一个与尺寸有关的调用处重置
交换链。实测两次重置都成功，但游戏仍按 1520×764 设视口，画面布局不对——进程内模式的后一半
（`TryOverrideWindowedClientSize`、`TryNotifyWindowedUiSizeChanged`）在数据层里。5.1-e 在 `resized`
回调里调用这两个函数；回调在 D3D 线程上，而游戏的 D3D 线程就是窗口线程，与进程内在 `WM_SIZE` 里做是同一个线程。

**实现后（11-17）**：照此实现（`war3_proxy_services.cpp` 的 `ObserveResized`）。分辨率字段改写成功，世界与界面布局正确。
`TryNotifyWindowedUiSizeChanged` 在两种模式下都返回失败（“找不到窗口的消息目标”，现在日志里带原因），
所以界面文字在两种模式下都是缩放出来的；这是进程内原有的行为，没有在这一段修。

## 7. 这份设计没有回答的事

- **覆盖层（设置面板）。** 数据层只产生 ImGui 的绘制列表。建议的路线是数据层自己经代理的 `IDirect3DDevice9`
  把列表画出来（动态缓冲、带纹理的 FVF 绘制、裁剪矩形，都是代理已有的调用），宿主不加代码；
  要先核对代理对这种 FVF 与 `Present` 前插入绘制的支持。没有覆盖层就不能给玩家试用，但不挡 5.1-b 到 5.1-e。
- **全屏（已做，有限制）。** 代理只接受窗口化交换链；游戏不带 `-window` 启动时 `CreateDevice` 会被拒绝。
  5.1-e 要把全屏请求按无边框窗口处理（进程内模式的全屏也不是独占全屏），在此之前探针一律带 `-window`。
  5.1-e 之后：模式等于主显示器当前模式的全屏请求按无边框窗口处理；别的分辨率仍然拒绝（不改显示模式）。
- **锁后备缓冲**（游戏的截图）。标志已接受，`LockRect` 未实现；可以用 Target 回读实现只读锁。
- **宿主里的诊断怎么回到游戏内面板**（4c 设计 §8 原样保留）。
- **帧时间。** 5.1-a 没有可用的帧时间数据（§2）。命令环统计里每帧约 90 条同步记录，是 5.2 帧时间门要看的第一个地方。
  5.2 量到了：代理模式的帧率是进程内的几分之一，远超过提议的 1.5 倍（回执 §6.2）。每帧约 78 条同步记录、
  约 45 次 GPU 提交；按调用分的同步次数还没有统计，这是帧时间工作的第一步。
- **x86 产品 DLL 的静态 TLS（5.2 发现）。** llvm 构建的产品 DLL 带 3.22 MiB 的 TLS 模板，游戏进程的每个线程各一份
  （代理模式 45 个线程约 145 MiB）。怎么处理由作者定（回执 §6.3）。
- **输入桌面上的呈现。** 现在的呈现配置要求非输入桌面，这是测试安全约束，不是产品形态；玩家环境的配置归 5.3。
