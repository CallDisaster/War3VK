# ③ 配额论证：约束是**会话预算被逐帧重复耗尽**，不是「对象太多」— 2026-09-18

## 1. 三个数

```
kNormalBudget              = 3584
emitted - terminalEmitted  = 3648 - 64 = 3584      <- 精确打满
firstSightInserted         = 64                    <- 只能让 64 个对象进入
场景中不同 caster 键        >= 107（修正① 之前实测）
```

## 2. 代码结构：为什么「逐帧重复」是主因

`war3_palette_object_evidence.h` 的 `Entry` 有阶段标志 `sawServed` / `sawSubmit` / `sawDraw`（h:112-113）。
这些标志供**终态判定**用（`:255` 的 `closedChain`），但 S/E/D 三点**没有**「已发过就跳过、不消耗配额」的抑制：

- FirstSight（`NoteFirstSight`）：**修正① 后按条目去重**（本次改动）；
- Served（`:474` `e->sawServed = true;`）：无抑制；
- Enqueued（`:519` `e->sawSubmit = true;`）：无抑制；
- Drawn（`:563` `e->sawDraw = true;`）：无抑制。

⇒ **每帧对同一对象重复发射 S/E/D 是设计行为** —— 每条记录携带自己的 `frames.renderFrame`，
逐帧信息本身就是证据的一部分。

## 3. 结论

```
会话预算 kNormalBudget=3584 被逐帧重复的 Enqueued/Drawn 耗尽
=> 耗尽后，新对象的 NoteFirstSight 因 CanEmit 失败而无法建条目（修正② 之后）
=> 只有 64 个对象能在耗尽之前进入，其余 ~43 个完全不可见
```

三种做法的代价：

| 做法 | 效果 | 代价 |
| --- | --- | --- |
| (a) 提高 kNormalBudget | 更多对象可见 | 改变取证开销（编码/内存/导出体积），须单独论证 |
| (b) 让 S/E/D 按对象去重 | 同样能让更多对象可见 | 放弃逐帧信息 —— 而逐帧到达正是这些阶段的主要证据 |
| (c) 保持现状 | 64 条**有真实链首的完整链** | 其余 ~43 个不可见（不伪造、不撒谎） |

## 4. 建议：保持现状 (c)

1. 修正② 之后的现状是**诚实的** —— 可见的 64 条链每条都有真实链首（实机 64/64）；
2. **不可见 ≠ 错误** —— 对象没有被伪造出一条链，只是没有证据；
3. **(b) 是有害的** —— 它会让「某对象在某帧被提交」这类事实消失，而那正是 S/E 点存在的意义；
4. **(a) 需要独立论证** —— 前提是「多出的那批对象是否真的需要证据」，而这一点**当前无法回答**
   （我们不知道那些对象是什么、是否重要）。

⇒ **在拿到「为什么需要它们」的证据之前，提高预算不是可以顺手做的改动。**

## 5. 本轮结论的两点限定

- `emitted-terminal=3584` 读自 **AFTER 运行（`INPUTS=0`）**。round 261 已确认两次运行 `INPUTS` 不同
  ⇒ **阶段构成类数字不可跨运行比较**；但「同一运行内预算打满」这一自洽关系（3584 就是该运行的
  `kNormalBudget`）**不受影响**。
- `107` 来自**修正① 之前**的运行 ⇒ 它证明「场景确有 >=107 个不同 caster 键」，
  但**不同运行的键集合未必相同** ⇒ 结论「预算是约束、现状诚实可辩护」成立，
  但「恰好 43 个对象被牺牲」**不应作为精确数字引用**。
