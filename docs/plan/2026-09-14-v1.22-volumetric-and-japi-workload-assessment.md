## 当前核实的规模和缺口

### API 清单不是渲染生效证明

- `WarVK/jass/warvk_api.j` 有 109 个公开函数，后端命令表有 106 条命令，
  `WarVK/action.txt` / `call.txt` 有 92 个唯一 GUI script 入口。三者口径不同，不能混为一数。
- 当前 smoke 源码在 6 个 helper 中提及 36 个不同公开函数，主要覆盖点光、闪电与数学；
  这是源码提及数，不是 36 个 API 已经通过运行验收。
- `war3_japi_v1_protocol_test.cpp` 的 backend stub 验证协议到分发，不能证明实际渲染状态或像素改变。
- 11 条已暴露 JASS 包装的命令被 implemented feature mask 排除：
  `outline.setEnabled/setColor/setParameters`、`bloom.setEnabled/setParameters/setRadius`、
  `postfx.setEnabled/setExposureGamma/setColorGrade`、`aa.setMode/setSharpness`。
  它们会返回 `UnsupportedFeature`；没有查询诊断的 void 包装调用容易被理解为“静默不生效”。
  现有静态合同要求这些包装存在但暂不在 GUI 中展示，不得将其误报为已实现或已通过。

全量校验的交付应为逐项状态表：支持且有执行证据、明确不支持、失败待修；
每条关联参数/返回或错误、能力位、运行前提、生命周期和实机效果。
如果本版要求所有公开包装都可用，补齐上述 11 条是额外实现工作，不能用隐藏错误代替完成。

### 太阳 API：已发现源码语义不一致，尚未完成玩家复现

在本 release 基础中：

1. `WarVK/action.txt` 称该入口为“启用太阳光”，JASS 包装发送 `sun.setEnabled`。
2. `war3_japi_v1.cpp` 的 `SunSetEnabled` 分发确实写入 settings mailbox 的 `sun.enabled`。
   所以不是简单的“整个太阳命令没有分发实现”，也不属于上述 11 条 unsupported 命令。
3. `D3D9DeviceEx::SetLight` 对 Light 0 的 `sun.enabled=false` 分支保留传入的原生灯并返回；
   没有将其直射贡献置零。此路径实际是“停止覆盖原生太阳”，不是“世界没有太阳”。
   ImGui 的文案也明确叫“太阳光覆盖”。
4. 体积散射/体积太阳阴影消费者又用该布尔量决定是否有有效太阳；部分自定义材质参数路径
   读取 `sun.intensity` 时没有在同处合入 `sun.enabled`。需按实际 material/pass 激活条件逐一验证，
   不能据此推断玩家地图一定经过这些路径。
5. 默认昼夜系统拥有方向/颜色，手动写入可被后续帧的自动控制取代；已有独立 ownership 开关。
   必须分别复现“启停语义”和“方向/颜色被自动更新”两类问题，不能混成一个根因。

首个测试用例应在固定时刻/机位/曝光下分别切换原生覆盖、直射强度、CSM、体积太阳，
同时读回 requested/applied 状态与能力/错误。保留环境光、点光与自发光，不能以全屏变黑作为
唯一成功条件。先确认作者希望的关闭语义与兼容策略，再改产品行为，避免破坏旧地图。

### Froxel / 局部雾 / Guide

已有 High/Medium 网格、三种局部雾体积与最多 8 槽、独立方向阴影 Guide 和重建路径。
尚需的是组合质量、实际后端、作者控制和性能验收，不是重新造一套引擎。

- v1.21 发布说明明确允许最坏 1440p/4K 请求安全回退 Legacy；请求 High 不代表实际在跑 High。
  验收必须包含 requested/effective backend、回退原因及对应帧性能，不能单看设置项。
- 既有 450 万 grid-cell、3.5 亿 traversal 工作量门是安全条件；不以取消或粗暴抬高上限冒充完成。
- Froxel：低俯角/侧视、近远距离、运动相机、时域历史、动态小 caster、阴影泄漏和亮度稳定。
- 局部雾：Sphere/Box/Cylinder、内外穿越、边界/重叠、8 槽与溢出、开关/删除/句柄失效、
  独立全局介质、太阳/点光组合、API 修改与实际采样的对应。
- Guide：细阴影可读性、移动边缘阶梯/闪动、遮挡边界、低分辨率重建、近远切换、额外 GPU 成本。
- 以同图/同机位/同画质 2560×1440 为主要性能基准；1080p/4K另列兼容性，不混用收益。
  如果要求所有最坏场景都无条件维持 High，则是额外算法/预算工程，不在本初评的保守回退假设内。

## 工作量初评

单位为工程人日（约 6–8 小时有效工作），不是保证日历交付时间；不含等待玩家反馈。

| 工作包 | 估计 | 交付物 |
| --- | ---: | --- |
| API 语义清单、太阳复现、测试地图/矩阵设计 | 1–2 | 版本绑定、太阳控制合同与最小可重复案例 |
| 全部 API 端到端校验及已支持接口的问题修复 | 4–6 | 逐项状态表、错误可见性、参数/生命周期/结果验证 |
| Froxel High + 局部雾 + Guide 共享渲染链收口 | 4–7 | 组合视觉与性能证据、后端回退可解释、作者控制可验证 |
| 最终组合回归与发布证据整理 | 2–3 | clean 候选、隔离/玩家回归、更新日志与已知限制 |
| **本次新增范围合计** | **11–18** | 不包含把 11 条 unsupported 包装全部产品化 |

上述 11 条如果要求本版全部补齐，额外暂留 **3–6 人日**，须先确认能复用现有后端，
不是承诺全部都是简单绑定。若实际缺算法/安全所有权则重估。
原版模型点光/白名单点阴影及同步/截图等原有 v1.22 整合余项暂留 **4–7 人日**；
因此整个版本当前首轮预算约 **15–25 人日**，若补齐所有 unsupported API 则约 **18–31 人日**。
随机裂缝或新的 GPU 故障一旦成为阻断项，可能超过这个范围；没有证据不能承诺何时定位。

先用 1–2 人日完成太阳与 API 语义清单后再重估。下周开始推进合理；若理解为下周全部
发布，当前证据不足以作承诺。视觉目标以用户确认的参考/缺陷及可重复场景收口，
不能仅凭静态测试通过或没有报错宣布“开发完毕”。
