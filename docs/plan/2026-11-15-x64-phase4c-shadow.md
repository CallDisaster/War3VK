## 1. 要解决的问题

4a 的模板是“一个特效一份执行器，进程内 pass 是薄适配器”。阴影不能照抄，原因有三个：

1. **体量。** 阴影 pass（`War3ShadowReceiverPass`）是 `d3d9_war3_shadow.cpp` 12.5k 行、`_resources` 1.3k、`_csm` 0.75k、
   `_outline` 1.1k。级联阴影图、点光阴影、体积光用的太阳阴影图、时间滤波、描边都在它的 `Run` 里录成裸命令。
   把它改写成“只认识记录的执行器”等于重写，并且重写出的那一份才是玩家以后跑的代码，两模式对照比的就是新旧两份实现。
2. **输入不是几个数。** SSAO 的输入是 6 个浮点数。阴影的输入是这一帧的全部投射体：每个投射体一份几何（顶点、索引缓冲）、
   一个世界矩阵、包围球、十几个数据层事实；外加 `War3RenderSettings` 里太阳、阴影、昼夜、环境光四个结构的全部字段。
3. **跨帧状态与生命周期。** pass 自己留着阴影图、上一帧的投射体签名、时间滤波的历史。地图切换、设备重置、
   单位被永久移除（墓碑）、阶段策略改变都会让这些状态作废；进程内靠读 x86 的全局量得知，宿主没有这些量。

## 2. 接缝：pass 本身进宿主

**决定：不改写。同一份 pass 源码编进 x64 宿主，宿主补上它编不进来的那部分符号，输入用记录重建。**

这个决定是量出来的，不是估的（`scratchpad` 里的链接闭包脚本，对阶段 3 的 x86 构建）：

- 阴影 pass 的四个目标文件，除 `dxvk`/`util` 以外一共引用 **21 个目标文件里的 65 个符号**，其中**来自 `d3d9_device.cpp` 的是 0 个**。
  也就是说 pass 不认识设备，它认识的是一圈诊断和状态服务。
- 这 65 个符号分两类。闭包为零的辅助文件（负载调节器、混合光追判定、回放校验、点光阴影的 CPU 计划、雾体积）
  直接编进宿主，用的是同一份源码。剩下的（性能监视器、诊断中心、帧证据、着色器管理器、`War3RenderState`、
  对象注册表等）如果编进来会把 `war3.cpp` 和游戏状态一起拖进宿主，它们由宿主的一个服务文件提供。
- pass 源码里只有一行不能在 x64 上编译（把 `VkImage` 句柄截成 32 位用于日志），已改。另加一个不带设备参数的构造函数
  （原来的设备指针从未被读过）。

| 部件 | 形状 | 文件 |
|---|---|---|
| pass | 原样。x86 设备与 x64 宿主编译同一批源文件 | `src/d3d9/d3d9_war3_shadow*.cpp`、`d3d9_war3_csm.cpp`、`war3/render` 里四个辅助文件、`war3/state/war3_fog_volume.cpp` |
| 宿主服务 | pass 引用而宿主不编译的符号。诊断类是空操作；数据层事实类由记录提供 | `tools/render_host/dxvk_core/shadow_host_services.{h,cpp}` |
| 记录 | 光照设置、帧事实、投射体、投射体的 alpha 测试、点光、单位描边、体积光、雾体积，八种记录，一个无依赖头文件 | `src/d3d9/war3/effects/war3_shadow_scene.h` |
| 记录 → pass 输入 | 两端共用的一层函数：把记录和几何变成 `War3PipelineInput` | `src/d3d9/war3/effects/war3_shadow_scene_input.h` |
| 宿主接线 | 会话把带投射体记录的 draw 交给它，BeforeUi 时运行 pass | `tools/render_host/dxvk_core/shadow_before_ui.{h,cpp}`、`d3d9_backend.cpp`、`d3d9_host_main.cpp` |
| 对照 | 一个夹具两种模式；比像素，也比 pass 自己的账目 | `AutoTest/test_render_host_d3d9_shadow.cpp`、`run_x64_shadow_gate.py` |

宿主服务文件的规则（`AutoTest/test_shadow_scene_static.py` 钉住）：不包含设备头文件，不读游戏内存；
诊断出口一律空操作（宿主不产出游戏内的性能面板和证据文件）；pass 读的数据层事实只有五个，全部来自记录：

| pass 读的 x86 全局量 | 宿主里的来源 |
|---|---|
| `War3RenderState::GetGameTime()`（游戏内一天中的时刻） | `ShadowFrame.timeOfDay` |
| `CurrentShadowCasterTombstoneSerial()` | `ShadowFrame.tombstoneSerial` |
| `CurrentShadowStagePolicyRevision()` | `ShadowFrame.stagePolicyRevision` |
| 运行时配置关掉的模块 | `ShadowFrame.runtimeDisabledModules` |
| 帧号（pass 用它保证每帧只上传一次） | 执行端自己的帧序号 |

前四个是“帧事实”，4c-3 定下它们的语义（静态测试钉住）：

- **事实在两条记录之间保持不变。** 没有 `ShadowFrame` 的帧不改它们；宿主不把它们退回默认值。
  x86 上它们本来就是进程里的全局量，不随帧清零。
- **宿主里的初值等于 x86 数据层的初值**：时刻 −1（读不到）、墓碑序号 0、策略版本 1、没有关闭的模块。
- **序号和版本只被比较“变没变”**，不比较大小。x86 上两者只增不减，地图切换也不归零。
- **模块字里 pass 只问一位**：`shadow.taa`（`War3RuntimeModule::ShadowTaa`，第 9 位）。共用层里的常量
  `ShadowPassModules` 就是“pass 会问的位”，以后 pass 多问一个模块，这个常量和静态测试一起改。
- **进程内臂也经记录走**：夹具入口在 BeforeUi 把记录里的事实通过数据层自己的接口写进去
  （`SetGameTime`、发布墓碑、推进策略版本），然后 pass 照常从全局量读。记录要求的状态在这个进程里到不了时
  （序号或版本比数据层的小、一次要推进 64 步以上、或者要求的模块开关与进程的不同）入口拒绝这一帧。
  模块开关是进程启动时读环境变量定下的，所以“模块关闭”用另一对进程来对照，不是帧内切换。

八种记录，编号接着 4a/4b（12、13 是 4c-2 加的，14 是 4d-1 加的，15 是 4d-2 加的，16 是 4d-3 加的）：

| 编号 | 记录 | 走哪条消息 | 大小 | 内容 |
|---|---|---|---|---|
| 9 | `Lighting` | `FrameScene` | 492 字节（123 个字） | `War3RenderSettings` 的 `sun`、`shadows`、`dayNight`、`ambient` 四个结构的每一个字段 |
| 10 | `ShadowFrame` | `FrameScene` | 56 字节 | 这一帧的数据层事实与投射体集合的封口 |
| 11 | `ShadowCaster` | `AnnotateDraws`（挂在它的 draw 上） | 136 字节 | 一个投射体的世界矩阵、包围球、分类与身份 |
| 12 | `ShadowCasterAlpha` | `AnnotateDraws`（紧跟同一 draw 的 `ShadowCaster`） | 12 字节 | 这个投射体做 alpha 测试：哪一级纹理、阈值、哪组纹理坐标 |
| 13 | `PointLights` | `FrameScene` | 4 + 36×n 字节（n ≤ 16，最多 580） | 这一帧数据层的活动点光 |

### 3.1 Lighting

布局只写一次：`WAR3_SCENE_LIGHTING_FIELDS` 是一张 X-macro 表，每个字段一行（记录成员名、它在 `War3RenderSettings` 里的路径、
默认值、枚举的上限）。记录结构、编码、解码、“设置 → 记录”“记录 → 设置”五处都从这张表展开，不存在手写的第二份布局。

- 种类：`B` 开关（0 或 1）、`U` 无符号字、`Q` 64 位（两个字）、`F` 有限浮点、`E` 枚举（0 到上限）、`V` 四维向量（四个有限浮点）。
  解码时逐字段按种类校验，不合规整条拒绝。
- **加字段的绊线**：`war3_shadow_scene_input.h` 里断言四个设置结构的大小（40、280、104、20 字节，x86 与 x64 相同）。
  有人给设置加字段而没加进表，两个构建都编不过。另有运行时检查 `LightingDefaultsAgree()`：表里的默认值必须等于
  `War3RenderSettings()` 的默认值，不等则 pass 不运行（宿主拒绝，夹具入口返回错误）。
- **不在这条记录里的设置一律关闭**：体积光只在这一帧有 `VolumetricLight` 记录时打开（§3.7），
  单位描边只在这一帧有 `Outline` 记录时打开（§3.6）。

### 3.2 ShadowFrame

| 字 | 字段 | 说明 |
|---|---|---|
| 0 | `timeOfDay` | 游戏内时刻（小时）；负数表示还读不到。只有“跟随游戏时间”的光照时钟（`clockMode = 0` 且太阳随时间运动）用它 |
| 1 | `runtimeDisabledModules` | 运行时配置关掉的模块，一位一个。pass 只问 `shadow.taa` 一位（§2） |
| 2–3 | `tombstoneSerial` | 墓碑序号。变了说明有投射体被永久移除，pass 丢掉它留着的阴影图和旧帧状态 |
| 4–5 | `stagePolicyRevision` | 阶段策略版本，同上 |
| 6 | `casters` | 数据层这一帧发了多少条 `ShadowCaster` |
| 7、8 | `omittedCasters`、`omissionReasons` | 数据层自己没能发出的必需投射体数量与原因位；两者同时为零或同时非零 |
| 9、10 | `dynamicPoseCount`、`dynamicSkinnedOutputCount` | 动画投射体的姿态数与蒙皮输出数 |
| 11 | 保留 | 必须为 0 |
| 12–13 | `dynamicPoseSignature` | 任一姿态变化就变的签名 |

**这条记录是投射体集合的封口。** pass 只在“集合已封口且没有遗漏”时发布新的阴影图。执行端在封口时把三种遗漏都记进去：
数据层报告的遗漏、数量对不上（`casters` 与实际收到的条数不等）、执行端自己拒绝的投射体（§4）。
没有 `ShadowFrame` 记录的帧，集合不封口，四个帧事实保持上一条记录的值（§2）。
不发布新图时接收仍然用上一张已发布的阴影图，画面停在那里。实测（4c-1 回执 §3）已封口的**空集合**也是这样：
pass 不为零个投射体渲染阴影图。生产端一帧一条投射体都没发出来时，玩家看到的是上一帧的阴影，不是没有阴影。

**例外是生命周期刚结束的那一帧**（4c-3 回执 §3）：墓碑序号变了、策略版本变了、换了地图或设备重置之后，
旧阴影图已经作废，这时的空集合会渲染一张空的阴影图，画面等于没有阴影的世界。所以“上一张图留着”只在同一段生命周期内成立，
旧地图的阴影不会因为新地图第一帧没有投射体而留在屏幕上。

### 3.3 ShadowCaster

挂在 draw 上的记录：**几何就是这次 draw 自己的顶点缓冲和索引缓冲**，记录里不带几何。位置元素由两端各自从顶点声明里找
（`POSITION0`、三个浮点）。

| 字 | 字段 |
|---|---|
| 0–15 | `world`：物体到世界的矩阵 |
| 16–19 | `boundsCenter`、`boundsRadius`：世界空间包围球；半径 0 表示没有包围球（永不被剔除） |
| 20 | 四个字节：`mode`（只有 1 = FixedWorld）、`objectKind`、`lifecycle`、`boundsProvenance` |
| 21–23 | `category`（阶段类别）、`batchTag`（-1 未知）、`stage`（-1 未知） |
| 24 | `flags`：11 个已知位（混合、深度写、深度测试、加色、路径阻挡及其标记、单位身份已证、包围球身份已证等） |
| 25–28 | `batchHandle`、`rawcode`、`objectHandle`、`part`：数据层身份，执行端只比较和记日志，从不解引用 |
| 29–32 | `geometryKey`、`boundsGeneration` |
| 33 | `boundsAge`：包围球是几帧前算的；`0xffffffff` 未知 |

值在记录生成处（代理的 `AnnotateNextDraw`）和到达处（宿主解码）各校验一次；进程内夹具入口用同一个解码函数挡在 draw 前面。

### 3.4 ShadowCasterAlpha

挂在 draw 上，**必须紧跟同一个 draw 的 `ShadowCaster`**（线上规则 `CompanionFollowsCaster`：代理的 `AnnotateNextDraw`
和宿主解码各查一次；单独出现、或与它的投射体分在两个 draw 上都拒绝）。**纹理就是这次 draw 自己绑定的那张**，
记录只指明哪一级，与 §3.3“几何就是这次 draw 自己的缓冲”同一个道理。

| 字 | 字段 |
|---|---|
| 0 | `stage`：纹理级，0–7 |
| 1 | `alphaRef`：阈值，`D3DRS_ALPHAREF` / 255，0–1 的有限浮点 |
| 2 | `texcoord`：顶点声明里第几个 `TEXCOORD`（0–7） |

执行端：纹理取 draw 在那一级绑定的纹理（宿主用 `Owner::textures` 里那份的视图，进程内用 D3D9 纹理的采样视图）；
纹理坐标由 `FindShadowTexcoord` 在流 0 的顶点声明里找，必须是两个浮点；采样器是 pass 自己的，两端在运行前用同一个函数
（`BindShadowAlphaSamplers`）绑定。没有纹理、或坐标不是两个浮点，按 `Layout` 拒绝（§4）。

### 3.5 PointLights

`FrameScene` 记录：数据层光源管理器（`War3LightManager`）这一帧的活动点光，按它的顺序，最多 16 个。一个字是个数，
之后每个点光九个字：位置（三个浮点）、半径（≥ 1）、颜色（三个非负浮点）、强度（非负）、阴影强度（0–1，0 表示不投影）。
没有这条记录的帧没有点光。点光与点光阴影的开关和参数（是否启用、最多几个投影、立方阴影图分辨率等）本来就在 `Lighting` 里。

**pass 从光源管理器读点光，不从输入结构读**（`GetFrameSnapshot`），所以执行端在运行前把记录放进**本进程的**光源管理器
（共用层的 `ApplyPointLights`；宿主放进宿主自己那一个，进程内放进 x86 数据层那一个）。只有点光与管理器里现有的不同时才改写它：
pass 按管理器的代数和点光编号保留跨帧的东西（点光阴影的发布状态），游戏里管理器也只在点光变了时才变。

### 3.6 Outline

`FrameScene` 记录（4d-1）：单位描边。前 11 个字逐字段就是 `War3OccludedOutlineSettings`（开关、模式、是否走屏幕空间、
线宽像素、可见部分与被遮挡部分各画不画、RGBA 颜色），之后一个字是句柄个数，再跟 n 个句柄（最多 1024 个，不为 0）。
解码逐字段校验：开关只能是 0/1，模式 0 或 1，线宽有限且在 (0, 64]，颜色有限且在 0–1，字节数必须正好等于 44 + 4n。
`war3_shadow_scene_input.h` 断言设置结构是 28 字节，有人给它加字段而没加进记录，两个构建都编不过。
**没有这条记录的帧不画描边**，设置里的描边开关被关掉，句柄集合被清空。

pass 不从输入结构读要描边的对象，它对每个投射体问数据层 `War3RenderState::IsOutlineHandle(batchHandle)`。
游戏里句柄由地图经 JASS 命令放进数据层（`war3_jass_command_bridge.cpp`）。所以执行端在运行前把记录里的句柄放进
**本进程的**句柄集合（共用层的 `ApplyOutlineHandles`；宿主放进服务文件里它自己的集合，进程内放进 x86 数据层那一个），
集合与记录相同时不动它。宿主按 x86 数据层的规则给句柄取键（低 20 位，0 表示没有句柄），静态测试比对两边的这两条规则。

两条描边路径都对照过：屏幕空间（MRT 画两张遮罩，再按边缘合成到帧的颜色目标）与几何（在裁剪空间把投射体的顶点
向外推、只画背面，拿帧的深度做测试）。两者都只是重放 §3.3 的投射体，不需要新的几何记录。

### 3.7 VolumetricLight

`FrameScene` 记录（4d-2）：体积光。布局照 `Lighting` 的办法写成一张 X-macro 表（`WAR3_SCENE_VOLUMETRIC_FIELDS`，41 行），
每行一个 `War3VolumetricLightSettings` 的字段，记录结构、编码、解码与两个方向的转换都从它展开。种类多一种 `I`（有符号字，
采样数 `sampleCount` 是 `int`）。解码逐字段校验：开关 0/1，`quality` 0–2，浮点有限，字节数正好 164。
`war3_shadow_scene_input.h` 断言设置结构是 148 字节；运行时检查 `VolumetricDefaultsAgree()`（表的默认值等于设置的默认值），
不等则宿主拒绝、夹具入口返回错误，与 `Lighting` 相同。

**这条记录的含义是“这一帧跑体积光”**：没有记录的帧，设置里的体积光开关被关掉，阴影 pass 也就不渲染体积光专用的太阳阴影图。
游戏里体积光还受“后处理”模块开关（`War3RuntimeModule::PostFx`，进程内注册 pass 时读）与 `postFx.enabled` 管，
这两者不在记录里：生产端在它们关掉时不发这条记录（阶段 5.1）。记录里仍带 `enabled`，pass 读的就是它。

体积光 pass（`War3VolumetricLightPass`，`d3d9_war3_volumetric_light.cpp`）照本文 §2 的办法原样编进宿主：它除了 DXVK 设备
只认识阴影 pass（读太阳阴影图、体积光专用的太阳阴影图、点光阴影），另加一个“DXVK 设备 + 阴影 pass”的构造函数，
进程内仍从 D3D9 设备取阴影 pass。它跟在阴影 pass 后面，用**同一个** `War3PipelineInput`：阴影 pass 把它解算出的太阳写进
`input.lighting`，体积光照这个太阳打光（§5）。它读点光也走光源管理器，`PointLights` 记录照常经 `ApplyPointLights` 放进去。

两条路径都对照过：froxel 网格（`quality` 2，三个计算 pass 加合成）与光线步进（`quality` 0）。froxel 的历史混合要求帧序号连续，
两端的帧序号都是“已执行的 BeforeUi 次数 + 1”，所以历史在两端同样有效。体积光的另两种介质（雾体积、天气）见 §3.8。

### 3.8 体积光的介质：FogVolumes 与天气

体积光 pass 除了记录里的全局介质与高度雾，还散射两种介质（4d-3）：

**雾体积**（`FogVolumes`，`FrameScene` 记录 16）。地图作者用 JASS 放的局部雾，数据层的 `War3FogVolumeManager` 管着，
pass 每帧向它要帧快照（`GetFrameSnapshot`，派生出的世界→局部矩阵与包围球）。记录带的是**作者写下的值**，不是快照：
一个字的个数，接着每个体积 13 个字——形状（0 球、1 盒、2 圆柱）、是否活动、位置、半尺寸、旋转角（度）、密度、边缘羽化。
次序是管理器里的次序，最多 8 个（快照的上限）。执行端在运行前用管理器自己的 `AddSphere`/`AddBox`/`AddCylinder`、
`SetRotationDegrees`、`SetActive` 把它们建进自己的管理器（宿主是宿主进程里那一个，进程内是 x86 数据层那一个），
所以 pass 读到的矩阵在两端由同一段代码算出。解码照管理器的范围逐项校验（位置 |x| ≤ 10⁶，半尺寸 0.5–10⁵，旋转 |r| ≤ 360000，
密度 0–2，羽化 0–1，浮点有限；球的三个半尺寸相等，圆柱的 x、y 相等），字节数正好 4 + 52n。
`ApplyFogVolumes` 只在记录与上一次建的不同、或管理器被别的东西改过（代数变了）时才清空重建；没有记录的帧等于空记录。
体积的 `id` 与代数不上线：pass 不拿它们做判断。
雾体积只随体积光自己的介质散射，所以只在有 `VolumetricLight` 记录的帧里起作用。

**天气介质**（天气的雾与低空雪）。pass 读 `input.weather`；进程内是天气运行时每帧的快照。不另加记录：执行端从这一帧的
`Snow` 记录（4a，编号 6）取 pass 读的那部分（`WeatherFromSnow`：四个强度、区域、时间、风位移、种子、编号），帧序号与两个纪元
用执行端自己的。天气运行时的两个修订号不上线，留 0：天气介质由体积光 pass 另开的一个“只管天气”的实例画
（froxel 中档，**时间滤波关闭**，不读阴影图，不带点光），它不留历史，修订号无处可用。
天气介质**不需要** `VolumetricLight` 记录：有 `Snow` 记录且编号 > 0、雾或低空雪 > 0 的帧，体积光 pass 也要跑
（`VolumetricRuns(packet, shadow)`，两端同一个判断），这时它自己的介质是关的，只有天气实例画。

两种介质各有一项账（§4 `AddVolumetricRunFacts`）：散射了几个雾体积；天气实例在同一次运行里合成了没有。

### 3.9 不上线的东西

**帧序号、环形索引、地图纪元、设备纪元都归执行端所有，不在任何记录里。** 理由：这些值的含义是“执行端的哪个状态还有效”，
让 x86 发过来等于让数据层替执行端管它的缓存。宿主里地图纪元 = 会话代数 + 1（`SessionReset` 推进它），
设备纪元 = 渲染目标代数（`Reset` 推进它），帧序号 = 已执行的 BeforeUi 次数 + 1。

## 4. 记录 → pass 输入：两端共用一层

`war3_shadow_scene_input.h` 是执行端一侧的全部逻辑。x64 宿主和进程内夹具入口都只调用它，谁也不手工填投射体结构
（静态测试钉住：两端的源码里不出现 `War3ShadowCasterDraw`、`War3ShadowInstanceRef`、`producerCompleteness`）。

| 函数 | 作用 |
|---|---|
| `ShadowPassSettings(lighting, outline, volumetric)` | 记录 → 设置；描边只随 `Outline` 记录打开（4d-1）；体积光只随 `VolumetricLight` 记录打开（4d-2） |
| `ShadowWorldCamera(camera, …)` | 相机记录 → 世界相机；只有透视投影有效 |
| `FindShadowPosition(声明, …)` | 在顶点声明里找位置元素 |
| `AppendShadowCaster(scene, record, geometry, …)` | 一条记录加一份几何 → 一个投射体和它的回放实例；不能回放的返回拒绝原因 |
| `SealShadowScene(scene, packet, account, …)` | 绑定回放、按 §3.2 封口 |
| `ShadowPipelineInput(…)` | 组成 `War3PipelineInput`；场景被移入，一帧的投射体只回放一次 |
| `ShadowRunFactsOf(pass)` | pass 对上一次运行的自述（运行、阴影图是否渲染、接收是否绘制、用了/画了多少投射体、提前返回原因；4c-2 起还有 alpha 测试的投射体数、时间滤波的历史与作废原因、接收是否有点光阴影；4d-1 起还有是否画了描边） |
| `ShadowCasterPool` | 执行端自己的投射体内存池：动态缓冲在 draw 时拷进去（见下） |
| `FindShadowTexcoord(声明, …)` | 在顶点声明里找 alpha 测试用的纹理坐标（§3.4） |
| `BindShadowAlphaSamplers(input, pass)` | 给 alpha 测试的投射体绑 pass 自己的采样器 |
| `ApplyPointLights(packet)` | 把 `PointLights` 记录放进 pass 读的光源管理器（§3.5） |
| `ApplyOutlineHandles(packet)` | 把 `Outline` 记录的句柄放进 pass 问的描边句柄集合（§3.6，4d-1） |
| `VolumetricDefaultsAgree()` | `VolumetricLight` 表的默认值等于设置的默认值（§3.7，4d-2） |
| `AddVolumetricRunFacts(pass, facts)` | 体积光 pass 对上一次运行的自述并进阴影 pass 那一行账：跑了、画的后端（`War3VolumetricQuality`，没画为 −1）、合成了、它拥有的存储（4d-2；含天气实例的，4d-3）；散射的雾体积数、天气实例在同一次运行（帧序号与两个纪元相同）里合成了没有（4d-3） |
| `WeatherFromSnow(snow, …)` | `Snow` 记录 → `input.weather`，帧序号与纪元用执行端自己的，修订号留 0（§3.8，4d-3） |
| `VolumetricRuns(packet, shadow)` | 这一帧跑体积光 pass：有 `VolumetricLight` 记录，或有天气介质（§3.8，4d-3）。两端都只用它判断 |
| `ApplyFogVolumes(packet)` | 用管理器自己的接口把 `FogVolumes` 记录建进执行端的雾体积管理器；记录与上次相同且管理器没被改过时不动（§3.8，4d-3） |

两端只在一处不同：几何从哪来。宿主用它自己那份 draw 缓冲（`Owner::buffers`）；进程内用 D3D9 缓冲自己的 `DxvkBuffer`。

**动态缓冲在 draw 时拷贝**（4c-2）。调用方随时会改写动态缓冲（下一次 `Lock(DISCARD)`，或设备得先等 GPU 用完的普通 `Lock`），
而 pass 到 BeforeUi 才回放投射体，所以 draw 读到的那一段在 draw 时拷进执行端的 `ShadowCasterPool`，与进程内采集拷进
`war3_shadow_arena` 是同一个做法。字节的来源：宿主是它自己那份缓冲的映射（流模式下 draw 的上传已经写进去了），
进程内是 D3D9 缓冲当前映射的那一段。池每帧新建主机可见的块（1 MiB 一块，一帧最多 16 MiB），投射体拿着它的块，
回放它的命令列表拿到退休，然后还给设备；一帧的东西不留给下一帧，所以结束的地图或设备在这里什么也不留。

**执行端拒绝它不能回放的投射体**，并把拒绝计入封口：

| 拒绝原因 | 条件 | 归属 |
|---|---|---|
| `DynamicBuffer` | 动态缓冲拷不进执行端的池：draw 时拿不到它的字节，或这一帧的池已满（16 MiB） | 4c-2 起动态缓冲在 draw 时拷贝，只剩这两种情况 |
| `Layout` | 不是三角形列表，或位置不是三个浮点；alpha 测试的投射体没有纹理、或纹理坐标不是两个浮点 | 进程内的调色板蒙皮投射体（`PaletteSkinnedFF`）在 x64 走哪条路由阶段 5.1 定（§7）；游戏自己的蒙皮 draw 是动态缓冲里的 FixedWorld 投射体，不会落到这里 |
| `Range` | draw 读到缓冲之外 | 永远拒绝 |

## 5. 执行顺序与生命周期

- **顺序**：阴影先于其它 BeforeUi 特效。进程内是 pass 的注册顺序（`ShadowReceiver`、`VolumetricLight`、`SSAO`）；宿主在 `runBeforeUi` 里
  先跑阴影、`VolumetricRuns` 成立（有 `VolumetricLight` 记录或天气介质，§3.8）时接着跑体积光（同一个输入），
  再跑 4a/4b 的执行器，录进同一个命令列表。宿主的体积光 pass 在第一次要跑时创建，与阴影 pass 同寿命；
  它的天气实例在第一个有天气介质的帧创建，归它所有。雾体积在阴影 pass 运行前建好（`ApplyFogVolumes`）。
- **插入条件**：`BeforeUi` 标记到达时，场景包里有特效记录**或**有 `Lighting` 记录。仍然是“一个完成的世界场景一次”。
- **包的寿命**：`FrameEnd`、`Present`、`SessionReset` 三处都清空场景包、阴影包和这一帧已收到的投射体（宿主 `clearScene()`）。
  投射体在运行前被移入 pass 输入，账目同时清零；没有运行的帧也在帧尾丢掉它们。
- **纪元**：宿主每次运行前先调 pass 的 `InvalidateMapEpoch(地图纪元, 设备纪元)`。纪元没变是空操作；变了，
  pass 按它在进程内地图切换时的同一条路径丢掉跨帧状态。所以 `SessionReset`（地图切换）和 `Reset`（设备重置）
  不需要给阴影另加消息。墓碑与策略版本随 `ShadowFrame` 到达，pass 原有的比较逻辑照常工作。
- **pass 的寿命**：宿主的 pass 在第一次需要时创建，随创建它的设备一起销毁（在上下文之前）。

四种“生命周期结束”在两种模式下各走哪条路（4c-3 的对照门每种都有帧，静态测试钉住两边的入口）：

| 事件 | 代理 + 宿主 | 进程内 | 什么时候生效 |
|---|---|---|---|
| 投射体被永久移除 | `ShadowFrame.tombstoneSerial` 变 | 夹具入口向数据层发布墓碑，序号变 | 下一次 pass 运行 |
| 阶段策略改变 | `ShadowFrame.stagePolicyRevision` 变 | 夹具入口推进数据层的策略版本 | 下一次 pass 运行 |
| 地图切换 | 代理导出 `WarVKD3D9RequestSessionReset` 记下请求，在下一次 `Present` 之前发 `Op::SessionReset`；宿主的地图纪元 = 会话代数 + 1 | `War3RequestShadowMapEpochReset()`（游戏卸载地图时调的同一个函数），设备在 `Present` 里应用 | **下一次 `Present`**。请求之后、`Present` 之前的帧还属于旧地图，旧阴影图照用 |
| 设备重置 | 宿主 `Reset` 重建目标，目标代数（设备纪元）加一 | `Reset`/`ResetEx` 发起设备纪元迁移，设备在下一次 `Present` 里应用 | 代理：`Reset` 之后的第一次运行；进程内：`Reset` 之后的第一次 `Present` |

- **两种模式都要有 `Present`。** 进程内不 `Present`，地图切换永远不会被应用；设备重置之后不 `Present`，
  每一次运行都因为设备纪元过期被拒绝。夹具在每个生命周期事件后调一次 `Present`
  （宿主在离屏档位下返回 `E_NOTIMPL`，但 `SessionReset` 照样送达）。
- **地图切换请求在世界场景中间的处理两边不同**：进程内入口拒绝；代理接受并留到下一次 `Present`。夹具只在帧之间请求。
- **生命周期结束后 pass 手里的东西**：阴影图作废，下一次已封口且无遗漏的集合渲染新图；光空间基底的连续性不随地图或设备清掉
  （新地图第一帧的画面等于同一个太阳下旧地图最后的画面，不等于进程第一帧）。
- **宿主占的显存不随生命周期变**，两笔账都在宿主日志的 `D3D9 shadow-host` 一行里，对照门逐次运行检查：
  - `resourceBytes`：pass 自己数它拥有的每一张图和每一个缓冲（`War3ShadowReceiverPass::ResourceBytes()`）。
    第一次运行后就是定值，两种模式相同；第一个投影的点光出现时 pass 建它的点光立方阴影图，增长一次，之后又是定值
    （4c-2 回执 §7）；第一个屏幕空间描边的帧 pass 建两张描边遮罩（R8，与帧的颜色目标同尺寸），再增长一次（4d-1 回执）；
    第一个有体积光的帧 pass 建体积光专用的太阳阴影图（两层，边长是记录里的 `volumeSunResolution`），又增长一次（4d-2 回执）；
    第一个走 HiZ 的点光接触阴影帧，pass 的混合光追（`War3HybridRayTracing`，pass 拥有它）建 HiZ 金字塔、可见性图与一个
    常量缓冲，再增长一次（4d-3 回执）。混合光追的图与缓冲在 4c-3 加出口时漏数了（出口只数了 pass 每次运行清掉的两个视图），
    4d-3 补上：混合光追给出三个只读访问器，出口经它们数，静态测试要求它的每个图和缓冲成员都被数到。
    对照门把这些帧列在 `STORAGE_GROWS` 里，只允许在它们那里变。执行端的投射体内存池不是 pass 的成员，
    它的块一帧一还，算在设备分配器那笔账里。
  - 体积光 pass 自己的存储另记一项（`volumetricBytes`，`War3VolumetricLightPass::ResourceBytes()`，4d-3 起含它的天气实例），
    只在它跑过的运行里有值，froxel 与光线步进各是一个定值，天气实例建了之后加上它的，两种模式相同。
  - `deviceMemoryLog`：宿主设备分配器在每次运行后的已用字节和已申请字节（所有堆合计）。它是整个宿主的，不只是 pass，
    所以 pass 之外有东西被结束的地图或设备留下来也会显出来。从最后一种新资源出现之后（对照门里是 `shadow-return` 帧）
    到会话结束，已用字节必须是同一个值，已申请字节不得增长。
  数值见 4c-3 回执 §6。

## 7. 后面的段照什么做（给 Opus）

4c-2 每解除一种拒绝，都是同一套五步：

1. **读采集代码**（`d3d9_device.cpp` 的 `War3TryCaptureShadowCaster` 及语义生产者）里这一类投射体给 `War3ShadowCasterDraw` 填了哪些字段、
   几何放在哪。字段是值就进记录；是 x86 内存或 GPU 对象就要想清楚谁拥有、怎么过边界。
2. **加记录或加字段。** 新的回放模式是 `ShadowCaster.mode` 的新值加一条配套记录，不改已有字段的含义。
   布局写进 `war3_shadow_scene.h`，在 `AutoTest/test_render_host_annotation.h` 里加一份手写字节的布局测试（x86 与 x64 都跑）。
3. **在 `AppendShadowCaster` 里接上**，同时去掉对应的拒绝分支。两端自动一起得到它，不要在宿主或设备里各写一份。
4. **夹具加帧**（`test_render_host_d3d9_shadow.cpp`）：一帧只引入这一类投射体，对照门里加它的名字和期望。
5. **跑门**：阴影门、特效门（77 帧的哈希不变；4c-1 回执把两张表各数一遍记成 154）、GPU 参照门（48 个哈希不变）、切口门、静态测试。
   宿主源码在冻结构建之后不能再动（后面的门会查源码漂移），要改就重做冻结构建并把三道宿主门重跑一遍。

具体到各项：

- **动态缓冲**：宿主在 `addShadowCaster` 时把 draw 引用的顶点/索引范围拷进宿主自己的阴影内存池
  （进程内的对应物是 `war3_shadow_arena`，同样在 draw 时拷贝）。池的上限、溢出时计为遗漏而不是崩溃。
  流模式下 draw 是先录后提交的，拷贝必须排在这次 draw 的上传之后、下一次改写之前，这是这一项里唯一需要小心的地方。
- **蒙皮投射体**（4c-2 查明，延后，交阶段 5.1 定路线）：游戏（1.27a）自己不做顶点混合，`D3DRS_VERTEXBLEND` 在 draw 时恒为关，
  姿态后的顶点在 CPU 上算好、写进动态缓冲画出来。进程内阴影的蒙皮投射体却不来自 draw：数据层用模型 geoset 的绑定姿态几何、
  混合权重与索引建持久几何，回放模式 `PaletteSkinnedFF`，调色板是数据层每帧算的姿态；`ShadowFrame` 的三个 `dynamicPose*`
  字段就是这些姿态的计数与签名，pass 把它们混进回放封口。x64 有两条路：
  1. 在游戏的蒙皮 draw 上发 `ShadowCaster`：执行端 4c-2 已经具备（动态缓冲里的 FixedWorld 投射体），x86 什么也不多存；
     代价是只有画出来的单位投影，视野外单位的影子会缺。
  2. 走内容载荷：geoset 几何按内容键上传一次，调色板走 `BonesRef`，`ShadowCaster.mode` 加新值和一条混合布局记录；
     要定 `dynamicPose*` 在宿主里怎么算、怎么进封口，碰封口语义，归 Fable。
  选哪条取决于生产端怎么交出 geoset 与姿态，4c-2 没有先替它写第 2 条的执行端。
  （宿主固定管线确实不收顶点混合，但游戏用不到它，不是这一项的前置条件。）
- **alpha 测试**：投射体要采样它的漫反射纹理。纹理已经在宿主里（draw 绑定过），记录只需指明用哪一级绑定和阈值。
- **点光**：一条 `FrameScene` 记录带点光列表（位置、半径、颜色、是否投影）；`Lighting` 里点光的开关和参数已经在表里。
- **时间滤波**：pass 自己留历史，不需要新记录；需要的是夹具里连续多帧的期望。

**4c-3 留给 4c-2 的挂点**（对照门里已经有这些帧，新东西接上去就被它们检查）：

- **新的跨帧状态要在生命周期帧上清干净。** 宿主阴影内存池、蒙皮姿态、时间滤波的历史，都是“上一帧留下来的东西”。
  对照门的生命周期段（墓碑、策略、三次地图切换加一次游戏退出、一次设备重置）每一种事件后面都跟着一帧空集合
  （期望画面等于没有阴影的世界）和一帧完整集合（期望等于事件之前的画面）。新状态如果没有随事件清掉，
  会在这两帧里露出来。给新投射体加帧时，在生命周期段之前至少用到一次新状态，让它有东西可留。
- **资源字节数的出口要跟着改。** `War3ShadowReceiverPass::ResourceBytes()` 逐个点名 pass 拥有的图和缓冲；
  静态测试从头文件里找出每一个 `Rc<DxvkImage>`、`Rc<DxvkBuffer>` 成员，出口里没点到名就失败。
  内存池如果不是 pass 的成员（比如放在宿主的 `ShadowBeforeUi` 里），要另给它一个字节数并加进宿主日志的账目，
  对照门里“每次运行后字节数相同”的断言要按新的预期改（池会随投射体数量涨落时，改成“回到同一个值”）。
  宿主设备分配器那笔账（`deviceMemoryLog`）不用改代码就会把池算进去；对照门要求它从 `SETTLED` 帧起不变，
  新资源第一次出现的帧如果排在 `SETTLED` 之后，把 `SETTLED` 挪到它后面，不要放宽成“允许增长”。
- **每次运行都有一行账。** 宿主日志的 `runLog` 和进程内账目的 `last` 是同一组字段（静态测试比对两边的字段名）。
  新路径如果有新的可观察事实（比如时间滤波是否用了历史），加进 `ShadowRunFacts`，两边自动一起得到，
  再在对照门的期望表里给每帧写上期望值。
- **时间滤波的对照帧已经有一半。** 模块关闭的那一对进程里有一帧 `taa-requested`：设置里请求时间滤波、模块关闭，
  期望画面与不请求相同、`taaMode` 为 0。4c-2 的“模块打开且请求”那一帧与它配对，差别就是时间滤波本身。
- **跟随游戏时间的光照时钟只有第一帧是确定的。** pass 从第二个连续的“跟随游戏时间”帧起按墙上时钟平滑时刻。
  对照门里每个时刻帧之前都隔一帧固定时钟的帧。要连续多帧跟随游戏时间的期望，先想清楚怎么让两端的平滑走同一条曲线。

**新路径第一次跑到时，校验层会报 pass 原有的违规。** 进程内的命令流从来没有校验层覆盖，pass 一进宿主就第一次被校验。
4c-1 跑到的路径（太阳级联阴影图、接收）报了四类，已修（回执 §4）。同一写法在还没跑到的路径上原样留着，
等那条路径进了对照门、能被校验时再改，不要提前盲改：

| 写法 | 校验层规则 | 还留着的位置 | 归属 |
|---|---|---|---|
