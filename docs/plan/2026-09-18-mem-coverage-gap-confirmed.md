# 覆盖缺口**已核对确认**：`d3d9_mem.cpp` 的分配契约在**任何门禁**里都没有覆盖 — 2026-09-18（round 75）

>
> 本轮把这条**闭合**。

## 1. 核对方法（两条独立路径）

### (a) 宿主机测试是否引用 D3D9Memory / d3d9_mem

在 `src/` 全树搜索 `D3D9Memory|d3d9_mem`，并筛出路径含 `tests`/`test` 的文件：

```
src 下【测试文件】里提及 D3D9Memory / d3d9_mem 的:  （空）
```

⇒ **零命中**（`D3D9Memory` 这个模式同时覆盖 `D3D9MemoryAllocator`、`D3D9MemoryChunk` 等派生名）。

### (b) meson 门禁里是否有相关测试目标

```
meson 里 test() 注册数 = 76
其中名字含 mem/chunk/alloc 的:  war3_frame_recorder_memory, war3_frame_recorder_memory_control
```

⚠️ **易混之处（必须点名）**：这两个测试名字里有 `memory`，但它们测的是
**帧记录器（frame recorder）的内存控制**，与 **`d3d9_mem.cpp` 的 D3D9 分配器**是两回事。
不能因为它们存在就说"内存分配有覆盖"。（`war3_frame_recorder_memory_control` 正是我在
D 阶段做的 W4 记录器准入静态测试所在的族。）

## 2. 核对结论（覆盖缺口的准确表述）

| 门禁 | 是否覆盖 `d3d9_mem.cpp` 的 `Alloc` / `AllocLocked` 契约 |
| --- | --- |
| Python 静态门禁（263 个 `test_*_static.py`） | ❌ 零命中 |
| 宿主机 meson 测试（76 个 `test()`） | ❌ 零命中 |
| **门禁外的** Python 测试 | ✅ **仅 2 个**：`test_d3d9_memory_chunk_census_offline.py`（绿）、`test_d3d9_memory_chunk_tail_offline.py`（**红**，见 round 74 诊断 2） |

⇒ **准确表述**：`d3d9_mem.cpp` 的分配契约**只被两个门禁外的测试覆盖**，
  其中**唯一断言这些契约细节的那个是红的**且**长期无人看见**。

## 3. 这条确认**加强**了什么

- round 74 的表述是"**门禁内** 0 命中"；本轮升级为"**任何门禁**（Python + 宿主机）都 0 命中"；
- 因此"未来这条路径的真实回归不会被抓住"这句话，现在**覆盖了 meson 门禁**，不只是静态门禁；
- 同时它也**限定了**修复方向：把 `test_d3d9_memory_chunk_tail_offline.py` 的锚点更新后纳入门禁，
  是**唯一**能恢复这条路径可见性的动作（没有别的门禁可以"顺便"覆盖它）。

## 4. 依然不声称

- **不**声称"`d3d9_mem.cpp` 完全没有测试价值"（2 个门禁外测试存在，只是不在门禁里）；
