# x64 迁移：增强层拆分方案与数据层切口

日期：2026-10-30。作者确认"全面接管渲染层，增强层一并迁到 x64"后由 Claude 起草并开始实施。
本文件是方向与顺序的决策记录；实测数字来自同日回执，不是迁移完成或游戏内收益证明。
上级计划：[x64 渲染迁移](2026-10-11-x64-render-migration.md)。

## 1. 结论

1. 内存收益基本是全有或全无：只要 x86 进程里还创建 Vulkan 设备，约 617 MiB 的
   Vulkan/DXVK/驱动底座就还在（[内容驻留回执](../research/2026-10-30-x64-x86-content-residency.md)）。
   因此原版 D3D9 路径与增强层都要在代理模式下完全不依赖进程内设备。
2. 增强层拆成两半，不整体搬：
   - **x86 采集端（数据层）**：Game.dll hook、游戏内存读取、JASS/japi 原生函数、各 registry、
     每个 draw 的判断。hook 改的是游戏自己的代码，只能在游戏进程和游戏线程上同步执行；
     游戏对象指针跨进程无意义。
   - **x64 执行端**：阴影/CSM/SSAO/体积光/雾/天气/AA/后处理/GPU 蒙皮的 GPU 部分及其资源。
3. 两半之间只传数据，不传指针：每帧一份场景包（相机、灯光、雾、天气参数）、按 draw 顺序的
   标注记录（对象身份、阶段、标志），以及按内容身份上传一次的有效载荷（几何、骨骼矩阵）。
4. 产品形态是**同一个 x86 d3d9.dll 的两种模式**：现有进程内模式保留为回退；代理模式下
   该 DLL 只运行数据层和 D3D9 代理前端，不创建进程内设备。代理模式达到等价前不切默认。
5. 共享渲染核心（与 FORGE 共用的姿态/材质/蒙皮规则）不在迁移关键路径上：迁移搬的是
   WarVK 已有的 GPU 代码，不是重写模型绘制。它按原 W0–W5 路线另行推进。

## 2. 数据层切口实测（2026-10-30 基线）

工具：[run_x86_data_layer_cut_gate.py](../../AutoTest/run_x86_data_layer_cut_gate.py)，
只用 llvm-nm 读完成的 x86 构建目标文件，不编译、不启动游戏。每个目标文件按显式规则归类，
未知文件即失败。数据集从数据层出发，自动并入它需要的非核心文件（render/gpu_skin/shadow/
shader/tools 等），直到只剩通往核心（设备、DXVK、特效、ImGui）的边。

基线：`AutoTest/artifacts/x86-data-layer-cut-20261030-r2/receipt.json`（r1 因未归类
`version.o` 失败，保留）。构建 `build32_device_owner_fixed_function_20261029`，DLL
`26B411E99AAEEB2A53F064E1D221202915CE995C95742C1B9891659FD4C55A69`（即 T1 游戏内存测量所用 DLL），
该构建之后 `src/` 无改动。

| 方向 | 符号 | 说明 |
|---|---:|---|
| 正向：数据层 → 核心 | 113（49 条边，21 个文件） | 设备 42、特效 37、DXVK 41、ImGui 19（有 COMDAT 重叠，按定义者计） |
| 反向：核心 → 数据层 | 477（105 条边） | `d3d9_device.cpp` 388、swapchain 44、阴影 41、pipeline 33；天气/AA/体积光各 3 |

数据集共 114 个文件：数据层 70 个，另并入 44 个不触及核心的 render/gpu_skin/shadow/tools 文件。

正向切口分四类，处理方式不同：

| 类别 | 例子 | 处理 |
|---|---|---|
| 经具体设备类调用 D3D9 API | 自动实例化、队伍色、帧截图、着色器管理 | 改为经 `IDirect3DDevice9` 接口；属于设备内部的子系统归设备侧 |
| 数据层驱动特效 | JASS 雾体积、shaderpack、诊断查询、品牌提示 | 变成发往宿主的单向命令；getter 在 x86 留镜像状态 |
| 调试 UI 绘制 | `war3_shader_api` 经 ImDrawList 画覆盖层 | ImGui 留在 x86（输入在游戏窗口），绘制数据序列化给宿主 |
| DXVK GPU 对象 | GPU 蒙皮资源/包存储、阴影 arena、性能监视器 GPU 计时、异步截图 | 属于执行端，迁到宿主；与 CPU 部分拆文件 |

反向面说明真正的难点：特效文件本身很少直接读数据层，耦合集中在 draw 路径里的逐 draw 判断
（自动实例化、GPU 蒙皮拦截、插入点检测、阴影候选、可见性/语义谓词）。这些判断改在 x86
代理前端执行，结果写成标注随 draw 发送；只有 GPU 执行留给宿主。会改变游戏行为的拦截
（GPU 蒙皮跳过原生上传、自动实例化吞掉 draw、索引拆分）必须在 x86 同步决定。

## 3. 传输合同（D9C2 开发协议扩展）

按需协商，未协商时新 op 一律拒绝；不改已有 draw 记录布局。

1. **场景包**：每帧一次的非批次 op，携带带 schema/字节数的定长记录（相机、视口、时间，
   之后加灯光、雾、天气快照）。宿主只保留当前帧的最新一份。
2. **阶段标记**：少量非批次 op（世界开始、UI 前、帧结束等），按 draw 顺序定位插入点。
3. **draw 标注**：随 draw 批次发送的附加 op，紧接在其对应的 draw 批次之前；条目按批内序号
   引用 draw，越界、空批、夹入其他 op 都是协议错误并 fail-closed。不按 draw 单独往返。
4. **内容载荷**（后续）：几何、骨骼矩阵等按内容身份上传一次，标注只引用身份；x86 不保留副本，
   沿用内容驻留的预算与回读机制。

宿主侧先接一个记录器消费者，按帧计数并哈希，供门禁逐值核对顺序与绑定；真实执行器逐个接入。

S0 已完成第 1–3 项与记录器，见[标注传输回执](../research/2026-10-30-x64-annotation-transport.md)。
S1 的调用方普查与第一组（拓扑、渲染状态值域）见 [S1 回执](../research/2026-10-30-x64-s1-d3d9-path.md)：
游戏只用固定功能索引 draw 与托管 A8R8G8B8 纹理，RT/DS、StretchRect、着色器属于 WarVK 特效。
第二组 G3（协商尺寸 1..4096、分带回读、Peer 模式按真实尺寸呈现）见同一回执 §6，尚未接游戏窗口。
第三组 G4（游戏交换链 X8R8G8B8/D16/IMMEDIATE、按原版语义的窗口模式 Reset、改尺寸后跳帧）见 §7；游戏改窗口尺寸时由 fork 的 WM_SIZE hook 处理而不是 Reset，x86 侧还需要等价处理。
第四组 G5（缓冲普查：游戏只用三个 NOOVERWRITE/DISCARD 环形缓冲；NOSYSLOCK、1 MiB MaxBuffer、按 Lock 方式上传，stream 档位 DISCARD 换存储不等 GPU）见 §8；每次 Unlock 仍是同步往返，切 FVF 时宿主新建声明。
第五组 G2b（DEPTHBIAS 进 effects 包，宿主照原版选偏移表示与系数）与按 FVF 缓存声明（宿主声明 64+ → 3）见 §9；至此普查到的游戏 D3D9 用法在开发路径上都有了像素对照。
第六组 G6（异步档位下上传与状态同步不等回复，NOOVERWRITE 越过暂存 draw；ring 固定功能批 64 → 20 批）见 §10；状态变化仍切断合批，纹理上传仍同步。
第七组 G7（代理截获窗口的 WM_SIZE，像 fork 一样保留资源重置交换链；放大、缩小都与 fork 逐像素一致）见 §11；War3 分辨率字段的改写留给 S2。
S2 第一组（只用 D3D9 API 的队伍色、着色器管理、材质绑定、帧截图改经 `IDirect3DDevice9`；正向切口 113 → 104 个符号、49 → 46 条边）见 [S2 回执](../research/2026-10-31-x64-s2-forward-cut.md)，其中按处理方式拆了基线并列出后续各组。
与上文的差异：错绑或夹入其他消息时，宿主拒绝该消息并作废记录；同步档位下可恢复，异步批次下按既有合同是终止性的。
代理侧任何非 OK 都 fail-closed。

## 4. 实施顺序

| 阶段 | 内容 | 验收 |
|---|---|---|
| S0（本日） | 切口测量门与基线；传输合同第 1–3 项与记录器消费者 | 门禁 ratchet；原始协议正反例；CPU/GPU 门 |
| S1 | 原版 D3D9 路径补全：真实分辨率交换链、RT/DS、Reset、StretchRect、格式 | 按真实 census 覆盖；像素与 VVL 门 |
| S2 | 正向切口逐类归零（行为不变），代理模式入口 | 切口 ratchet 每轮只减不增；x86 构建与现有测试 |
| S3 | 特效按依赖从少到多迁移：天气 → AA/SSAO → CSM/描边 → 阴影/GPU 蒙皮 | 同输入两模式像素对照；内存与帧时间分账 |
| S4 | 代理模式在游戏内跑通，切换默认前的内存/性能/视觉门 | 实机门由作者在场安排 |

S1 与 S2 可以交替推进；S3 的每个特效都依赖 S0 的传输。共享内存命令环（T2 ④）在 S3
引入骨骼矩阵等大块载荷前完成。

## 5. 不变的约束

Game.dll guard、隔离桌面、玩家 DLL 不部署、不提交/推送/发布、失败回执保留。构建 BelowNormal、
`-j2`、门禁串行；本机有其他会话在跑大规模任务，避免占满资源。T0 快照与 1.5×/2× 阈值仍待作者确认。
