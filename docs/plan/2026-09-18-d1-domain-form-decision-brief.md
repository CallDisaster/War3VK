# D1 决策简报：domain 隔离的形态 (a) vs (b)（2026-09-18 主线程）

> 背景：今夜已落地**形态 (a)**（domain 作为**条目上的显式字段** + 8 处 fail-closed owner-check），但 D1（共享 key 类型）**未闭合**（见 `2026-09-18-registry-domain-isolation-record.md` §6）。本简报给证据与建议，**建议需你确认后才动代码**（当前树已冻结）。

## 1. 问题是什么

- 今天：Stage13 常驻表与 S1/Generic 路径**共用 key 类型**，但各自独立容器；同 key 跨 domain **不会天然不共享槽位**，只是被 **owner-check 拒绝**（拒绝时不触碰对方槽位/instances/lastSeen/字节账）。
- 形态 (b)：把 domain **下沉到 key 内部**（key 级隔离），使「同 key 不同 domain」在容器层面**根本不可能相遇**。

## 2. 证据（今夜实测）

| 事实 | 来源 |
| --- | --- |
| owner-check 拒绝路径**全部 fail-closed**：lookup 命中/常驻复核、publish（在任何 GPU 分配与 GC **之前**）、GC 擦除归属、reset move 前归属、两处域作用域 purge | 域隔离记录 §2 |
| **跨域碰撞反例已证明隔离生效**：离线模型 `legacy_cross_domain_hits=2` vs `isolated=0`；宿主 C4 反例 | 域隔离记录 §3/§7 F4-10 |
| 宿主域测试 46/46、域静态门禁 13 OK、域门禁+出口门禁在 256/256 内全绿 | 主线程亲跑 |
| 「两 domain 取值相同」会**编译失败**（显式索引 switch 的 duplicate case value） | 变异 2A |
| 6 个域拒绝计数已可对外观测（稳态应为 0） | 出口块记录 + 主线程亲跑 |

## 3. 形态 (b) 的代价（基于 T7 勘察的依赖点）

- **D1 触及 key 类型本身** ⇒ 影响面大于今晚任何一块：`War3ShadowGeometryRegistryEntry` 的查找/创建/擦除全部路径、离线模型、Stage13 常驻表的 key、以及可能的 hash/相等语义；
- 需与 **D7**（Stage13 自身两条回收路径仍绕过 registry 的 cap/expiry/bytes 账）**一起设计**，否则 key 级隔离后会留下"两套账"的更大不一致；
- 改 key 需要**新的 legacy 参考 + 宿主差分**（本夜范式），且 key 级属"结构性"改动，**值级差分咬不住**，必须靠结构断言 + 编译期约束。

## 4. 我的建议（请确认或否决）

**建议：暂缓 (b)，先做 D4/D5 的「只读分账」，且把 (b) 与 D7 合并为同一次改动。**

理由（可复核）：
1. **当前安全边界已成立**：形态 (a) + owner-check 已在行为层面阻断跨域命中（有反例证明），且拒绝路径 fail-closed；
2. **F3 仍无法执行**，而 F3 是"不劣化"的唯一判据 —— 优先把**观测与账目**做齐（D4/D5 只读分账 + pre-U5 基线协议），比提前做结构性重构更划算；
3. **(b) 单独做会制造中间态不一致**：key 隔离了、但字节/条目账仍单池（D4/D5 未做）⇒ 反而更难解释 F2-5「分账守恒」；
4. **合并 (b)+D7 更省一次全量门禁**（每次结构性改动都要重跑七条等价门禁 + 全量静态 + 生命周期等）。

## 5. 若你决定做 (b)，落地要求（照本夜范式）

1. 先补 `FROZEN` 增量项（若新符号不匹配语义命名族，baseline 用预算门禁同一 `DEF_RE` 实测、`budget=0` 与迁移**同一次改动**落地）；
2. 生成器加模式产出 legacy `.inc`，双向 fail-closed（模块正文 == `.inc` 正文 == 快照独立重抽）；
3. 宿主差分（逐用例整数精确相等 + 段末 `memcmp`）+ **结构断言**（key 内 domain 参与相等与 hash）；
4. **≥2 条变异真跑**：① 把 key 的 domain 参与相等去掉 ⇒ 差分红；② 把两个 domain 值写成相同 ⇒ 编译期或门禁红；
5. 全门禁在最终树上取数 + DLL 身份（**同源码重链接不逐字节复现**，登记最终树最后一次真实构建）。
