# 构建不可复现：**实测确证 + 机制定位 + 交付含义** — 2026-09-18（round 69）

> 起因：我注意到 DLL 哈希在源码内容不变时仍逐轮变化
> （`B3D08D6D` → `56A72D2A` → `514266DB` → `E2E0270A`）。本轮把它当成一个**待实测的问题**来做。

## 1. 对照实验（源码内容**逐字不变**，只更新 mtime）

```
① DLL = 514266DB2536488691AD89C286056B0C2D0E0D3698BB9AC4388147C07F71F448
② 把 war3_palette_object_evidence.h 以**同样字节**重写（内容逐字不变，只新 mtime）
③ 重建 → [30/30] Linking target src/d3d9/d3d9.dll
④ DLL = E2E0270AD6EDFFB0CDB3E65EB04D1C1307F05D4694AA6F954FE544534E6E41B8

⇒ 同内容不同哈希 = true
```

## 2. 机制（**两个**确定原因，都已指名/实测）

### 原因 ①：PE 头 `TimeDateStamp` = 链接时刻

```
e_lfanew            = 128        （签名 "PE\0\0"，OptionalHeader magic 0x10b = PE32）
TimeDateStamp       = 1789750964 => 2026-09-18T17:02:44Z
DLL mtime           = 2026-09-18T17:02:44.893Z
⇒ 相差 0 秒
```

⇒ **每一次链接都改变 DLL 字节**（这与"有没有重编译"无关）。

### 原因 ②：`__DATE__ " " __TIME__` 被嵌进数据段

```
war3_perf_monitor.cpp:3839   snapshot.meta.buildTimestamp = __DATE__ " " __TIME__;

实测在 DLL 字节内直接搜到：  "Sep 18 2026"   与   "14:52:09"
```

⇒ 该 TU 重编译时数据段也会变（注意：`14:52:09` **不是**本次链接时刻 17:02 —— 说明它来自
  更早的一次**编译**，即"链接未必伴随重编译"。两条原因**互相独立**）。

## 3. 交付含义（本轮的可执行改进）

1. **DLL 哈希不是源码指纹** —— 它同时编码了构建时刻；
2. 包内 DLL 哈希**在任何重建后失效**（源码可逐字不变）；
3. ⇒ 交付包的**身份依据必须是源文件哈希集合**（`HASHES.txt` 正是它）；
4. ⇒ 复核时**不得**用"DLL 哈希与包内不一致"推断"源码被改过"。

**已执行**：在 `stageC-chaintype` 与 `stageD-session` 两个包的 `MANIFEST.md` 末尾追加
「追加更正（round 69）」小节，写明上述对照实验、两个原因与复核方式；包内 DLL 仍是
**打包时那一份**（与包内 HASHES.txt 自洽），未替换成当前树的重建产物。

## 4. 我此前说法的地位

我在多处写过"**哈希变化不等于源码变化**" —— 那是对的，但当时**只是观察**；
本轮给出了**机制层面的解释**（PE 时间戳 + `__DATE__/__TIME__`）。

## 5. 不声称

- **不**声称 DLL 哈希**毫无用处**：作为"打包那一刻构建产物的标签"仍然有效；
- **不**声称已让构建可复现（**未做**，也未裁定是否要做；`__DATE__/__TIME__` 大概率是**有意**的
  诊断信息，去掉它会改变性能报告内容 ⇒ 需裁定）；
- **不**声称除这两条之外没有**其它**不可复现来源（我只定位并实测了这两条）；
- 全局边界：一张表不代表一种事实，一条链结算不代表观察完整，
  观察完整不代表对象已证明，更不代表阴影已恢复。
