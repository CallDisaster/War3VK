## 3. 怎么解释

**修复前**：同一对象**每帧**再发一条 FirstSight，每对象每帧固定吃掉 2 个非终态配额（首见+入队）。
每帧配额 64 ⇒ 每帧恰好只有 **32 = 64/2** 个对象能拿到链首；3584 的会话配额**全部**被这 32 个对象的重复发射烧光，
后来出现的 75 个对象「有条目、有终态、零阶段事件」。

**修复后**：每个对象只在**首次**观测时发一条链首 ⇒ 配额从"每帧 2N"变成"每对象一次性 2 条"，
于是**同样 3584 的配额**能覆盖 **64** 个对象（而非 32）—— **链首覆盖翻倍**。

⇒ **这正是修正① 的预期效果，且是"用同一份预算覆盖两倍对象"**。

## 4. 仍未解决的（配额仍是硬约束）

```
Drawn 的不同对象        : 107
含链首的链              :  64
缺链首的链              :  43      <-- 仍有 43 个对象拿不到链首
emitted − terminal      : 3584 = kNormalBudget   <-- 普通预算仍精确打满
```

⇒ **写方修正① 把浪费消掉了，但没有增加总预算**。配额仍是绑定约束，因此：

- **写方修正②**（把 `CanEmit` 预检提到 `Insert` 之前）仍有意义：它消除"有条目、有终态、零阶段"的假链；
- 但它**不会**让 43 个对象拿到链首（预算就那么多），而且会带来"预算紧张时对象完全不可见"的代价，
  需要显式丢失计数；
- 若要真正覆盖全部 107 个对象，须论证**提高 `kNormalBudget`** 或**降低每对象配额消耗**（例如首见链不必然消耗 2 条）。

**我不建议无论证地抬高预算** —— 那会改变取证开销，须单独论证（子线程 D 亦然）。

## 7. 顺带记录：`CAND_SHA` 钉死带来的一个操作问题

首次启动时驱动 **fail-safe 中止**：

```
ABORT: built candidate hash != expected; rebuild first
```

原因是 `CAND_SHA` 还钉着 c1 时代的 `BBEF3BBC…`。而 **round 237 已实测"只改注释也会改变 DLL 哈希"** ⇒
**每次重建都必须同步更新该常量**。

**这个中止本身是好事**（绝不会部署与验证过的不同的产物），但它意味着"改了注释忘了更新常量"会让人误以为驱动坏了。已更新为 `77CAEED9…` 并在注释里写明该教训。
