# 🎯 子线程 D 定案：FirstSight 疑点的真因是**普通预算饱和 + 错误的去重维度** — 2026-09-18

> D 用纯代码分析 + 算术恒等式定案，并**质疑了我给它的一个数字**。核对后：**D 对，我错**。

## 1. 先认错：我把两份导出的数字混用了

我在给 D 的提示里写了 `firstSightEmitted = 160`，但那个数字来自 **cpu-10488（全开运行）**；
而我让它解释的"32/107 条链缺 FirstSight"来自 **cpu-31736（DRAWS=0 运行）**，后者的实际值是 **1304**。

D 因此提出一个**无法成立的等式**并明确要求我以文件复核：
> 「`FirstSight = 1304` 与 `firstSightEmitted = 160` **不可能同处一份导出**…更可能是两个数字来自**不同批次导出**」

**核对结果**：

```
cpu-31736 : firstSightEmitted=1304   导出 stage counts FirstSight=1304   <- 配对成立
cpu-10488 : firstSightEmitted=160    导出 stage counts FirstSight=0      <- 该导出被环淘汰光了
```

⇒ **D 的怀疑完全正确**，原因是我混用了两份文件。**这就是独立验证的价值** ——
我此前多轮"自我复核"从未发现过这类跨文件的数字混用。

## 2. D 的核心发现（经双份数据确认）

### 2.1 普通预算精确饱和（这是真瓶颈）

```
cpu-31736 : emitted 3691 − terminalEmitted 107 = 3584 = kNormalBudget  ✅
cpu-10488 : emitted 3692 − terminalEmitted 108 = 3584 = kNormalBudget  ✅
```

我此前说"总预算 4096 没到、所以总预算不是瓶颈"—— **这话只对了一半**：
总预算确实没到，但**普通事件预算（4096−512=3584）是精确打满的**，
而饱和之后**任何非终态事件永远发不出去**。
（终态走 512 预留、不受影响 ⇒ 所以每条链都还有终态，造成"链都走完了"的假象。）

### 2.2 去重维度错了：`(对象键, 帧)` 而不是"对象"

`war3_palette_object_evidence.h:385-388`：

```cpp
} else if (e->lastFirstSightFrame == frames.renderFrame) {   // 只拦**同帧**
  m_counters.droppedDuplicatePerFrame++;
  return;
}
```

`lastFirstSightFrame` 只在**真的发射**时更新 ⇒ **跨帧不去重** ⇒ 同一对象每帧再发一条。
实机：32 个对象 → 1304 条（≈41 帧）。

### 2.3 真因因果链（D 的定案）

```
① 生产采集点 d3d9_device.cpp:23132 的 while 循环里，对**每个提交的 caster、每帧**
   调 NoteFirstSight + NoteEnqueued ⇒ 每对象每帧固定吃掉 **2** 个非终态配额；
② 每帧配额 kPerFrameBudget = 64 ⇒ 每帧恰好只有 **32 = 64/2** 个对象抢到配额
   —— 正与"32 条链有 FirstSight"吻合；
③ 每会话配额 kNormalBudget = 3584 被打满后，**之后所有非终态一律发不出**；
④ 但 NoteFirstSight 是**先 Insert（h:378）再判预算（h:389）**
   ⇒ 后出现的 75 个对象**有条目、有终态、却一条阶段事件都没有**；
⑤ 窗口关闭时终态对 !sawFirstSight 的条目**无条件写 stage=Drawn**（h:258-259）
   ⇒ 解析器看到 ["Drawn"]，判 rejectedStageMissingFromStream。
```

**关键算术**：`firstSightInserted − 有 FirstSight 的链数 = 107 − 32 = 75`
= **恰好等于缺链首的链数**。

⇒ **"75 条链缺链首"不是环的问题、不是解析器的问题、不是 arm 时机的问题，是写方在插入时被预算拒发**。
⇒ 而"只有 Drawn"是**终态兜底的假 stage** —— 那条链里**连一个真实的 Drawn 事实都可能不存在**。

## 3. D 给出的最小修正点（语义已定案，可以动手了）

我上一轮"不改写方"的理由是：**语义未定论**（每帧重发是否为本意）。**D 已经定案：不是本意，是 bug。**

### 修正①（一处条件）— 去重按条目而非按帧

```cpp
// war3_palette_object_evidence.h:385
} else if (e->sawFirstSight) {                 // 原：e->lastFirstSightFrame == frames.renderFrame
  m_counters.droppedDuplicatePerFrame++;
  return;
}
```

**语义立刻与 h:58-63 的文档一致**（"该对象首次进入观察"）；
**副作用是正向的**：每帧 2N → 每对象一次性 2 条，配额压力骤降，75 个对象有条件拿到链首。
**读方无需改**（链内 chainSequence 仍是 1,2,3,…）。

### 修正②（一处顺序）— 预算预检提到 Insert 之前

使"表里有条目 ⇒ 链首一定发过"成为**不变量**，杜绝"有终态、无链首"。
代价：预算紧张时该对象**完全不可见**（连终态也没有）—— 这是"不伪造事实"的方向，
但**必须显式记录一个丢失计数**，否则又变成新的静默丢失。

### 修正③（一行）— 终态不得给"从未发过首见的首见链条目"兜底写 `Drawn`

按 `firstReason` 区分：首见链（`NotChecked`，h:378）用 `StageOfRank(e.maxStage)`；
只有**拒绝链**才保留冻结的 `Drawn` 行为（保住 v1/v2 旧合同）。
否则解析器永远把"预算丢弃"读成"绘制命令已记录"。

### D 明确不建议

直接抬高 `kPerFrameBudget`/`kNormalBudget` —— 那会**把根因藏起来**且改变取证开销，需单独论证。**我同意。**
