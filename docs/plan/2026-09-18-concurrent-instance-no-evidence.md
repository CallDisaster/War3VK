# 采集尝试结论：并发实例无法产出证据 — 必须干净环境 — 2026-09-18

## 1. 本轮做了什么

在"孤儿 18948 仍存活"的情况下，用显式放行（`WARVK_ALLOW_EXISTING_WAR3=1`）启动了第二次运行（pid 45032）。

## 2. 结果：**没有拿到证据**，且原因已定位

```
status   -> WaitNamedPipeW failed: 2   (\\.\pipe\War3ControlPlane_45032 不存在)
arm      -> 同上
trigger  -> 同上
export   -> 同上
stop     -> ok:true stopped:true;  随后 "process 45032 exited"
restore  -> OK via rename-park (try 0);  RESTORE OK True
新导出    -> 无
```

**关键判据**：控制面管道 `War3ControlPlane_45032` **从未出现**；
而在上一次**干净**的 20 秒运行中，同一条管道是存在的（`shutdownSession.transportOk: true, ok: true`）。
⇒ 说明这次游戏**没有真正跑起来**（极可能因并发实例争用游戏文件而启动失败/提前退出）。
这解释了为什么既没有管道也没有导出。

## 3. 由此确立的结论

| 结论 | 依据 |
| --- | --- |
| **并发实例不可用** | 第二个实例无控制面管道、无导出、启动后很快退出 |
| **必须干净环境** | 干净运行时控制面管道正常（上一轮 20s 运行实证） |
| 恢复机制**已足够** | 两轮都靠 `rename-park` 把现场换回基线（进程存活亦然） |

⇒ 前置检查"拒绝脏环境启动"**必须保留**；显式放行那一条**在实践中被证明无效**。
这一点值得写下来：我原本以为"孤儿只持有 parked 文件、不影响站点"就够了，
但**站点完整性**与**游戏能否正常启动**是两件事 —— 后者是并发实例破坏的。

## 4. 因此需要一次干净启动

```powershell
taskkill /F /PID 18948     # 或任务管理器结束 War3.exe
```

之后运行采集（驱动已就绪：25s 后 `status`+`arm` → 运行 120s → `trigger`+`export`）；
干净环境下控制面管道应当存在，导出即目标④所需的**实机 palette 对象证据**。
