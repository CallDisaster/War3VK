# x64 迁移整体路线与模型分工

日期：2026-11-13。作者要求列出 64 位迁移的整体计划，并按难度分配模型：最难的部分用 Fable 5.2，
其余用 Opus 5.5。本文件是顺序与分工的决策记录，不改变上级计划的目标与约束：
[x64 渲染迁移](2026-10-11-x64-render-migration.md)、[增强层拆分](2026-10-30-x64-enhancement-split.md)。

## 目标与前提

- 目的不变：减轻 32 位游戏进程的地址空间压力。合成工作量下 x86 已用 VA 从进程内 DXVK 的
  739.9 MiB 降到代理模式 59.5 MiB（[内容驻留](../research/2026-10-30-x64-x86-content-residency.md)），
  游戏内估计可省 500–650 MiB VA、250–300 MiB 私有内存（推断，未实测）。
  11-17 实测（5.2 的同图 A/B，三张图）：可用地址空间多 566–620 MiB，专用字节少 251–326 MiB。
- 收益全有或全无：x86 进程里只要还创建 Vulkan 设备，约 617 MiB 的 Vulkan/DXVK/驱动底座就还在。
  所以阴影与 GPU 蒙皮这类最难的部分不能跳过。
- 产品形态：同一个 x86 `d3d9.dll` 两种模式。进程内模式保留为默认与回退；代理模式达到等价前不切默认。
  1.22 系列不推出 64 位。

## 阶段与分工

工作量为相对估计（小/中/大），不是工期。

### 阶段 0：对齐基线 — Opus 5.5，小（11-13 完成）

10-31 之后主线合入了 1.22.02 与 1.22.03，开发路径要先确认没被破坏。

1. 从当前 main 重建 x86 开发构建与 x64 宿主；重跑切口门（104/46 ratchet）与 GPU 参照门（主路径与 `--resize`）。
2. 把 1.22.03 新增的 x86 → 设备事件登记进传输合同的阶段标记清单：世界 `RenderScene` 进入/返回
   （光照作用域）、BeforeUi 第 10 层分界、帧末兜底条件、换图信号。代理模式下这些都不能再经
   `RunWithActiveDevice` 直接调设备。
3. 交付：回执、更新后的切口基线、阶段标记清单。
4. 结果：新基线 `x86-data-layer-cut-20261113-r2`（正向 106/48）；阶段标记清单需要新增 WorldSceneEnter/WorldSceneExit 两个标记
   和一条会话重置请求消息，BeforeUi 第 10 层与帧末兜底由宿主据此自行判定，不需要新消息。

### 阶段 1：传输层定型 — Fable 5.2，大（第 1、4、5 项 11-13 完成；第 2、3 项 11-15 完成）

后面所有特效都建在它上面，先定型。设计见[传输层设计](2026-11-13-x64-phase1-transport-design.md)。

1. 共享内存命令环替换管道往返（原 T2 ④）：批次边界、背压、序号、损坏检测，一律 fail-closed。
   同时按阶段 0 回执 §4 加 WorldSceneEnter/WorldSceneExit 标记与会话重置请求（换图）。
2. 内容载荷协议（合同第 4 项）：几何、骨骼矩阵按内容身份上传一次，标注只引用身份；x86 不留副本，
   复用内容驻留的预算与读回。
   结果（11-15）：内容在 x86 上只留索引、不占驻留预算，回读走专用的 `ContentRead`；宿主另有按键索引的仓库
   （单个 4 MiB、16,384 个、合计 256 MiB）。宿主里的消费者归 4c。
3. 有界上传窗口与 DISCARD 换存储（内存方向原 ③），定默认 x86 预算。
   结果（11-15）：默认档位 驻留上限 32 MiB + 空闲窗口 1 MiB（`d3d9_upload_window.h`），开发代理保持显式开关，
   阶段 5 产品接入时采用；数值待游戏内重锁普查后校准。
4. 宿主故障语义：心跳/超时检测；宿主崩溃或卡死时 x86 侧的行为（见“待作者确认”第 2 条）。
5. 验收：协议正反例；故障注入（杀宿主、卡宿主、写坏消息）；x86 VA 账本；像素与 VVL 门。
6. 第 1 项做完后量出的后续题目（不属于传输层，排期待定）：固定管线 draw 每个带 3,180 字节完整状态，1,025 draw 的帧
   一帧 3.28 MB 进环，环模式相对进程内仍是 3.3 倍（绝对差约 2.9 ms/帧）。要缩小需要状态去重/增量编码。

### 阶段 2：设备接口形状 — Fable 5.2 定型并完成第一组，中（11-15 完成）

[S2 回执](../research/2026-10-31-x64-s2-forward-cut.md)已查明：只把成员改成虚函数不够，调用处拿到的是
`final` 的 `D3D9DeviceEx&`，编译器照样去虚化；要改 `d3d9_device.h` 的类层次和几个大文件。

1. 定接口形状（设备实现纯虚服务接口，或另建注册表），让数据层不再依赖具体设备类。
2. 完成“诊断与测试入口”组（设备内部入口 13 个 + 特效诊断 11 个）。阶段 0 新增的两个正向符号也归设备内部入口：
   `War3SetWorldLightingScope`（代理模式由场景标记提供）、`startup_report::snapshot`（启动失败报告的适配器与设备
   创建记录要由宿主回传）。
3. 交付：接口设计说明与第一组实现，写清后续各组照做的步骤。验收：切口 ratchet、x86 构建、静态测试、GPU 参照门。
4. 结果（11-15）：没有改成“另建注册表、不动设备类”，而是两者各用在合适的地方——设备实例上的入口由设备类实现一个纯虚接口，
   不需要设备的入口走数据层里的注册表。新基线 `x86-data-layer-cut-20261115-r1`（正向 83/36）。

### 阶段 3：S2 其余分组 — Opus 5.5，中（11-15 完成）

照阶段 2 的模式做。每组符号的归类（进接口、内联、还是搬状态）与验收步骤见[阶段 2 设计](2026-11-15-x64-phase2-device-interface.md) §5：

1. JASS 雾体积与 shaderpack 改成单向命令，查询读 x86 侧镜像状态。
2. ImGui 覆盖层：ImGui 留在 x86，只交出绘制列表。
3. 实例化缓冲、材质编译剩下的具体类调用。
4. 完成后正向切口只剩“DXVK GPU 对象”一类，随阶段 4 迁移。
5. 结果（11-15）：见 [阶段 3 回执](../research/2026-11-15-x64-phase3-s2-groups.md)。新基线 `x86-data-layer-cut-phase3-20261115-r1`（正向 19/24），
   剩下的 9 个数据层文件（GPU 蒙皮资源与包仓库、阴影 arena、显存档位、alpha-test 负载、异步截图、帧历史、性能监视器）都只到 DXVK。
   与设计不同的两处：雾体积没有建镜像，状态整体归数据层，执行端反向读（代理模式下随 4d 进场景包）；ImGui 不需要新入口，
   数据层只用 ImGui 核心构建绘制列表，覆盖层本身由谁驱动归阶段 5 接线。

## 模型使用规则

- **升级到 Fable**：Opus 在同一问题上连续两轮找不到根因；或改动会触及阴影生命周期、传输协议、
  宿主故障语义的约束。
- **Fable 段落的交付物**：设计说明 + 第一组实现 + 测试，写进 `docs/plan` 或 `docs/research`，
  让 Opus 能照着继续。
- **高风险改动审查**：跨进程所有权与生命周期的改动即使由 Opus 写，也由 Fable 只读审查一遍。
- **会话方式**：需要大量上下文的阶段（1、2、4a、4c、5.1）直接把会话切到 Fable；单个设计问题或
  审查可以在 Opus 会话里开指定 Fable 的子代理，但子代理只知道交给它的说明。

## 待作者确认

1. **性能门阈值**：上级计划中“代理模式中位帧时间不超过进程内 1.5 倍、p99 不超过 2 倍”一直未确认。
   建议接受，作为切默认前的门；可选开关试用阶段不卡这一条。
2. **宿主崩溃时的行为**：建议安全退出并写报告、提示玩家，不做游戏中途退回进程内模式（资源都在宿主，
   热回退要在 x86 重新建设备并重建全部资源，风险与工作量都大）。5.1-e 已按这条建议实现（写报告、弹窗、结束进程，不存档）；
   作者仍未确认。
3. **发布目标版本**：建议 64 位作为 1.23 的可选开关，而不是 1.22.x 的补丁。
4. **v1.22.x 的阴影时间滤波越界读**（4c-2 回执 §4.1）：v1.22.00–v1.22.03 里，面板“阴影时域模式”选 Temporal 时，
   时间滤波的两个辅助 pass 给 17 个绑定的布局只写 14 个描述符；夹具里同一份 x86 渲染器在这一步崩溃。修复在工作区（未提交）。
   是否单独出 1.22.x 补丁、补丁前是否要实机复现，由作者决定。
5. **x86 产品 DLL 的静态 TLS**（[5.1-b 到 5.2 回执](../research/2026-11-17-x64-phase5-1-proxy-mode.md) §6.3）：
   迁移这条线上的 x86 构建用 llvm-mingw，产品 DLL 因此带一个 3.22 MiB 的 TLS 模板（函数内 `thread_local` 的定长缓存表），
   Windows 给进程里每个线程各分配一份：代理模式 45 个线程约 145 MiB，进程内 76 个线程约 245 MiB。
   1.22 发布用的 GCC 构建是模拟 TLS（按变量、按线程首次访问才分配），没有这笔固定开销。三条路：
   (a) x86 数据层回到 GCC 构建；(b) llvm 构建加 `-femulated-tls`；(c) 把这些表逐个改成已有的 `ThreadLocalLazyArray`
   （最大的一组在 M2-5 逐字节迁移保护的块里，线程登记表的容量也只有 16）。(a)、(b) 不动源码，建议先试；
   哪一条都要作者定，这一次没有动。
   **11-17 作者选 (b)。** 实验见 [TLS 实验](../research/2026-11-17-x64-static-tls-experiment.md)：模板降到 12 B，进程内低 2 GiB 多出 228–255 MiB，
   但 compiler-rt 的模拟 TLS 在 DLL 卸载时释放索引，导致 12/12 局退出崩溃；因此按 (b′) 自带访问函数实现，过门后才改交叉文件。
6. **帧时间差距怎么对待**：5.2 第一轮里代理模式的中位帧率是进程内的四分之一到五分之一，远超过第 1 条提议的 1.5 倍。
   切默认前必须解决；可选开关的试用能不能带着这个帧率开始，由作者定。
